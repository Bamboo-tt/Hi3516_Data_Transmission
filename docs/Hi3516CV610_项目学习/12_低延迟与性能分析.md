# 12 低延迟与性能分析：沿一幅图像寻找等待

[返回学习导航](README.md) · [上一章：部署与分层验证](11_部署与分层验证.md) · [下一章：分层故障排查](13_分层故障排查.md)

上一章把可观测的交接从板端一直连接到接收端。现在假设画面已经持续出现，但操作者发现画面落后于真实场景：应该提高帧率、减小编码片段，还是缩小网络缓存？回答之前，需要先找出等待发生在哪一段。

帧率描述每秒完成多少幅图像，延迟描述其中一幅从场景变化到屏幕呈现经历多久。流水线可以连续产出旧画面，因此高帧率与低延迟必须分别解释。本章沿同一幅图像推进，再用一次流量突发说明各层缓存如何把负载问题变成等待。

源码数值属于配置目标，算例均给出假设；本次没有板端或接收端实测。

## 12.1 先确定延迟的起点和终点

### 12.1.1 端到端时延覆盖哪些阶段

```text
场景变化
  → 曝光与 Sensor 读出
  → VI/ISP/VPSS 的处理与等待
  → VENC 编码并形成可输出单元
  → 应用被调度、取流、封装
  → 本地 socket/设备排队
  → 网络传输
  → 接收重组、解码、显示等待
  → 屏幕呈现
```

这些阶段可以流水重叠。例如上一部分图像进入后级时，Sensor 可能仍在读出下一部分。一幅图像要依次满足所经过的处理和交接条件，而多幅图像能同时处在不同阶段；这就是吞吐与延迟可以不同的原因。

分析总时延要沿同一幅图像的关键路径，把未重叠的等待计算进去；分析持续吞吐则要找哪个阶段长期消费最慢。不能把每层测到的完整工作区间直接相加，也不能用最快一层的处理时间代表整条流水线。

发送函数耗时只覆盖本地调用的一小段。即使 `sendto()` 很快返回，数据也可能仍在内核、无线承载、接收抖动缓冲或显示队列里。

PTS 是媒体时间标记，不天然等于“真实场景曝光开始的墙上时间”。【待确认】本项目 SDK pack 的 PTS 精确对应哪个采样事件、使用哪个时钟、与接收端如何对齐，仍需版本对应的 SDK 依据与运行测量。

### 12.1.2 帧周期说明机会间隔，不给出总时延

设帧率为 `f`，单位为幅/秒，则相邻图像的目标周期为：

`T_frame = 1 / f`，单位为秒。

【配置目标】A 的 Sensor/ISP 和 VENC 配置围绕 100 fps，目标周期为 10 ms。B 的编码配置为 30 fps，目标周期约 33.3 ms。

这只能说明目标采样或输出节奏。作为算例，若按 100 fps 连续输出，而当前显示始终落后最新完成图像 10 个周期，仅这段差距就约为 100 ms。这个例子没有假定本项目实际有 10 帧缓存，只说明持续出图不能排除历史数据积压。

实际帧率还受曝光、Sensor 时序、资源负载、丢帧策略和消费者速度影响，需要用明确口径统计完整图像。

## 12.2 曝光与读出：首先得到可处理的图像

### 12.2.1 缩短曝光不能无限保持画质

图像处理之前，首先要有足够的光信号形成像素。曝光时间决定积累信号的时长；光照较弱时，延长曝光可以增加信号，却可能增加运动模糊，并挤占目标帧周期。限制曝光之后，自动曝光只能在允许的增益等范围内继续折中，不能保证亮度与噪声都保持原状。

【源码实现】A 的 `true_isp_init()` 在 [new_main2.c](../../hi3516firm/new_main2.c) 中把自动曝光时间上限设为 10000 μs，也就是 10 ms，并限制模拟、数字和 ISP 数字增益范围。设计意图是让曝光约束配合 100 fps。

但 `main()` 随后调用 `isp_calibration_load_bin()` 导入 ISP/3DNR 参数。因此前面的赋值不能独立证明最终生效的曝光约束；若 PQ BIN 包含相关配置，可能覆盖先前设置。应以配套版本文档及导入后的参数回读判断。

Sensor 模式中的有效高度也不是完整帧周期：行时间、有效行、消隐、时钟及寄存器时序共同决定读出节奏。学习 SC500AI 模式表时，应把目标 fps、帧长和曝光限制联系起来，而不是只看宽高。

### 12.2.2 提前通知让后级更早有机会工作

【源码实现】A 的 `vi_init()` 将 VI 帧中断类型设为 `OT_FRAME_INTERRUPT_EARLY`，`early_line = 1080 - 200 = 880`；VI pipe 的低延迟行数设置为 `1080 / 4 = 270`。

提前中断与低延迟行数是不同配置：前者改变通知发生的时机，后者参与模块按部分图像推进的低延迟机制。它们都试图减少“必须等整幅图像完成才通知或向后推进”的等待，但不能简单把 880 行和 270 行相减作为节省时间。

【资料记录】本地 [MPP 开发参考](../../hi3516cv610/海思Hi3516CV610R001C01SPC020/ReleaseDoc/zh/01.software/board/MPP/MPP%20媒体处理软件%20V6.0%20开发参考.pdf) 的 PDF 第 88、295 页进一步区分：低延时机制在指定行写入后通知后端，并提供先写后读的硬件保证；提前上报中断没有同样的保证。因此提前通知越早，并非无代价地越好，后端读取不能追上尚未完成的写入。

该文档版本为 11，日期 2025-03-19，位于 R001C01SPC020 资料目录。它用于解释机制；与当前实际链接库的完整配套关系、该模式下两项设置的生效情况仍待确认。

若有经过确认的总行数 `H_total` 和帧率 `f`，近似行周期可写为 `T_line = 1 / (f × H_total)`。某个有效阈值相差 `ΔL` 行，对应时间量级约为 `ΔL × T_line`。

该估算需要总行时序和 API 阈值语义，本章不以 1080 个有效行代替 `H_total` 计算板端延迟。模式限制、驱动支持和调用返回值也决定配置是否真的生效。

## 12.3 图像处理：降低整帧等待，同时看清存储代价

### 12.3.1 A 的低延迟链路与 B 的通道不能混用

【源码实现】A 使用 `VI_OFFLINE_VPSS_ONLINE`，VPSS chn0 设置 270 行低延迟；VPSS group 的提前中断代码处于注释中。该程序不是“所有提前中断均开启”。

B 在 [sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 中采用 VI/VPSS 在线及 wrap 配置，`vpss_start()` 设置 group 的 `OT_FRAME_INTERRUPT_EARLY_END`，阈值为 group 最大高度的一半。

B 还对 **VPSS chn1** 设置 200 行低延迟，而 `venc_get_and_send_one_frame()` 只发布 **VENC chn0**。当前一一绑定关系是 VPSS chn0→VENC chn0、VPSS chn1→VENC chn1。因此不能将 chn1 的 200 行参数直接写成 RTSP 主码流的低延迟参数。

| 对照项 | A：自定义 RTP | B：RTSP 示例 |
|---|---|---|
| VI/VPSS 模式 | VI offline、VPSS online | VI online、VPSS online |
| VPSS wrap | 自定义配置关闭 | 主路径启用相关 wrap 配置 |
| VI 提前中断 | 880 行 | 主入口与当前 common VI 路径未见相同显式设置；驱动默认行为另行确认 |
| VPSS group 提前中断 | 相应代码注释 | group 高度的一半 |
| VPSS 通道低延迟 | chn0，270 行 | chn1，200 行 |
| 网络发布 | chn0 H.265 | chn0 H.264 |

【资料记录】上述 MPP 文档 PDF 第 92–93 页将两个模式字段分开定义：VI online/offline 描述 VI_CAP→VI_PROC 是否经过 DDR，VPSS online/offline 描述 VI_PROC→VPSS 是否经过 DDR。按此理解，A 的前段 RAW 路径离线，后段进入 VPSS 的路径在线，不能把 A 概括成整段 VI→VPSS 离线。

在线、离线、wrap 和低延迟阈值共同约束可用的数据推进方式。具体 DMA、DDR 总访问次数和行调度还由 SDK/驱动实现，现有应用源码不足以证明“完全不落 DDR”或“端到端零复制”。

### 12.3.2 用像素量理解带宽规模

NV21 是 Y 分量加交错 VU 色度的 4:2:0 格式。在宽高为偶数、无额外对齐且紧密排列的理想情况下，宽 `W`、高 `H` 的一幅图像占用：

`B_frame = W × H × 3 / 2` 字节。

代入 A 的 1920×1080，可得 3,110,400 字节/幅。若按 100 幅/秒计算，一次完整图像流的字节规模约为 311,040,000 字节/秒。

这里的“单次图像流规模”不是实测 DDR 带宽。实际 buffer 要使用 stride、平面对齐及 SDK 计算规则；多个模块读写、参考帧、RAW 数据和压缩存储会改变总访存量。该算式的作用是解释：高帧率原始图像很大，所以硬件通路和减少不必要的 CPU 搬运很重要。

VB 块数决定可同时容纳多少工作缓冲，不等于实际排队深度。更大的池可能避免资源不足，也可能容纳更多等待；需要同时观察资源占用和生产消费速率，不能看到“大缓冲”就认定一定更慢。

## 12.4 编码：让可发送的数据尽早形成

### 12.4.1 切片输出减少等待的单位

完整图像输出要等整幅图像编码到满足取流条件；切片输出让一部分编码结果较早可用，从而与后续编码重叠发送。

【源码实现】A 的 `encoder_init()` 设置 H.265、`is_by_frame = TD_FALSE`，同时启用切片、`slice_output_en = 1`、`split_mode = 1`、`split_size = 4`。

这相当于改变“下游最早可以拿到什么”的条件：后续部分仍在编码时，先完成的输出单元已经有机会进入取流与封装。它没有让接收器立即获得完整图像，后续仍需收到并重组同一图像的其余内容。

代码注释对 LCU 和行的表述不完全一致，具体 `split_size` 单位与可支持范围须按当前 SDK 的切片接口说明确认，不能仅据注释断言每片恰好对应多少像素行。

更早输出的代价包括：更多 NAL 或取流批次、更多分片和系统调用、协议头占比上升，以及对 NAL/pack 边界处理更严格的要求。一个 SDK pack 是否等于一片，必须通过 SDK 合同和实际码流观察确认。

B 通过公共 VENC 辅助代码使用按帧输出设置，其取流线程在 VENC fd 就绪后处理。不能把 A 的切片路径作为 B 已启用的优化。

### 12.4.2 码控限制平均负载，不消除瞬时突发

【配置目标】A 为 H.265 CBR，目标帧率 100、GOP 100、统计周期 1 秒，1080P 下目标码率字段为 4096 Kbit/s。虽然也构造了 AVBR 结构，但实际启用的是 CBR。

前面的行级推进和切片让数据更早出现，接下来必须回答链路能否及时送走这些数据。码率控制通过调节压缩结果，在画面质量与数据量之间选择。复杂运动或细节增多时，为压住平均码率可能提高量化强度，导致细节损失。

CBR 约束的是一定统计条件下的输出，不表示每幅图像或每个毫秒都产生相同字节。刷新图像和复杂画面仍可能形成短时峰值；即使平均值落在网络能力以内，这些峰值也会产生排队。

若用十进制 4096 Kbit/s 作为预算，平均每幅编码数据量约为：

`B_average = R / (8 × f)`。

其中 `R` 的单位为 bit/s、`f` 为幅/秒、结果为字节/幅。代入 4,096,000 与 100，约为 5120 字节/幅；它只是平均预算，SDK 码率单位及实际码控效果仍要核对。

A 将最大重编码次数设为 0，试图避免额外编码轮次带来的等待。代价是压缩器调整单幅图像大小的余地变小，需要依靠量化范围和其他策略维持码率。

同时配置了 `OT_VENC_FRAME_LOST_P_SKIP`，阈值表达式为 `custom_bit_rate × 1024 × 1.2`。这是编码模块的帧丢失策略配置，不是应用检查到 UDP 拥塞后丢某个 RTP 包；阈值单位、统计窗口和具体丢弃效果仍取决于 SDK。

### 12.4.3 帧内刷新分散负载，但恢复并非即时

A 启用按行帧内刷新，`refresh_num = 1`、请求 QP 为 30，同时关闭场景变化检测和自适应插入 IDR 的相关配置。帧内编码区域不依赖相同方式的先前预测信息；把这些区域分布到连续图像，可以分散刷新开销，减少集中刷新的突发压力。

GOP、帧内刷新、参考结构和 IDR 都会影响预测关系。不能因为 `gop = 100` 就断言线上每秒必有一个特定大小的 IDR，也不能把 `refresh_num = 1` 写成每帧都是可独立解码的完整图像。

【待确认】实际恢复周期需要看码流中的 NAL 类型、参考依赖、参数集发送和接收解码行为。弱网丢失一个参考区域后，画面可能逐步恢复，也可能等待更完整的刷新机会。

## 12.5 取流与封装：区分调度等待和复制成本

A 在 `processStream()` 中轮询状态；没有 pack 时外层 `usleep(1)`，查询或 GetStream 失败时函数内等待 100 ms。这 100 ms 是错误分支的恢复节奏，不能算作正常每幅图像的固定延迟；若错误持续发生，它却会显著拉低有效处理速度。

B 用 `select()` 等待两路 VENC fd，2 秒是没有事件时的超时。只要 fd 已就绪，调用可以提前返回，不能据此认定 RTSP 额外缓存了两秒。

【源码实现】A 的 FU 分片先复制到 `g_tx_buffer`，`transmit()` 再把 RTP 头和载荷复制到 `g_combined_buffer`。小 NAL 路径直接组合 RTP，少一次 FU 暂存复制。源码中的 `sendmsg()` 方案被注释，当前不能宣称采用了该方案，更不能宣称整个链路零复制。

B 每次取流分配 pack 描述符，RTSP 封装又把 RTP 字节写入自己的环形队列。优化时可评估复用有界描述符和发送缓冲，但必须保留第 10 章讲的 SDK 借还边界。

因此本层既有调度等待，又有字节搬运和协议处理。测量时应分别记录等待就绪、GetStream、有效字节量、封装、发送调用和归还；如果只给整个循环计时，就无法判断时间耗在等编码结果还是消费结果。

## 12.6 本地排队与网络：大缓冲可以隐藏问题

### 12.6.1 一次短暂降速怎样留下持续延迟

为了隔离队列机制，先用一个不含协议头开销的算例。假设编码侧持续产生 4 Mbit/s，某段网络在 0.2 秒内只能排出 2 Mbit/s，并且这段期间没有丢弃。队列增加量由流入与流出的差值决定：

`ΔQ = (R_in - R_out) × Δt / 8`。

其中速率单位为 bit/s、时间为秒，除以 8 后得到字节。代入算例，新增待发送数据为 `(4,000,000 - 2,000,000) × 0.2 / 8 = 50,000` 字节。

如果网络随后只恢复到 4 Mbit/s，而上游仍以 4 Mbit/s 产生数据，旧队列不会自行缩短：每送走一份，又进入同样多的新数据。这就是短暂卡顿结束后，画面可能持续落后的原因。若随后能以 6 Mbit/s 排出，净排空速度为 2 Mbit/s，这 50,000 字节还约需 0.2 秒才能消化。

因此处理积压有三类选择：提供高于持续流入的余量、降低上游持续负载、或丢弃已经太旧的数据。第三种还要考虑图像参考关系，随意丢包可能用花屏代替等待。上述算例只解释机制，不是当前链路测量。

### 12.6.2 非阻塞限制调用等待，不清除已有队列

【源码实现】A 请求 `SO_SNDBUF = 2 × 1024 × 1024` 字节，然后使用非阻塞 UDP。该值是设置请求；实际内核取值、系统上限和运行占用未在本次检查中获得，不能写成“实际一直缓存 2 MiB 视频”。

现在再看已经在队列前方的数据会造成多长等待。设前面已有 `Q` 字节，有效排出速度为 `R` bit/s，则送完这些字节的时间量级为 `T_queue = 8Q / R` 秒。它描述一个排队位置的等待，不是有持续流入时净排空整个队列的时间；后者还取决于刚才推导的流入与流出差。

例如假设真实排队量恰好为 2 MiB、排出速度为 4 Mbit/s，结果约为 4.19 秒。这是对假设队列的计算，不是该程序实测时延，也没有把请求的 socket 大小当成实际排队量。

更大缓冲可以吸收瞬时突发，却不能修复长期“生产速度大于消费速度”。低延迟设计需要同时决定允许等待多久、超过期限丢什么，以及丢弃后解码器怎样重新获得可用画面。

### 12.6.3 包长、包数与传输开销互相制约

A 的 `max_frame_size` 实际用作最大 RTP 载荷长度，为 1405 字节；加 12 字节 RTP 基本头、8 字节 UDP 头和无选项 IPv4 的 20 字节头，IP 包预算为 1445 字节。

名称中的 frame 不表示整幅图像。一个较大的 NAL 会成为多个 FU/RTP 包；每多一个包就多一次头部和发送处理，也多一个可能丢失的单位。尺寸太大又可能超过实际路径支持的包长。

【待确认】当前有线网络与资料中的 WFB 无线承载不是同一个包长环境。WFB 的实际接口、MTU、额外封装和无线设置需要在部署场景中核对，不能由这个常量证明无线链路已适配。

B 的队列按 RTP 包容量控制，慢消费者会被推进到仍保留的数据。它约束内存增长，但不是按“最新完整图像”丢弃；弱网下的画面恢复与参考帧处理仍需单独考虑。

## 12.7 接收与显示：发送端无法代替接收端作证

接收端可能为了应对乱序和抖动先缓存数据，再完成 NAL 重组、解码和显示。更深缓存通常能提高连续性，也会延后画面；更激进的即时播放则可能更容易出现抖动、丢帧或花屏。

当前主线源码没有给出接收播放器的完整实现及运行参数，因此不能推断其缓存深度、是否硬解、显示刷新率或丢帧规则。发送端低延迟参数全部正确，也不能替代接收链路的检查。

若需要真实端到端结果，应先规定观测事件及显示终点，并通过同一时基或可校准方法关联。单端用单调时钟测量内部区间有助定位，但跨设备直接相减未经同步的时钟值没有可靠意义。

这一阶段的证据应至少分别回答：报文是否到达、是否完成媒体重组、是否成功解码、何时显示。它们是逐层递进的事实。

## 12.8 先修正统计口径，再讨论快慢

### 12.8.1 当前 A 日志中几个名字容易误读

【源码实现】`sendPacket()` 每处理一个通过起始码检查的输入单元就增加 `frames_sent`。该位置不是完整图像完成点，切片模式下一幅图像可能触发多次；日志的 Frames 和 pps 因而不能直接解释为视频 fps。

`bytes_sent` 只在 FU 分片分支累计 FU 载荷，漏掉直接发送的小 NAL，且不含 RTP 基本头。`packets_sent` 在调用发送函数后递增，而发送函数不检查 `sendto()` 返回值。

Rate 的表达式还把 bit/s 除以 `1024×1024`，标签却写成 Mbit/sec。按本章十进制码率口径比较前，需要统一单位；例如同样的 1,048,576 字节/秒，当前换算会显示 8，而十进制结果为 8.388608 Mbit/s。这只是单位换算示例，并不补齐上述漏计字节。

首个统计窗口也有不同含义：`last_timestamp` 从零开始，第一次 `interval` 是当前单调时钟读数减零，通常远大于本程序实际累计数据的时间。第一次打印后才记录当前时刻，后续窗口才能对应两次打印之间的计数。另一个边界是 `bytes_sent / frames_sent`：若没有输入单元被计入却仍进入打印分支，零分母需要处理，当前表达式没有保护。

因此现有 Rate/Frames/Packets 更接近部分处理活动的计数，无法直接证明成功发送码率、实际帧率或接收率。继续优化前，应先明确计数对象、单位和分母时间区间，再讨论数值大小。

### 12.8.2 一组能够支持因果判断的观测量

| 指标 | 计数位置或依据 | 它能够回答的问题 |
|---|---|---|
| 完整编码图像数 | 经 SDK 语义核实的帧尾/图像序号与 PTS | 编码实际输出节奏是否达到目标 |
| SDK pack 数、NAL 数 | 分别在取流与 NAL 解析处 | 输出粒度是否变化，边界假设是否成立 |
| RTP 尝试包数与成功包数 | 组包处与发送返回值 | 损失是否先发生在本地提交阶段 |
| 成功提交字节、失败及主动丢弃 | 明确是否含 RTP 头，分开记录原因 | 码率和丢弃统计是否可比较 |
| 队列占用与最老数据年龄 | 各队列所有者 | 延迟是否来自逐渐积累的等待 |
| 接收、解码、显示图像数 | 接收端对应阶段 | 网络可达、可解码和可显示是否一致 |

这些是后续验证设计，不是本次已经采集的数值。定位性能时一次改变一个关键因素，并同时记录画质、输出节奏、丢失与时延分布，才能判断优化是否只是把成本移到了别处。

4. 减小切片后日志 pps 上升，能否据此证明帧率或端到端性能提高？

## 12.10 参考答案

1. 可以。10 ms 是相邻目标图像的周期，多幅图像可并行处于不同处理阶段；显示的数据若落后最新完成图像 10 个周期，仅这段差距就约 100 ms。吞吐与单幅图像等待需要分别测量。
2. 参数施加给 VPSS chn1，当前发布的是绑定到 VPSS chn0 的 VENC chn0。性能参数必须沿实际绑定和发布条件关联到同一条通路。
3. 降速期间积累 50,000 字节；恢复后流入与流出同为 4 Mbit/s，没有净排空余量。更大缓冲容纳积压，非阻塞改变调用等待方式，都不会自动删除已排队的数据。
4. 不能。更小切片可能增加 NAL、pack 或 RTP 数而不改变图像数，当前 `frames_sent` 也不是可靠图像计数。还需比较完整图像节奏、成功提交、接收解码、画质和端到端时延。
