# 05 SYS、VB 与缓冲区管理

[学习首页](README.md) · [上一章：媒体系统初始化](04_媒体系统初始化.md) · [下一章：VI、ISP、VPSS 图像通路](06_VI_ISP_VPSS图像通路.md)

上一章建立了采集、处理和编码对象。现在把注意力放到它们反复交接的图像上：一幅图像在内存中有多大，谁正在使用它，什么时候可以被下一幅图像覆盖？只有回答这些问题，初始化里的块大小、块数和工作模式才有具体含义。

本章先用一幅 NV21 图像理解布局，再分别解释 A、B 的实际配置，最后把缓冲放回持续生产和消费过程。布局算例属于原理推导，源码配置属于申请意图，实际分配与占用仍需板端数据。

## 5.1 图像需要可预测、可重复使用的内存

连续采集意味着 Sensor 不断产生新图像，而编码器可能仍在处理上一幅。如果每个模块随意申请、覆盖和释放内存，就无法保证硬件读到的内容完整，也很难控制分配耗时与内存碎片。

**SYS**是媒体系统公共管理层，负责初始化、模块绑定及相关公共接口。**VB**（Video Buffer）是视频缓冲池机制：把同规格图像块组织成池，模块需要时取得，使用完成后归还，后续图像再复用这些块。

在更底层，**MMZ**（Media Memory Zone，媒体内存区）提供供媒体硬件使用的内存管理资源。硬件访问内存涉及物理地址、连续性、对齐和访问一致性；普通 `malloc()` 给出的用户态指针，并不自动满足这些约束。可以把 MMZ 理解成可安排的媒体内存资源，把 VB 理解成其中图像缓冲的组织和复用方式。

VB 也不是所有媒体内存的总和。编码参考图像、模块内部工作区等可能另有需求，因此公共池大小相加只覆盖其中一部分。本地 [MPP 开发参考](../../hi3516cv610/海思Hi3516CV610R001C01SPC020/ReleaseDoc/zh/01.software/board/MPP/MPP%20媒体处理软件%20V6.0%20开发参考.pdf) §2.3.1 说明了池与块的关系，§12.3、§12.5 提供 VB、MMZ 调试入口；资料与当前 SDK 的对应边界见第 02 章。

历史部署文档记录过 `mmz=...32M` 加载参数。它说明某个方案曾怎样安排媒体内存，A、B 的 `sys_init()` 本身没有保证当前板端始终存在 32MiB 可用空间。判断申请能否成功，必须接上当前驱动加载配置和可用量。

## 5.2 从一幅 NV21 图像推导缓冲大小

### 5.2.1 先算有效数据，再算布局开销

A、B 的处理后图像主要采用 `YVU_SEMIPLANAR_420`，通常称 **NV21**。其中 Y 保存亮度，VU 交错保存色度；**4:2:0** 表示色度在水平、垂直两个方向都降低采样密度。

假设宽高均为偶数、每个分量 8bit、没有压缩和额外对齐，一幅宽 W、高 H 的图像包含 `W×H` 字节的 Y，以及 `W×H/2` 字节的 VU，总量为 `W×H×1.5`。

可以用一个 2×2 像素区域复算：四个位置各保留一个 Y，共 4 字节；这四个位置共用一组 V、U 色度采样，共 2 字节，因此平均每个像素需要 `6÷4=1.5` 字节。在 NV21 中色度按 V、U 交错排列；同样是 4:2:0 的 NV12 按 U、V 排列。两者尺寸和字节量相同，读反顺序仍会造成颜色错误，不能只靠缓冲大小判断格式相容。

以 A 的输出尺寸 1920×1080 为例：

```text
Y  有效数据：1920 × 1080       = 2,073,600 字节
VU 有效数据：1920 × 1080 ÷ 2   = 1,036,800 字节
合计：                         3,110,400 字节
```

这是未压缩有效像素的算术结果，尚未确定实际 SDK 分配的块大小。它解释了为什么后面需要编码，也让我们知道“图像宽高”只是内存预算的起点。

### 5.2.2 stride 决定下一行从哪里开始

**stride**（行跨度）是一行起点到下一行起点的字节距离。硬件可能要求按某个边界对齐，使 stride 大于一行有效数据长度。即使图像宽度不变，增加行间填充也会增加所需内存。

下面专为说明原理假设 Y、VU 的 stride 都为 2048 字节，Y 有 1080 行、VU 有 540 行；这不是当前 SDK 的分配结果，也没有计入额外平面对齐或压缩头。

```text
Y 平面
行 0：  [1920 字节有效亮度][128 字节填充]
行 1：  [1920 字节有效亮度][128 字节填充]
...
行 1079：[1920 字节有效亮度][128 字节填充]

VU 平面
行 0：  [1920 字节交错 VU][128 字节填充]
...
行 539：[1920 字节交错 VU][128 字节填充]

示例存储量 = 2048 × (1080 + 540) = 3,317,760 字节
比有效数据多 = 207,360 字节
```

在这个示例中，按 `base + row×1920` 找下一行就会读错位置；应使用真实 stride。一般多平面图像还需分别看各平面的地址、stride 和高度，不能假定每个格式都按相同方式连续排列。

实际代码把尺寸、位宽、像素格式、压缩方式、对齐和视频布局一起交给 SDK：A 使用 `ot_common_get_pic_buf_size()`，B 使用 `ot_common_get_pic_buf_cfg()`，wrap 则使用专用计算函数。**分配依据是完整布局契约，宽×高只是其中两个输入。**

### 5.2.3 输入位宽和处理后格式属于不同边界

A 的 MIPI 配置写 RAW10，VI PIPE 使用 Bayer 12BPP 描述，VPSS 输出采用 NV21。第一项描述输入传输，第二项属于 PIPE 图像属性，第三项描述处理后亮度与色度布局。

因此 A 为离线 RAW 环节申请的 Bayer 块，不能套用上面的 NV21 算例。B 主通道还使用紧凑段压缩，布局中可能包含不同的数据和描述开销；实际打包、转换是否被当前 SDK 支持，需要匹配接口约束和格式回读。

## 5.3 接口字段、有效池、实际分配和当前占用是四层信息

`ot_vb_cfg` 是启动时提交的配置，尚不是运行时池状态。两条主线都先清零结构体，再填需要的 `common_pool` 项；应先找出哪些项的块大小和块数非零。

| 所处层次 | 应观察的对象 | 能回答的问题 |
| --- | --- | --- |
| 接口字段 | `max_pool_cnt` 及当前版本语义 | 该字段的含义与是否生效；参考版本将它列为保留项 |
| 申请配置 | `common_pool[i].blk_size`、`blk_cnt` | 程序请求了哪几种规格、每种几块 |
| 实际分配 | VB 初始化返回、池查询、底层可用内存 | 哪些资源确实建立成功 |
| 运行占用 | 空闲块、持有者、归还与等待状态 | 此刻资源够不够、是否被长期持有 |

MPP 参考 §2.5.2.19 把 `max_pool_cnt` 解释为系统可容纳的缓存池数，并注明该参考版本中它是保留字段，内部固定取 `OT_VB_MAX_POOLS`；`blk_size` 或 `blk_cnt` 为零的公共池项不创建。即使另一版本改变保留行为，也不能把这个字段读成当前已经分配的块数。

由此可以直接判断：`max_pool_cnt=128` 不等于 128 个有效池，也不等于 128 幅图像已排队。判断运行时是否积压，要继续读占用数据，而不是只看初始化常量。

## 5.4 A 把三个 Bayer 块用于有内存交接的输入路径

A 的 [new_main2.c](../../hi3516firm/new_main2.c) 在 `sys_init()` 中使用 1920×1080、Bayer 12bit、非压缩、线性布局和默认对齐计算块大小，然后请求公共池 0 的三个块。

| 配置项 | 源码填写内容 | 能据此确认的范围 |
| --- | --- | --- |
| `max_pool_cnt` | 2 | 仅确认源码赋值；参考版本将该字段列为保留项 |
| `common_pool[0]` | SDK 计算的 Bayer 块大小，3 块 | 一个显式有效公共池配置 |
| 其他公共池项 | 清零 | 未请求其他有效公共池 |
| 补充信息 | 构造 JPEG、BNR motion 掩码，提交调用被注释 | 不能视为已启用补充信息 |

这与 A 的 `VI_OFFLINE_VPSS_ONLINE` 相互关联。按参考定义，VI 采集侧把 RAW 写入 DDR，处理侧再读取；这里的 Bayer 池与该离线 RAW 环节的需求方向相符。处理侧到 VPSS 则在线交接，详细路径见第 06 章。

配置提交后仍要经历 VB、SYS 初始化。A 没有检查相关返回值，因此源码中的“三块”首先是申请数量。即使申请成功，也只是这个公共池的块数，不能据此推导整个图传只用三个缓冲，或端到端固定缓存三帧。

## 5.5 B 用普通池服务子通道，用 wrap 服务主通道

B 的 [sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 在 `get_vb_cfg()` 中设置 `max_pool_cnt=128`。普通池从通道 1 开始填写，循环后再安排一个 wrap 池，因此当前双路配置形成以下结构。

| 公共池项 | 实际申请 | 对应需求 |
| --- | --- | --- |
| `common_pool[0]` | 保持零值 | 未按普通整帧方式填写主通道池 |
| `common_pool[1]` | 1024×768、8bit NV21、非压缩，SDK 算块大小，3 块 | 子通道普通图像缓冲 |
| `common_pool[2]` | `wrap_size`，1 块 | 主通道 VPSS-VENC 环绕缓冲 |

**wrap**（环绕缓冲）让生产者和消费者在满足硬件时序的前提下，按图像行块复用一段存储。它可以减少完整图像缓冲的需求，但要求下游及时消费，避免上游覆盖仍需读取的内容。这里的环绕单位是媒体图像行，后面 RTSP 库的 RTP 包环形队列则存储网络包，二者属于不同层。

### 5.5.1 wrap 大小来自时序和两路输出的共同约束

`get_wrap_cfg()` 先按 Sensor 类型提供 `full_lines_std`，默认 SC4336P 分支给出 1500，再调用 [sample_comm_vpss.c](../../sample_source/common/sample_comm_vpss.c) 的 `sample_comm_vpss_get_wrap_cfg()`。辅助函数准备帧率、是否全在线、Sensor 总时序行数及主/子输出尺寸，请 SDK 计算 `buf_line`；再结合格式、压缩和对齐计算 `buf_size`。

这条推导说明，主图像虽然是 2560×1440，也不能直接用一幅 NV21 大小代替 `wrap_size`；它既与布局有关，又与生产和消费节奏有关。改 Sensor、改帧率或改子通道尺寸，都应重新计算并检查结果。

如果 `get_wrap_cfg()` 遇到未支持的 Sensor，会关闭 wrap；普通池配置却仍采用当前“子通道池加 wrap 池”的生成方式。扩展 Sensor 时，应连同主通道关闭 wrap 后的缓冲需求一起核对。当前还不能凭这个分支确认某个新 Sensor 场景必然可用或必然失败。

B 通过 `sample_comm_sys_init_with_vb_supplement()` 提交 JPEG、BNR motion 补充信息，并检查主要初始化返回值。实际池建立与占用仍需查询，这些错误检查只是把申请意图向分配成功推进了一步。

## 5.6 在线模式和 depth 改变不同的交接关系

平台中的在线/离线描述硬件处理段之间是否经过 DDR，和网络是否联网无关。MPP 参考 §2.3.3 明确定义了两条边界：

- VI 在线/离线：VI_CAP 采集侧到 VI_PROC 处理侧，离线时 RAW 经过 DDR。
- VPSS 在线/离线：VI_PROC 到 VPSS，离线时 YUV 经过 DDR。

A 的 VI 离线、VPSS 在线，因而 RAW 段需要内存交接；B 两段都在线，可以省去这两个边界的整帧写读。编码参考图像、VPSS 输出和其他内部工作区仍然要使用内存，在线不能推出全链路零内存。

**depth** 则回答另一个问题：为用户主动取得通道图像保留多长的队列。MPP 参考 §5.4.39 给出了 VPSS 通道 depth 的这层语义。A、B 的 VPSS 通道均配置 `depth=0`，应用靠绑定把图像交给 VENC，没有在主链中持续主动获取这些原始图像。

因此 depth 为零仍可有绑定输出和硬件缓冲。若扩展 AI，需要主动 `GetChnFrame` 取得图像，就必须一起安排 depth、池容量、处理时长以及 `ReleaseChnFrame` 归还。只加入取图动作而长期持有帧，会改变原有资源的可复用时间。

## 5.7 从取得到归还，追踪一块内存的可使用窗口

**bind**（绑定）建立源模块与接收模块的数据关系。A 的 `vi_bind_vpss()`、`vpss_bind_venc()` 和 B 的公共绑定函数，使平台在图像产生后自动交接。应用不用在每帧循环里读取 NV21 再主动送给编码器，但平台仍需管理处理、持有和复用的先后。

下面用一个普通图像块说明生命周期原则。它不是闭源库内部状态机的逐项还原，wrap 的行级复用还具有额外时序约束。

```mermaid
flowchart LR
    FREE[可用块] --> WRITE[生产者取得并写入]
    WRITE --> USE[交给下游使用]
    USE --> HOLD[仍有使用者时保持内容]
    HOLD --> RELEASE[所有相关使用完成]
    RELEASE --> FREE
```

若下游仍在读，覆盖内容就会破坏它处理的这一幅图像。多个消费者、编码参考关系或用户态取图都可能延长持有窗口；这里以“持有与归还”解释共同原则，不假定当前库内部使用某种特定引用计数实现。

应用主动取得 VENC 码流后，也有明确的使用窗口，必须以 `ReleaseStream` 归还 SDK 数据。它与图像 VB 是不同对象，却遵循相同的所有权问题：归还表示应用不再读取该批数据，不表示远端已经收齐或解码。具体 pack 地址与有效范围将在第 07 章展开。

绑定也只能证明自动交接，不能证明端到端零复制。图像转换可能产生新输出，编码产生另一份字节流，协议封装还可能复制字节；是否复制应逐段核对布局、地址与实现。

## 5.8 缓冲数量为什么同时影响吞吐和延迟

生产快于消费时，**背压**表示下游速度不足开始影响上游。它可能表现为等待可用块、接口失败、丢帧或队列增长，具体行为取决于发生的模块和配置。

增加块数能吸收短时波动，也可能容纳更多过时图像。以一个纯示意的串行队列为例，假设消费者每处理一幅需要 `1/30s`，且新到图像前面还有 3 幅等待处理，那么仅前面三幅就需要约 `3×1/30s=100ms` 才能处理完；若还有一幅正在处理，还要计入它的剩余耗时。仅知道输入是 30fps，并不足以推出这个等待值。这也不表示 B 配置三个块便固定产生 100ms 延迟，因为块可能正被并行处理或用于其他用途。必须先确认块的实际角色、消费速率与排队状态，才能把数量换算成等待时间。

实际排查可以沿同一生命周期收敛：启动分配失败时查布局预算、可用 MMZ 和接口返回；运行一段时间才停顿时查占用是否回落、取得/归还是否配对；图像年龄不断增加时查各阶段消费者速度和队列，而不是只扩容某个池。

这些是验证思路，当前没有板端分配、占用或等待时长的测量。本章已经给出了读取这些数据所需的对象和关系。

## 5.9 自查问题

1. 在本章假设的 1920×1080 NV21 图像中，stride 为 2048 时需要多少存储？为什么不能拿它当 A 的 Bayer 池大小？
2. A 的 `max_pool_cnt=2`、池 0 三块、初始化成功、当前两个空闲块，分别属于哪层信息？
3. B 主通道没有普通整帧池项，怎样判断它的内存需求是否被其他机制覆盖？换 Sensor 时需检查哪些输入？
4. `depth=0` 为什么仍能绑定到 VENC？增加块数为何既可能减少瞬时停顿，也可能增加画面等待？

### 5.9.1 参考答案

1. 假设两平面采用相同 stride 且没有额外开销，存储量为 `2048×(1080+540)=3,317,760` 字节。A 的池按 Bayer 12bit 等属性计算，像素格式和布局不同，需使用对应 SDK 结果。
2. 分别是接口字段赋值、有效申请配置、实际分配结果、运行时占用。参考版本将 `max_pool_cnt` 标为保留项，不能从赋值 2 推断实际容量限制；应按有效 `common_pool` 项和运行状态判断。
3. 沿主通道的 wrap 配置、`buf_line`、`buf_size` 和额外公共池核对。更换 Sensor 需核对总时序行数、帧率、两路尺寸、在线模式与布局；关闭 wrap 后应重新安排普通缓冲。
4. depth 管理用户主动取图队列，绑定输出走平台关系。更多块可吸收波动，但消费者持续较慢时也可能容纳积压；要结合每块角色、持有时间和队列状态判断。
