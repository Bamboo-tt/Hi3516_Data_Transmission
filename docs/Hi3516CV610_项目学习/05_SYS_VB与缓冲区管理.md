# 05 SYS、VB 与缓冲区管理

本章解释图像在媒体模块之间流动时“存在哪里、谁在使用、何时可以重用”。上一章已经说明应用怎样创建系统；这里要进一步理解：创建模块并不等于给所有图像都准备了足够且布局正确的内存。

先记住一个关系：SYS 建立媒体系统的公共运行条件；VB 让各模块反复借用图像缓冲块；模块之间按配置和绑定关系推进处理，处理结束后归还资源。网络发送缓冲和编码码流缓冲属于后面的不同层，不能把它们一起叫作“VB”。

返回 [学习首页](README.md)。本章两条主线配置均重新核对；参考资料中的内存机制与当前板端实际分配状态分别表述。

## 5.1 为什么不能每来一帧就随意 malloc

**SYS**是厂商媒体系统的公共管理层，负责系统初始化、模块绑定和相关资源接口。**VB（Video Buffer）**是视频缓冲池机制：提前描述若干种缓冲块，让媒体模块按需取得与归还，避免把连续采集变成频繁、零散的内存申请。

**MMZ（Media Memory Zone，媒体内存区）**是供媒体硬件使用的大块物理内存管理区域。硬件访问内存有地址、连续性、对齐和访问一致性等约束，普通用户态 `malloc()`得到的指针并不自动满足全部要求。

【背景原理】可以把 MMZ 理解为底层可用于媒体业务的内存资源，把 VB 理解为组织其中图像缓冲块的一套分配与复用规则。VB 不是全部 MMZ 消费者：编码参考图像、模块内部工作区等还可能有各自需求，所以不能把公共池大小相加就声称得到了完整媒体内存占用。

【资料记录】本地 [MPP 开发参考](../../hi3516cv610/海思Hi3516CV610R001C01SPC020/ReleaseDoc/zh/01.software/board/MPP/MPP%20媒体处理软件%20V6.0%20开发参考.pdf)§2.3.1说明公共视频缓存池由同尺寸缓存块组成，模块使用完毕后释放回池；§12.3、§12.5提供 VB、MMZ 调试信息的阅读入口。文档对应参考版本，真实总量和占用仍需板端查询。

【资料记录】部署文档中出现过 `mmz=...32M` 一类驱动加载参数。这是某个部署方案给媒体内存安排的记录；A 的 `sys_init()`与 B 的 `sys_init()`没有直接在源码中设定“板上始终有 32MiB 可用媒体内存”。必须先核对当前加载配置，再判断内存预算。

## 5.2 一幅图像占多少字节，不能只看宽和高

原始像素要按某种**像素格式**组织。A、B 的处理后图像主要使用 `YVU_SEMIPLANAR_420`：亮度 Y 单独存放，色度 VU 交错存放，通常称为 NV21。4:2:0 表示色度在水平和垂直方向都降低采样密度，因此未计对齐与其他开销时，8bit NV21 的像素数据量是宽×高×1.5。

以 1920×1080 为例，理论有效像素数据是 3,110,400 字节。它有助于理解未压缩图像为什么远大于网络码流，但不能直接拿来替换当前所有 VB 块大小。

**stride（行跨度）**是一行起点到下一行起点在内存中的字节距离。硬件可能要求行宽向某个边界对齐，因此 stride 可以大于图像的有效行字节数。多平面图像还要分别考虑 Y、VU 的地址和跨度；压缩布局还可能包含额外的描述或头部。

【源码实现】A 使用 `ot_common_get_pic_buf_size()`，B 使用 `ot_common_get_pic_buf_cfg()`及 wrap 大小计算辅助函数，而不是一律写 `width*height*3/2`。这些辅助函数接收尺寸、位宽、格式、压缩方式、对齐与视频布局，将它们一起纳入分配需求。

尤其要区分三个不同概念：

- A 的 MIPI RAW10 配置描述输入链路的采样位宽；B 的实际接收字段另见第 06 章。
- VI PIPE 的 Bayer 12BPP 是该接口配置采用的图像数据描述。
- VPSS 的 NV21 是后处理后的亮度、色度布局。

它们出现在不同边界，不能从数值不同就直接判定错误，也不能假定内存字节数与线上位数完全相同。是否允许相应组合以及具体打包方式，需要匹配的 SDK 说明与实际格式回读。

## 5.3 必须分开的四个数：容量、配置、分配、占用

这是阅读 `ot_vb_cfg`最容易混淆的地方。

| 层次 | 需要看什么 | 它不能回答什么 |
|---|---|---|
| 配置容量 | `max_pool_cnt`的接口语义及版本限制 | 不能直接回答当前创建了多少公共池 |
| 实际配置项 | `common_pool[i].blk_size`与 `blk_cnt` | 不能证明初始化已经成功 |
| 实际分配 | VB 初始化返回值、池查询和底层可用内存 | 不能说明此刻有多少块正在被使用 |
| 运行占用 | 空闲块、模块持有、引用与归还情况 | 不能仅由启动时结构体推断 |

【资料记录】MPP 参考§2.5.2.19把 `max_pool_cnt`描述为系统可容纳的缓存池数量，并注明该参考版本中它是保留字段、内部固定取 `OT_VB_MAX_POOLS`；`blk_size`或 `blk_cnt`为 0 的公共池项不创建。即使以后使用的库版本改变这一保留行为，也不能把 `max_pool_cnt=128`解释为分配了 128 块图像或创建了 128 个有效公共池。

【源码实现】两条主线都先把 `vb_cfg`清零再按需填项。所以需要逐项查看哪些池的块大小与块数非零。字段填写完成只代表申请意图；真正是否分配成功，要看后续接口结果。

## 5.4 A：一个显式公共池，服务离线 RAW 环节

[new_main2.c](../../hi3516firm/new_main2.c)的 `sys_init()`填写的图像描述是 1920×1080、Bayer 12bit、非压缩、线性布局、默认对齐；随后设置：

| 项目 | 当前源码填写值 | 应如何理解 |
|---|---|---|
| `max_pool_cnt` | 2 | 一个配置字段，不等于两个有效公共池 |
| `common_pool[0].blk_cnt` | 3 | 为这一规格请求三个可复用块 |
| `common_pool[0].blk_size` | `ot_common_get_pic_buf_size()`结果 | 由当前 SDK 按布局计算，不能直接套 NV21 大小 |
| 其他 `common_pool`项 | 清零状态 | 源码未为它们配置有效公共池 |
| 补充信息 | 构造了 JPEG、BNR motion 掩码，但设置调用被注释 | 不能写成已启用附加 VB 信息 |

【源码实现】后续顺序是退出已有 SYS/VB、提交 VB 配置、初始化 VB、初始化 SYS，再设置 VI/VPSS 工作模式。A 没有检查这些调用的返回值，因此这里能确认的是“调用与配置存在”，不能从函数返回到 `main()`就认为三个块已分配成功。

【配置目标】A 使用 `VI_OFFLINE_VPSS_ONLINE`，其离线 RAW 段需要经过内存。本章下一节解释该模式的准确边界。整个系统的内存需求还包括 VPSS、VENC、ISP 等内部需求，不能把“一个显式公共池”写成“整个图传只需要三个缓冲块”。

## 5.5 B：子通道整帧池与主通道 wrap 池

[sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c)的 `get_vb_cfg()`设置 `max_pool_cnt=128`，从通道 1 开始配置普通池，循环结束后把一个额外池留给主通道 wrap。以当前双通道配置看：

| 公共池项 | 配置内容 | 对应目的 |
|---|---|---|
| `common_pool[0]` | 保持零值 | 没有为主通道按常规方式填写整帧公共池 |
| `common_pool[1]` | 1024×768、8bit NV21、非压缩，块大小由 SDK 算，3 块 | 子通道输出的普通图像缓冲 |
| `common_pool[2]` | `wrap_size`，1 块 | 主通道 VPSS-VENC 环绕缓冲 |

**wrap（环绕或卷绕缓冲）**让生产者和消费者按满足硬件约束的行块复用一段内存，以减少整帧等待和整帧缓冲需求。它不同于 RTP 库按包保存的环形队列：前者处理媒体图像行，后者处理已封装的网络包。

【源码实现】B 的 `get_wrap_cfg()`先按 Sensor 类型给出 `full_lines_std`，再调用 [sample_comm_vpss.c](../../sample_source/common/sample_comm_vpss.c)的 `sample_comm_vpss_get_wrap_cfg()`。辅助函数组合主/子输出尺寸、帧率与是否全在线等参数，请 SDK 计算 `buf_line`，然后计算 `buf_size`。

因此 `wrap_size`既不等于主图像总字节数，也不应该凭经验任意缩小。下游读取速度与上游写入时序必须符合约束；省内存的代价是配置和时序之间的耦合更紧。

【源码实现】B 通过 `sample_comm_sys_init_with_vb_supplement()`提交 JPEG、BNR motion 补充信息并检查主要返回值。该路径比 A 有更多错误传播，但仍需读取真实返回和池状态，才能证明实际资源建立完成。

【待确认】如果换成 `get_wrap_cfg()`不认识的 Sensor，该函数会关闭 wrap；但 `get_vb_cfg()`仍按现有“子通道普通池＋wrap 池”的结构生成配置。扩展新 Sensor 时不能只修改模式宏，应重新核对关闭 wrap 后主通道需要的缓冲方案。本次没有改代码或复现这一扩展场景。

## 5.6 在线、离线、wrap、depth 分别影响哪一段

**在线**不是“连上网络”，**离线**也不是“读取磁盘文件”。在本平台中，它们指某两个硬件处理段之间是否通过 DDR 内存交接图像。

【资料记录】MPP 参考§2.3.3明确：

- VI 在线/离线：描述 VI_CAP（采集侧）到 VI_PROC（处理侧）的关系。离线模式将 RAW 写入 DDR，再由处理侧读取。
- VPSS 在线/离线：描述 VI_PROC 到 VPSS 的关系。离线模式将 YUV 写入 DDR，再由 VPSS 读取。

所以 A 的 `VI_OFFLINE_VPSS_ONLINE`意图是在 RAW 段经过 DDR，而处理侧到 VPSS 在线连接；B 的 `VI_ONLINE_VPSS_ONLINE`意图是这两段都在线连接。不要把 A 画成“VI 输出 YUV 必然先落 DDR，VPSS 再读”的链路。

在线模式可以减少某些内存往返和等待，但更依赖模块组合及时序；离线模式提供内存交接空间，同时增加相应的带宽和缓冲需求。两者都不意味着系统从此不需要内存，编码参考帧和后续输出依然有各自资源。

**depth**是用户获取通道图像的队列长度。MPP 参考§5.4.39明确 VPSS 的这层含义。A、B 主线的 VPSS 通道均设置 `depth=0`，对应当前应用不从这些通道主动提取原始图像，而是把输出绑定给编码器。

`depth=0`不等于没有硬件缓冲、不等于禁用绑定输出，也不等于网络延迟为零。若后续扩展用户态 AI，改成主动 `GetChnFrame`取图，就要重新考虑 depth、取还配对及持有时间，而不是只添加一个取图调用。

## 5.7 bind 交接的是数据关系，资源仍有生命周期

**bind**在系统中建立数据源与接收者的连接。A 通过 `vi_bind_vpss()`、`vpss_bind_venc()`连接模块；B 通过公共函数连接同类关系。绑定建立后，媒体模块把产生的数据交给下游，应用不必每帧先读 NV21 再调用编码器送帧。

【资料记录】MPP 参考§2.3.2支持这种自动交接语义。但“应用不拷贝原始图像”不是“从 Sensor 到网卡端到端零复制”：模块内部可能写读不同图像缓冲，缩放可能产生新输出，编码产生新码流，用户态协议处理还会复制字节。

【背景原理】一个缓冲块在下游仍需要它时不能重用。多个消费者、用户态取图或内部参考关系可能延长持有时间；只有满足相应释放条件，块才重新成为空闲资源。这里用“持有与归还”说明原则，不虚构当前闭源库的引用计数代码。

对原始图像，绑定关系中的大部分交接由平台管理；对应用主动取得的编码码流，程序必须调用 `ReleaseStream`归还 SDK 缓冲。释放用于说明“我不再读取这批数据”，不代表网络接收端已经收齐或解码。

## 5.8 缓冲多一点，不一定让视频更顺畅

【背景原理】当消费者慢于生产者，**背压**表示下游的处理能力不足开始影响上游。它可能表现为块不足、生产等待、接口失败、主动丢帧或队列增长，具体行为要分别看发生在哪个模块与配置。

增加块数可容纳短暂波动，却也可能允许旧图像积压更久。对于实时图传，必须同时看内存、吞吐和图像年龄：用户看到的画面是否越来越旧，比“程序没有立即报错”更接近真实体验。

| 现象 | 本章先检查的依据 | 下一步判断 |
|---|---|---|
| VB 初始化失败 | 请求块大小和数量、MMZ 可用量、驱动与 SDK 配套、返回码 | 是预算不足、布局不支持还是基础环境未就绪 |
| 运行一会儿后上游无输出 | 空闲块变化、下游持有时间、Get/Release 是否配对 | 区分泄漏、慢消费者和资源配置不足 |
| 改小尺寸后仍分配失败 | 是否真正更新了格式、压缩、对齐和 wrap 计算 | 不能只按显示分辨率估算资源 |
| 画面越来越迟但没有崩溃 | 媒体池、取流线程、socket 与接收缓存各层的积压 | 不要只扩大某一层缓冲掩盖瓶颈 |

这些是检查路线，不是本次已有板端测试结果。实际占用及等待行为仍属【待确认】。

## 5.9 自查问题

1. **A 的 `max_pool_cnt=2`为什么不能读成“两池、每池三块”？**

   回答要点：只填写了 `common_pool[0]`三块；容量字段、有效配置项、初始化结果和当前占用是四件事。参考版本还把容量字段注明为保留。

2. **B 主通道没有普通整帧池项，是否一定忘记分配内存？**

   回答要点：当前主通道使用 wrap，并有单独的 wrap 池配置；要沿模式与计算函数理解，不能只找一块完整 NV21 图像大小。

3. **`depth=0`为何仍能向 VENC 输出？**

   回答要点：depth 控制用户取图队列，不是全部硬件缓存；绑定交接走平台的数据关系。主动取图扩展需要重新安排队列与归还。

4. **绑定后不再由 CPU 逐帧递交图像，为何还不能称为端到端零复制？**

   回答要点：模块处理、内存交接、编码输出和网络封装各有边界；必须逐段确认地址、布局与复制行为，不能由一个 bind 推断全链路。
