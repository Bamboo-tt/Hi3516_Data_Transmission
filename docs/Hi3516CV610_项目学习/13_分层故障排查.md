# 13 分层故障排查：找到最早失去证据的位置

[返回学习导航](README.md) · [上一章：低延迟与性能分析](12_低延迟与性能分析.md) · [下一章：扩展示例与无线部署](14_扩展示例与无线部署.md)

上一章说明了画面可能在哪一段等待。实际故障往往只给出一个末端现象：黑屏、花屏、越播越慢，或者退出没有结束。要把它变成可处理的问题，需要找出正常链路第一次没有完成的交接。

例如“端口能连接”只说明连接层的一部分条件成立；“VENC 有 pack”说明编码出口有数据；“收到 RTP”又把证据推进到另一层。它们不能互相代替，但可以组合起来缩小范围。本章先给出这种判断方法，再沿七类现象展开。

下面列出的是后续验证路径，本次没有执行板端或接收测试。检查以身份、日志、返回值、状态和数据为依据，不通过猜测管脚或修改寄存器试错。

## 13.1 排查前先固定“正在研究的是哪一个应用”

### 13.1.1 同名设备、相近示例并不代表相同配置

| 要固定的事实 | A：自定义 RTP | B：RTSP 示例 |
|---|---|---|
| 对照入口 | [new_main2.c](../../hi3516firm/new_main2.c) | [sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) |
| Sensor 依据 | 源码自定义 SC500AI 1080P/100 fps 模式 | `SENSOR0_TYPE` 编译宏；本地默认值为 SC4336P 4M/30 fps，可能被外部构建覆盖 |
| 编码及发布 | chn0 H.265，目标 100 fps | 两路 H.264，目标 30 fps，仅发布 chn0 |
| 网络入口 | 源码目标 `192.168.0.2:5622` UDP | 554 端口、`/test.264` 会话路径 |
| 文件与构建上下文 | 相对路径读取 PQ BIN；Sensor include 与库依赖需整理 | 依赖 SDK 外层构建配置及公共代码 |

【源码实现】这些事实来自当前文件；运行中的二进制是否由它们构建，仍需要交付清单、构建记录和板端文件对应关系。`sample_venc`、`rtp_demo2` 或某个镜像存在，不足以证明当前源文件已经运行。

先保留可追溯的运行上下文：程序身份、编译时 Sensor 选择、SDK/PQ 配套、启动参数、工作目录、网络目的地址，以及是否有其他媒体应用同时占用相同硬件通道。

若实际运行的是资料中的无线派生程序，还要先确认它是否把 UDP 发往本机 WFB 进程。当前 A 的远端目的地址不能与无线部署记录中的本机地址混用；详细边界见下一章。

### 13.1.2 用交接点划分检查层级

```text
板级资源/驱动就绪
  → SYS/VB 初始化
  → Sensor 控制与 MIPI/VI 输入
  → ISP/VPSS 产出图像
  → VENC 产出可取码流
  → 应用正确获取并封装
  → 本地成功提交网络
  → 接收端收到且正确重组
  → 解码与显示
```

RTSP 还多一条会话控制支线：监听 → 接受连接 → 解析请求 → DESCRIBE/SETUP/PLAY → 允许媒体发送。这条支线与编码链路在当前 `rtsp_sever_tx_video()` 的事件驱动处相交。

“日志打印了”“函数返回成功”“计数持续增长”“接收到了”“显示正确”分别属于不同证据。排查时先找到能够重复观察的正常点，再检查其紧邻消费者；若消费者也正常，就继续向后，而不是重新配置已经有证据支持的上游。

这可以看成一系列可区分的判断：没有进入应用，先研究产物与装载；应用已进入但没有图像，研究资源和采集；编码结果存在却没有正确 RTP，研究取流与封装；RTP 重组正确而没有画面，再研究解码与显示。每一项检查都应改变下一步位置，否则只是重复采集同层信息。

## 13.2 现象一：初始化报错，或打印 Ready 后仍无有效工作

### 13.2.1 先找第一个失败步骤

媒体初始化按依赖建立资源。SYS/VB 提供公共基础，VI/ISP 建立输入与处理，VPSS/VENC 才有可能接过图像。因此后面的绑定或查询失败，可能只是前面创建失败的结果；先找最早断点，才能避免追逐派生错误。

【源码实现】A 的多处初始化函数返回 `void`，直接调用 MPI/ioctl，主函数继续执行；`rtp_send()` 的 Ready 日志也没有汇总前面步骤结果。因此这行日志只证明执行到该打印位置。

B 在 `start_sys_vi_vpss()` 和 `venc_start_encode()` 中有明确返回值与回退路径，更适合顺着最早的错误追踪；但初始化成功仍不等于后续线程持续健康。

检查依据应是连续的原始启动记录、最早失败 API 的返回码及其配套 SDK 含义，再把模式、模块编号和资源状态放回同一时刻。若只有末端错误而没有上游结果，下一步是补最早未知操作的观察，而不是假定此前全部成功。A 缺失的返回值也不能用 Ready 字样补齐。

### 13.2.2 把文件依赖与硬件依赖分开判断

A 的 `isp_calibration_load_bin()` 从当前工作目录读取 `./sc500ai_1080P_100.bin`。文件找不到、读取不完整或导入失败，与 Sensor 时钟、MIPI 或 VI 创建失败是不同问题。

下一步判断应按最早断点收窄：若先失败于资源初始化，就先核对 SDK/驱动/内存及运行身份；若只有 PQ 文件读取失败，就核对运行目录、文件身份和导入结果，同时确认应用为何继续执行。不要直接跳去改传感器寄存器。

缺少构建追溯时，还必须先核对运行二进制。否则分析当前源码中的分支，可能根本不是板端正在执行的分支。

## 13.3 现象二：媒体初始化似乎通过，但编码器没有输出

### 13.3.1 先区分“上游没图像”和“下游不取流”

【源码实现】A 用 `ss_mpi_venc_query_status()` 查询 `cur_packs`，B 先用 VENC fd 的 `select()` 等待，再查询状态。`cur_packs = 0` 只说明当前查询时没有可取 pack，不能独自证明 Sensor 没有图像。

这里有两个方向：上游没有向编码器持续提供图像，或编码结果已经产生却没有被正确消费。前者涉及 Sensor/MIPI/ISP、VPSS 和绑定；后者涉及取流线程、输出缓冲与归还。只看屏幕黑色无法选出方向。

先分辨查询 API 失败、查询成功但持续为空、fd 不就绪、GetStream 失败。API 失败需要解释返回码；持续为空要沿输入检查；状态有输出而取流失败则需要关注描述符、通道和调用约定。把这些状态都归为“编码器坏了”，会抹掉最有用的区别。

### 13.3.2 沿相邻模块比较持续变化的证据

需要从当前 SDK 可用的状态接口或已有板端日志中分别取得：VI 输入是否持续推进、VPSS 目标通道是否有产出、VENC 是否开始接收、pack 是否产生、应用是否借还成功。接口名称和可用统计以配套 SDK 为准，不能编造板端字段。

若 VI 已有连续输入而 VPSS 无输出，检查该段模式、通道和资源；若 VENC 已有 pack 而网络没有新数据，重点转向取流与封装；若输出最初正常随后停住，优先检查未归还的 stream 和下游停滞。

B 还应核对 worker 的生命状态。`venc_get_stream_proc()` 在获取 fd 失败或 `select()` 出错后会退出，但主线程仍可在等待信号，进程存在不能替代 worker 活性证据。

一个特别有区分度的观察是“从一开始就没有输出”还是“运行后逐渐停止”。后者提示系统曾满足部分初始化前提，应重点比较停止前的借还数量、缓冲占用和 worker 活性；它仍不是缓冲泄漏的直接证明。下一步只跨越一个已有证据的交接点，不同时改码率、目的地址和播放器。

## 13.4 现象三：接收端确实有数据，却无法解码

### 13.4.1 先确认收到的是预期协议

这时网络可达的证据已经前进一步，但需要继续确认负载。A 发 H.265/RTP/UDP，B 发 H.264 并通过 RTSP 协商传输；RTP 动态负载类型值本身不能独立说明编码格式。

确认接收配置与实际应用一致，再检查同一受控时间段中的 RTP 头、序号连续性、时间戳分组、NAL 类型、参数集以及 FU 首尾。序号帮助发现传输单元是否缺失；时间戳帮助关联媒体时刻；NAL/FU 边界决定能否重组。只数 UDP 包，无法回答这三个问题。

序号缺口还要排除乱序和正常回绕。例如观察到 100、102、101，只能据此确认到达顺序变化，不能在看到 102 时就把 101 算作永久丢失；应按接收侧约定的观察窗口判断。A 使用 16 位 RTP 序号，65535 后回到 0 属于正常回绕；重新启动也会重置序号，而且 SSRC 固定，因此比较时还要固定同一次运行和抓取时间段。

比较发送侧原始编码数据与接收端重组结果时，应按逻辑 NAL 内容比较，明确去除或重建 Annex B 起始码、RTP/FU 头。两侧处于不同封装层，直接对完整网络包与 SDK 缓冲求相等没有意义。

一个图像可以包含多个 NAL，一个 NAL 可以拆成多个 RTP 包，SDK pack 又是另一种输出描述。丢了一个包，影响范围可能大于一个包对应的像素区域，因为解码还依赖完整 NAL 和参考图像。

### 13.4.2 核对当前封装程序的输入假设

【源码实现】A 的 `sendPacket()` 只剥除输入开头的 3/4 字节 Annex B 起始码，然后按一份 NAL 处理；没有扫描一个 pack 内所有 NAL。若 SDK 实际 pack 布局不符合这个假设，需要回到取流合同和样本确认。

其大 NAL 分片只接受代码列出的类型；FU 的第二个载荷头字节固定为 1。若实际码流使用其他合法头字段或不同输出组织，不能仅凭“H.265”三个字认定该封装适配所有情况。

还要确认 `offset ≤ len`、去起始码后至少有完整 NAL 头，以及 pack 数量没有超过描述符容量。这些属于输入和资源边界检查，当前源码未完整覆盖，不代表本次已经复现异常。

如果切换 A 的 `stream_mode` 为 0，发送的是已被当前处理逻辑剥除起始码或拆成 FU 的载荷，不能默认把收到的所有 UDP 数据拼接为可播放的 Annex B 文件。

下一判断由样本决定：编码出口数据已经缺失，就回查编码与取流；按相同 NAL 内容比较后两侧不同，就查封装、提交和网络损失；NAL 一致而仍不解码，再确认参数集、随机接入条件与解码器支持。这样才把“无法解码”逐步分成不同原因。

## 13.5 现象四：RTSP 能建立连接，但无画面或请求无响应

### 13.5.1 TCP 建连不等于完成 RTSP 会话

客户端需要先得到媒体描述，再建立传输并进入播放状态。TCP 建连之后，应用仍可能尚未 accept，或没有继续处理 DESCRIBE；后面的 SETUP、PLAY 也可能各自失败。因此“能连接但无画面”首先要分成“控制流程未完成”和“控制完成但媒体不可用”。

检查实际请求、响应及客户端状态，确定最后完成的方法。当前会话路径为 `/test.264`，媒体为 H.264；SETUP 的 UDP 端口或 TCP interleaved 通道则决定下一步在哪里观察媒体。

### 13.5.2 当前实现要同时检查视频驱动事件是否活跃

【源码实现】[rtsp_demo.c](../../sample_source/rtsp_4m/rtsp_lib/rtsp_demo.c) 中 `rtsp_sever_tx_video()` 末尾才调用 `rtsp_do_event()`。应用没有独立网络循环，所以主码流停止也可能使会话请求无法继续处理。

优先核对 `venc_get_and_send_one_frame()` 是否持续处理 chn0 的可发布 pack，再核对事件函数是否得到调用。只有 chn1 仍有输出不能证明 RTSP 服务活跃，因为应用不发布 chn1。

若 DESCRIBE 已响应但解码初始化信息不完整，检查实际 SPS/PPS 获取。库中用于决定是否继续解析 H.264 参数集的条件重复检查 `pps_len`，没有在该条件中检查 `sps_len`。例如新会话先单独收到 PPS、尚未取得 SPS，后续调用就可能因为 `pps_len > 0` 而跳过解析；[utils.c](../../sample_source/rtsp_4m/rtsp_lib/utils.c) 的 SDP 构造又要求两者齐全才写入参数集。这个分支解释了应检查怎样的到达顺序；客户端能否从后续 RTP 取得所缺参数还要另查，不能直接宣称所有客户端都会失败。

若 SETUP/PLAY 已完成且服务端提交媒体，转去检查协商的传输、接收重组及解码；若请求根本不推进，先处理事件驱动断点，播放器缓存参数不是首要方向。

## 13.6 现象五：弱网花屏，偶尔恢复，或某个客户端明显落后

### 13.6.1 区分报文损失与解码恢复

压缩图像需要完整的编码单元，也可能依赖先前图像。一次 RTP 缺失可以使 FU 重组不完整；丢失某个参考图像后，后面的包即使完整到达，也未必立刻恢复正常。因此“网络已经恢复”与“解码状态已恢复”有时间差。

接收端序号缺口与异常画面的时间关系有帮助，但还需和发送侧成功提交对照：包可能在应用主动跳过、提交失败或网络途中丢失。确定损失层级后，才知道该研究发送资源、链路容量，还是参考刷新。

A 的 `transmit()` 忽略 `sendto()` 返回值，现有 `packets_sent` 也会在发送失败后增加。因此当前发送日志无法排除本地提交失败；不能只把损失归因于无线信号。

B 的共享 RTP 队列会覆盖旧包，并把落后的客户端推进到仍有效的队头。这保护队列容量，但不会自动选择下一张可独立解码的完整图像。客户端即使继续收到新包，也可能暂时缺少正确参考数据。

### 13.6.2 TCP 模式仍要检查应用层续传

若使用 TCP interleaved，网络层重传并不能修复应用写入错误。当前 `rtp_tx_data()` 未完整处理正数短写，且没有记录头已发出、载荷暂不可写时的续传进度。

【待确认】在慢连接条件下是否触发，需要实际返回值和字节流证据。本次确认的是缺少相应状态机制，不是已获得现场复现。

下一步应根据证据选择方向：链路容量不足就评估码率峰值与承载预算；本地发送失败就定位队列与返回值；慢客户端跳过数据就检查恢复边界；TCP 字节边界损坏则检查发送进度管理。

不要为了消除花屏无限加大缓存。更深缓冲可能让画面更连续，却把问题转化为更大的控制与观察延迟。

## 13.7 现象六：刚启动流畅，运行一段时间后延迟增加

### 13.7.1 先观察“数据有多旧”，再看平均吞吐

第 12 章的算例说明，短暂低吞吐留下的积压，在流入与流出恢复相等后也不会自动消失。长期供给更大，或者反复突发后没有足够排空余量，都可能让旧数据越来越多。单看平均发送速率，无法知道眼前正在显示的数据有多旧。

检查依据应覆盖队列长度及最老数据年龄：编码器待取数据、应用队列、socket/网络设备队列、无线承载队列、接收抖动缓存和解码显示队列。当前缺失的观测应标为待增加，不能用 `SO_SNDBUF` 请求值替代实际占用。

可沿同一媒体时间标记比较阶段间年龄，但要先确认 PTS 单位和时钟来源；跨设备比较还需要同步或校准。单看发送函数耗时变小，不说明屏幕上的图像更新更快。

### 13.7.2 根据增长位置选择下一判断

若 VENC 待取数据增加且 worker 忙于网络，问题可能在取流消费者；若发送端时间关系稳定、接收显示越来越旧，继续检查接收缓存与解码速度；若只有慢客户端落后，检查该客户端消费及队列推进，而不是重新配置 Sensor。

A 非阻塞 UDP 限制了发送调用等待，不能排除本地其他队列积压。B 有界队列限制内存，但仍可能保留一段旧媒体，并在满时通过丢弃造成恢复波动。

如果增长位置已确定，下一步才讨论降低持续负载、预留峰值余量或限制最长等待。丢弃旧数据还要选择完整 NAL、图像或可恢复位置；否则延迟降低可能伴随更长的花屏恢复。验证应同时观察数据年龄和解码连续性。

## 13.8 现象七：收到退出请求后卡住，或退出后再次启动异常

### 13.8.1 先区分未响应停止和未完成回收

A 的信号处理只在发送阶段注册 `SIGINT`，退出循环后没有完整的媒体清理与 ISP join；B 有显式清理链路，但取流 worker 的创建状态与运行开关复用，可能跳过已经结束线程的 join。

出现退出异常时，先记录最后执行到哪一步：停止请求是否已提出，worker 是否真正返回，是否还有借出的 stream，ISP exit 是否完成，join 等待的是哪一个线程。“退出标志已经置位”只完成了通知，不能替代后面的状态变化。

### 13.8.2 把每次等待与它的解除条件对应起来

B 的 VENC `select()` 最多等 2 秒后重新检查循环，但后续 SDK 调用及 ISP join 不由这个超时约束。若 join 等待的线程仍停在阻塞调用中，只改一个循环标志可能不能立即使它返回。

检查应顺着第 10 章的依赖顺序：先停止会使用资源的 worker，保证借出的码流归还，再解绑和停止模块，最后释放公共媒体内存。公共 ISP 路径是先 ISP exit，再 join 运行线程，不能把单独 join 当成停止 ISP 的命令。

若进程已经消失而再次启动失败，进程退出只是一个证据，应再检查失败发生在应用文件、已占用媒体资源、驱动状态还是另一实例冲突。不能据此直接下结论必须重启或重刷固件。

下一步是保留原始错误并核对资源所有者，优先建立可重复的启动—停止状态记录；本次文档不执行板端资源修改。

## 13.9 把定位结论写成可以被下一步验证的句子

建议每次只记录五项：**现象、最后正常层、首个缺失证据层、当前解释、下一项能够区分原因的检查**。

例如，“RTSP 有连接无画面”可以逐步变成：“TCP 已建立，但没有看到 DESCRIBE 响应；当前 chn0 无新 pack，应用网络事件只由视频入口驱动；下一步确认 worker 与 `rtsp_do_event()` 调用是否仍推进。”这是一条有源码因果依据的排查假设，尚不是已确认的现场根因。

与之相比，“网络不好，换个播放器”没有说明断点，也无法解释下一项检查将排除什么。

完成一次验证后，还要说明边界：模块计数推进证明了该层有活动；GetStream 成功证明获得了一份编码数据；发送成功证明本地提交；接收重组与解码成功才把证据延伸到对端。每一步都保留原始记录，避免把推测写进后续的“已验证结论”。

## 13.10 自查问题

1. A 已打印 Ready，但 `cur_packs` 长期为零。应怎样安排最初几项检查，为什么还不能只查网络？
2. UDP 报文持续到达却不能解码，怎样比较两端的数据才有意义？
3. B 的 TCP 连接已建立，chn1 仍在输出，但 DESCRIBE 没有响应。哪条源码关系能够解释这一组合？
4. 发现 TCP 发送未维护短写偏移，能否马上写成“现场花屏由此导致”？还需要什么证据？

## 13.11 参考答案

1. 先区分查询失败与查询成功但持续为空，再核对启动结果、VI 输入、VPSS 目标通道及编码接收状态。Ready 没有汇总初始化结果，编码尚无有效输出时修改播放器不能补齐上游前提。
2. 先确认协议和编码映射，再按逻辑 NAL 内容比较发送端码流与接收重组，明确各自外层头和起始码的处理。结合序号、时间戳、FU 首尾及参数集，分辨内容缺失、封装差异和解码条件。
3. 应用只把 chn0 的可发布 pack 交给 `rtsp_sever_tx_video()`，网络事件在其末尾推进。chn1 只取流归还，所以它有输出不保证应用会 accept 或处理请求。
4. 不能。源码证明续写状态机制缺失；还需实际发送返回值、连接背压及字节流边界证据，确认该条件在现场发生并与解码异常关联。否则只能记录潜在影响与下一项验证。

下一章把同样的边界思路扩展到 OSD、AI、录像、其他协议和无线部署：先确定接入位置，再说明资源和数据关系发生了什么变化。
