# 15 项目讲解提纲

[返回学习入口](README.md) · [上一章：扩展示例与无线部署](14_扩展示例与无线部署.md) · [下一章：关键源码与资料阅读索引](16_关键源码与资料阅读索引.md)

本章把前面的机制整理成一段可以独立讲述的项目说明。讲解的重点是交接关系：前一步产生了什么，下一步为什么需要它，哪里持有资源，失败后怎样判断。函数名只在能帮助听者定位时出现。

下面的时间分配是练习建议，不是运行性能数据。第一次可以按约 12–15 分钟讲完；时间较短时保留整体边界、一幅图像、低延迟取舍和证据边界四部分。

## 15.1 开场：用一分钟说明项目与两条主线

可以这样开始：

> 这个项目利用 Hi3516CV610 的相机接入、图像处理和硬件编码能力，把 Sensor 图像变成网络码流。应用负责配置和连接媒体模块，在编码出口取数据并封装协议。当前有两条主要源码路径：一条是 SC500AI 的 H.265/RTP 固定地址发送，另一条是双通道 H.264 编码加 RTSP 会话分发。

紧接着说明配置边界：A 的 1080p/100 fps 是源码请求的模式；B 的 Sensor 由构建选择，默认 SC4336P 4M/30 fps，两个编码输出分别为 2560×1440 和 1024×768，而且只发布通道 0。这样听者不会把 A 的 Sensor 和 B 的协议混成同一个应用。

对应阅读：[01 总览](01_项目总览与三条流程.md)、[README 的对照表](README.md)。需要展示源码时只打开两个 `main()`，不先从几百个目录和结构体展开。

## 15.2 第二段：两分钟讲清“程序能运行”需要哪些配套

先解释产物关系：板级支持包负责启动环境、内核和硬件适配；SDK 提供用户态媒体接口和库；工具链把应用和 Sensor 适配编译链接成目标程序；根文件系统把程序、库、调校文件和启动配置组织到板端。

这几类产物可以分别构建，最终必须配套。不要把图画成“应用源码依次生成驱动、内核、根文件系统”；应用只是交付物中的一部分。

再对应当前工程：它有 SDK/工具链归档、示例和镜像，但厂商示例需要外层构建配置，自定义应用还有 Sensor 相对路径与 PQ API 依赖需要整理。已有 ELF 或镜像不能替代可重复构建记录。

自然过渡到板端：

> 当应用真正运行时，它已经假定板上有匹配的媒体驱动、正确的 Sensor 引脚和时钟，以及可用媒体内存。接下来 main 做的是把这些资源配置成一条流水线。

对应阅读：[02 构建基础](02_BSP与SDK构建基础.md)、[03 Sensor 适配](03_板级资源与Sensor适配.md)、[11 验证](11_部署与分层验证.md)。

## 15.3 第三段：四分钟沿一幅图像讲完整过程

### 先从 Sensor 的两条通道讲起

控制通道把模式、曝光、增益和帧时序配置送给 Sensor；图像通道把连续像素数据经 MIPI 送入 SoC。控制写得成功和图像输出正确是两项证据，不能互相替代。

应用注册 Sensor 回调对象，把 SC500AI 的具体寄存器和时序适配接到 ISP/AE/AWB 框架。框架在初始化、获取默认参数或更新曝光等阶段使用回调；应用没有因此自行实现完整的自动曝光或白平衡算法。

### 然后解释图像在媒体系统中的交接

SYS 建立系统级媒体能力，VB 提供符合媒体要求的缓冲组织。VI/ISP 接入并处理 Sensor 图像，VPSS 提供处理后的通道输出，VENC 消费图像并压缩。

这里需要主动说明三个细节：

- 格式不仅是“宽×高”，还包括颜色平面、位宽、stride、压缩和对齐；stride 是每行实际跨过的存储字节数。
- online/offline 描述特定模块边界怎样交接，不等于整个程序是否联网，也不能直接推断所有数据是否经过 DDR。
- bind 建立 SDK 管理的模块数据关系，应用因此不必每帧把原始图像从 VI 复制到 VPSS 再复制到 VENC；内部搬运方式仍受 SDK 和模式约束。

### 再从编码结果进入应用线程

原始图像数据量大，VENC 用 H.264/H.265 利用空间和时间相关性压缩。码率控制约束输出预算，GOP/关键帧决定参考结构与部分恢复机会；切片输出使应用可能更早拿到一幅图像的局部编码结果。

应用等待或查询 VENC 状态，取得包数并准备描述符，然后 GetStream。描述符告诉应用地址、偏移、有效长度和 PTS；真正的字节仍由 SDK 管理。应用完成读取、复制或同步封装后，必须 ReleaseStream。

这里应明确说出四个边界：**编码图像、NAL、SDK pack、RTP 包。** 一幅图像可以有多个 NAL，一个大 NAL 可以分成多个 RTP 包；SDK pack 与 NAL 的关系需要具体接口契约，不能凭名字假定一一对应。

### 最后分别说 A 与 B 怎样发出去

A 去掉 Annex B 起始码，小 NAL 直接放入 RTP，大 NAL 在当前类型白名单内按 FU 分片。序号区分传输包，时间戳表达媒体时间，Marker表达访问单元结束，PT=96 的编码映射需要双方约定。应用经 `sendto()` 把数据报交给内核，再归还码流。

B 把通道 0 的 H.264 数据送入 RTSP 库，由库收集参数集、RTP 封装并复制进共享队列。客户端通过 DESCRIBE 获取描述、SETUP 选择 UDP/TCP、PLAY 开始消费；各客户端保存独立游标。随后应用可以归还 SDK stream，因为排队媒体包已由库自己的缓冲持有。

接收端还需要收包、重组、解码和显示。讲到这里才完成“一幅图像如何到达画面”的全链路，而不是停在发送系统调用。

对应阅读：[05 缓冲](05_SYS_VB与缓冲区管理.md)、[06 图像通路](06_VI_ISP_VPSS图像通路.md)、[07 编码](07_VENC编码与码流生命周期.md)、[08 RTP](08_自定义RTP与UDP发送.md)、[09 RTSP](09_RTSP会话与媒体分发.md)。

## 15.4 第四段：两分钟解释低延迟设计的取舍

先把总等待分为曝光与读出、图像处理、编码、取流、本地排队、网络、接收缓存与显示。高帧率只是其中一项条件；即使每秒产生很多图像，队列一直保留旧图像，看到的画面仍然可能很晚。

A 使用提前中断、低延迟行数、切片输出、限制重编码、帧内刷新和非阻塞发送，分别尝试减少不同阶段的等待或突发。它们各有边界：提前中断不等同于低延迟机制的硬件读写保证；切片增加包处理次数；限制重编码会影响质量/码率取舍；非阻塞避免等待 socket 空间，却可能让本次发送失败。

缓冲大小尤其适合用来说明取舍：增加缓冲能吸收短时突发，也能让积压数据变旧。应该确定允许保留多长时间的媒体，再观察实际队列与丢弃，而不是把“越大越稳定”作为默认规则。

B 的 200 行 VPSS 低延迟配置作用在通道 1，实际发布的是通道 0。这个例子说明性能结论必须沿活动数据路径核对，不能见到一个低延迟字段就归因到最终画面。

对应阅读：[12 低延迟与性能分析](12_低延迟与性能分析.md)。可接着追问：如果只能增加一个计数，应优先确认哪个交接？答案取决于当前不知道输入是否产帧、编码是否输出，还是网络是否成功。

## 15.5 第五段：两分钟解释并发、背压与退出

CPU 上有不同执行者。A 的主线程取流和发送，另有 ISP 线程；B 的主线程等退出，worker 取流并处理 RTSP，公共辅助层也启动 ISP 线程。

当前 B 没有独立网络线程：`rtsp_do_event()` 在视频发布函数尾部被调用。因此主码流停产时，不只是没有画面，RTSP 请求也可能不被及时处理。要改变这个关系，需要同时设计事件调度或线程安全的数据交接，不能只把函数移到新线程。

再解释背压：消费者慢时，等待和丢弃会出现在硬件缓冲、取流、共享 RTP 队列、socket 或接收端。RTSP 有界 ring 限制内存，但淘汰旧包不保证落在可解码边界；TCP 按顺序交付字节，也不等于当前应用正确处理了短写。

最后讲退出：请求停止只是发出意图，join 才是在等待成功创建的线程结束；工作结果是另一项状态。消费者仍可能读取 SDK 地址或会话对象时，不能先释放它们。A 当前清理不完整，B 还有运行标志与 join 状态混用，AI 分支则还要等待原始帧处理线程。

对应阅读：[10 并发与资源退出](10_并发与资源退出.md)、[13 故障排查](13_分层故障排查.md)。

## 15.6 用一个故障例子展示推理，而不是罗列命令

可以选择“RTSP 端口能连接，但没有画面”作为收束案例：

1. 先判断是只有 TCP 建连，还是 DESCRIBE/SETUP/PLAY 都得到应用响应。这决定控制事件循环有没有推进。
2. 如果控制响应也停滞，检查通道 0 是否产生并进入发布函数；当前事件循环依赖这里，通道 1 有数据也不足以替代。
3. 如果控制正常，再检查协商的传输方式、客户端游标、RTP 到达、参数集和可解码图像；TCP 场景还要看短写与边界是否完整。
4. 如果 VENC 根本无输出，向上回到 VPSS、VI/ISP 与 Sensor，而不是继续调整播放器缓存。

每一步都在缩小未知范围。结论中说明已经观察到哪一项证据、哪一项仍待确认，比直接猜“网络问题”更有说服力。

## 15.7 最后说明实现状态与验证状态

可以这样结束实际项目介绍：

> 目前能从源码解释两条媒体链、协议封装与资源生命周期，也能指出若干需要完善的边界检查和线程/发送状态。100 fps、码率、尺寸和低延迟参数是配置目标；源码、现有二进制和固件还需要补全版本关联。只有交叉构建、板端运行、接收解码与统一定义的时延测量，才能逐层补齐使用效果证据。

如果介绍扩展，补一句它接在哪个位置即可：OSD 改变媒体通道上的叠加内容，AI 介入原始图像处理，MP4 增加编码结果的文件消费者，无线与遥测则来自外部部署进程。没有证据时不将它们表述为主程序已经集成。

## 15.8 常见追问与回答要点

| 追问 | 回答的核心 | 继续追到哪里 |
| --- | --- | --- |
| 注册 Sensor 回调为何不等于 ISP 算法写完？ | 注册的是硬件差异与参数交接接口，算法和运行调度由框架/库完成 | 第 03 章的回调与寄存器更新链 |
| 绑定后还有复制吗？ | 绑定减少应用逐帧转交，协议封装和扩展仍有复制；内部硬件移动不能凭名称断言 | 第 05、06、08 章 |
| 100 fps 为什么不保证低延迟？ | 帧间隔、曝光、处理和各级排队共同决定时延 | 第 12 章 |
| PTS 能直接用来算发送端到接收端延迟吗？ | 必须先确认单位、起点与时钟同步；RTP 时间戳是媒体时钟，不是双方共享墙钟 | 第 07、08、12 章 |
| 为什么不一直重试发送直到成功？ | 会阻塞当前取流执行者并积压旧媒体；需要有界发送状态与丢弃/恢复策略 | 第 09、10 章 |

## 15.9 自查练习

**练习 1：不看代码，画出控制流程和媒体数据流两张图。**

回答要点：控制图有配置、创建、绑定、线程与退出；数据图有 Sensor、VI/ISP、VPSS、VENC、编码缓冲、封装与接收端。不能把应用调用顺序复制成每帧的 CPU 处理顺序。

**练习 2：选 A 的一个 pack，讲清从有效地址到归还的全过程。**

回答要点：数量与描述符准备、GetStream、offset/len、Annex B/NAL 假设、FU/RTP、发送结果、ReleaseStream；点出异步保存裸地址的风险。

**练习 3：有人说“连接成功、打印 Frames=100，所以已经实现 100 fps 低延迟图传”，怎样拆解？**

回答要点：连接层、图像计数、发送成功、解码显示和时延定义分开核对；当前 Frames 是 NAL 调用计数，配置帧率和统计标签都不能替代实际图像测量。

需要查回源码时，使用 [16 关键源码与资料阅读索引](16_关键源码与资料阅读索引.md)，带着具体问题进入对应入口。
