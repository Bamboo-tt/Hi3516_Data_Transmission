# 15 项目讲解提纲

[返回学习入口](README.md) · [上一章：扩展示例与无线部署](14_扩展示例与无线部署.md) · [下一章：关键源码与资料阅读索引](16_关键源码与资料阅读索引.md)

前面各章已经解释了组件，现在用一次完整讲述检验能否把它们连接起来。讲解始终跟随同一幅图像：它从哪里来，为什么需要变换，以什么形态交给谁，何时结束当前使用权。函数名称用于定位关键交接，不必把整个调用表念一遍。

下面可用于约 12–15 分钟的讲解练习，这是表达时间建议。较短场合保留系统边界、一帧图像、延迟取舍和验证状态；追问时再展开对应章节的机制。

## 15.1 先把任务和边界讲清楚

可以从一个具体场景开场：

> 相机前的物体移动后，远端需要尽快看到变化。Hi3516CV610 负责接入 Sensor 图像、处理并硬件编码，应用在编码出口组织网络发送，接收端重组、解码和显示。系统能否正常工作，取决于这几次交接是否同时成立。

随后交代本项目的两个真实入口。A 是 SC500AI 的 H.265/RTP 固定地址发送，B 是构建选择 Sensor 的双通道 H.264/RTSP 示例。A 的 1080p/100 fps 是源码配置；B 缺省 Sensor 为 SC4336P，编码输出为 2560×1440 与 1024×768，只有通道 0 发布到 `/test.264`。配置与板端结果分开交代，听者才不会把两个入口拼成同一个程序。

这段对应 [01 总览](01_项目总览与三条流程.md)。展示代码只需先打开两个 `main`，让后续解释有明确对象。

## 15.2 解释它为什么能够运行在板上

应用先要成为目标板能够装载的程序。交叉工具链把源码和 Sensor 适配编译为目标 ABI，SDK 头库提供媒体接口；板端内核、驱动、运行库、媒体内存与 PQ 文件共同提供运行条件。启动器、内核和应用可以分别构建，最终必须配套。

再把这个原理落到当前项目：厂商示例仍依赖外层 SDK Make 配置，A 的 Sensor 相对路径和 PQ API 需要在实际构建环境中整理。Git 提交能定位源文件状态，已有 ELF、镜像仍要通过构建记录和摘要与它关联。这样讲清了“有什么材料”和“能重复得到什么产物”的区别。

自然过渡到初始化：

> 板上驱动和 Sensor 条件齐备后，应用建立 SYS/VB、接入与 ISP、VPSS、VENC 和通道绑定。完成绑定以后，持续处理由硬件和驱动推进，CPU 线程负责控制与编码出口。

相关原理在 [02 构建](02_BSP与SDK构建基础.md)、[03 Sensor](03_板级资源与Sensor适配.md)、[04 初始化](04_媒体系统初始化.md)，产物证据在 [11 验证](11_部署与分层验证.md)。

## 15.3 沿一幅图像讲到接收端

### 15.3.1 Sensor 如何同时提供像素和控制

先讲两条通道：控制通道把模式、曝光、增益和帧时序送给 Sensor，MIPI 图像通道把连续像素送给 SoC。应用注册 `g_sns_sc500ai_obj`，把具体寄存器和时序差异接到 ISP/AE/AWB 框架；框架在初始化或曝光更新等阶段使用回调。

注册回调并不表示应用实现了完整 ISP 或 AE 算法。适配代码负责把框架要求转换成硬件可接受的参数，闭源库负责相应算法和调度。控制访问成功之后，还要确认像素接口的位宽、lane、时钟与接收属性对应，图像才能继续向下游流动。

### 15.3.2 一幅图像怎样存放并进入编码器

SYS/VB 提供系统和媒体缓冲条件，VI/ISP 接入 RAW 并进行图像处理，VPSS 形成通道输出，VENC 消费这些图像。描述内存时至少交代宽高、颜色布局、stride、压缩和对齐；stride 是从一行起点跨到下一行起点的存储距离。

用一个数值使需求具体化：1920×1080 的紧凑 8 位 YUV420 图像为 3,110,400 字节，100 fps 时仅一遍完整流过就是约 311 MB/s。这是尺寸算例，足以解释为什么需要硬件处理和编码，但实际 DDR 流量还包含布局、读写次数与压缩影响。

online/offline 描述特定媒体边界的交接方式；bind 建立源通道到目的通道的 SDK 数据关系。它减少应用逐帧手工转交，实际协议出口和 AI 分支仍有复制。说到这里，听者应能分清控制调用、媒体数据流与用户态数据访问。

### 15.3.3 压缩结果何时归应用使用

VENC 利用空间和时间相关性压缩图像。码率控制分配输出预算，GOP 与参考关系影响压缩和恢复，切片输出改变最早可取到编码数据的时机。应用查询或等待编码出口，准备描述符，通过 GetStream 获得地址、偏移、长度和 PTS，再读取有效区间。

这时明确四个不同边界：图像、NAL、SDK pack、RTP 包。一幅图像可以对应多个 NAL，大 NAL 可以拆成多个网络包；SDK pack 与 NAL 的映射则要根据接口契约确定。结构体描述的是 SDK 中的字节，应用的读取窗口在 GetStream 与 ReleaseStream 之间。

### 15.3.4 两种出口怎样交接同类编码结果

A 去掉 Annex B 起始码，小 NAL 直接承载，大 NAL 在当前类型白名单内按 HEVC FU 分片。序号随 RTP 包递增，同一采样时刻使用相同媒体时间戳，Marker 表示相应访问单元的末尾。PT=96 的编码含义需要双方约定，`sendto` 的结果需要另行检查，接收端还要重组与解码。

B 把通道 0 的 H.264 数据送入 RTSP 库，库收集参数集、分成 RTP 包并复制进共享队列。客户端通过 DESCRIBE 取得 SDP、SETUP 选择 UDP/TCP、PLAY 开始消费，各自保存发送游标。应用可在完成库内复制后归还 SDK stream，队列副本由协议库继续持有。

至此，一幅图像已经从 Sensor 连接到接收端；[05 缓冲](05_SYS_VB与缓冲区管理.md) 至 [09 RTSP](09_RTSP会话与媒体分发.md) 为每次交接提供详细依据。

## 15.4 用同一条数据流解释性能与可靠性

高帧率缩短采样间隔，显示延迟却还包含曝光/读出、处理、编码、取流、排队、网络和显示。只要某一级持续保留旧数据，高 FPS 与明显延迟就可以同时存在。

A 的提前中断、低延迟行数、切片、限制重编码、帧内刷新与非阻塞发送，分别作用于不同等待或突发来源。解释一个参数时说清它降低哪一项等待，又把什么代价交给下游：更多切片增加包处理频率，限制重编码影响质量与码率跟踪，非阻塞发送把“等待可用空间”变成“可能立即失败”。

缓冲可以吸收短时突发，但消费者长期偏慢时只会继续积压。若生产已经停止，排空时间可用“积压字节数÷发送字节率”估算；若新数据仍以输入速率进入，则要除以“发送速率−输入速率”，且发送必须持续快于输入。新数据也在消耗发送能力，只有剩余部分能用于减少积压。RTSP ring 限定内存，却按包淘汰；丢弃后是否可解码，还取决于 NAL 与参考链的恢复。

B 的 VPSS 200 行低延迟设置在通道 1，发布通道在 0。这个例子说明，要从具体消费者向上追溯活动路径，才能把参数与最终画面连接。[12 性能](12_低延迟与性能分析.md) 详细推导这些取舍。

随后转向退出：此时主线程、ISP 线程、取流 worker 或 AI 线程可能各自持有资源。发出停止请求只是改变意图，归还在途 stream、线程返回、join 完成才分别结束不同责任。回收共享对象以前，必须让使用它们的执行者完成访问。

当前 A 清理不完整，B 将运行标志与需要 join 的条件混用，AI 退出还缺少等待 dump 线程。与其笼统说“使用多线程提升效率”，更应指出它们如何交接数据、在哪里同步、失败怎样被主线程知道。详见 [10 退出](10_并发与资源退出.md)。

## 15.5 用一个故障把理解转成判断

选“RTSP 端口能连接，却没有画面”作为案例。先问最后一项观察是什么：TCP 握手成功，还是 DESCRIBE、SETUP、PLAY 都收到应用响应？前者只证明连接层；后者才证明控制处理至少推进到了相应阶段。

当前 B 的 `rtsp_do_event()` 在视频发布尾部调用。如果控制响应也停滞，应查看 VENC 0 是否产出并进入发布路径；通道 1 有包不足以替代。如果控制正常，则沿协商的传输方式检查 RTP 到达、客户端进度、参数集与可解码图像；TCP 还应检查 interleaved 头和负载是否完整发送。

若 VENC 本身没有输出，就回到 VPSS、VI/ISP 与 Sensor 的相邻交接。只有找到“上一环节已交付、下一环节未接受”的位置，才有依据提出修改。这个例子连接了会话状态、事件驱动和媒体路径，也示范了 [13 排障](13_分层故障排查.md) 的使用方式。

## 15.6 扩展和验证怎样收束

介绍扩展时先说接入对象：OSD 改变媒体通道上的叠加内容，AI 借用原始帧并手动送回编码，MP4 消费压缩样本并形成文件，WFB 消费本机 UDP 后承担无线传输，MAVLink 使用外部遥测进程。然后说明新增缓冲、线程、时间或格式契约，避免把示例目录名称当成已集成能力。

最后给出准确状态：当前源码能解释两条主链和可见的边界风险；配置值、当前 ELF、固件和实际画面之间还需要构建、板端和接收证据。发送统计也要明确计数对象，A 的 `Frames` 按 NAL 调用增加，不能直接作为图像 FPS。[14 扩展](14_扩展示例与无线部署.md) 与 [11 验证](11_部署与分层验证.md) 给出这些边界。

## 15.8 参考答案

1. 构建图记录配套产物；控制图记录创建、绑定和退出；逐帧图记录格式变化和数据使用。绑定路径中的原始帧由 SDK/驱动管理流转，应用并未逐帧调用 Get/Release；AI 等用户取帧路径才要显式成对借还。stream 由 VENC 借出、应用归还，RTSP 副本由 ring 生命周期管理。不能把应用调用顺序原样画成逐帧 CPU 运算。
2. 查询数量并准备足够描述符，GetStream，检查 offset/len 与实际 NAL 组织，去前缀、分片并写 RTP 字段，检查发送结果，ReleaseStream；接收端按协议重组。异步消费者若保留 SDK 裸地址，可能越过归还边界，必须复制或合法延长持有。
3. 确认连接属于哪一层，再分别验证输入图像数、编码图像数、NAL/RTP 包数、成功字节、解码与显示。检查 A 计数位置；帧率测量按图像定义，延迟测量说明起止点与时钟关系。PTS 和 RTP 时间戳不能未经时钟同步就当成跨设备墙钟。
4. 更大缓冲吸收突发，也可能延长旧媒体寿命；无限重试阻塞取流，并因当前调用耦合延迟控制事件和退出。需要有界排队、发送进度、丢弃/恢复策略和可终止等待；具体预算取决于业务允许的延迟与丢失。
5. 回调把框架与硬件差异连接，算法主体可能在库中；bind 把通道关联，用户态处理和组包仍有复制；RTP 组织媒体包，资料中的纠错由 WFB 外部承载实现。每种说法都应定位到实际边界和执行者。

能够连续解释这些题目后，再用 [16 来源索引](16_关键源码与资料阅读索引.md) 检查函数、配置和资料是否支撑每一项判断。
