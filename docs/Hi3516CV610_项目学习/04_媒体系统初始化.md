# 04 媒体系统初始化

[返回学习入口](README.md) · [上一章：板级资源与 Sensor 适配](03_板级资源与Sensor适配.md) · [下一章：SYS/VB 与缓冲区管理](05_SYS_VB与缓冲区管理.md)

前一章解决 Sensor 能按约定输出图像的问题。本章接着看：Linux 进程如何申请媒体资源、配置各模块并让它们组成可持续工作的链路。先把启动顺序理解清楚，下一章再深入这些模块使用的缓冲。

初始化不是单纯填写几个结构体。它包含两类不同的操作：**准备配置值**只改变进程内存；**调用 SDK/驱动接口**才请求系统建立资源或改变硬件状态。后者还可能失败，且失败后需要释放之前已经建立的资源。

## 4.1 开始执行 main 之前，还缺哪些条件

【源码实现】A 会打开 `/dev/ot_mipi_rx` 并调用媒体 MPI；两条主线都依赖配套的媒体驱动、可用媒体内存和正确的 Sensor 连接。应用源码并不负责构建内核或装载完整 BSP。

【资料记录】[使用文档（3）](../../hi3516firm/hi3516firm/海思hi3516-hi3519使用文档(3).docx) 的 `S99autostart` 示例先装载媒体驱动，再选择启动视频应用。该脚本目前以 DOCX 片段存在；其中 MMZ 地址、Sensor 参数和运行目录是历史部署示例，不是本次确认的板端配置。

进入 main 还不意味着所有依赖可用。至少需要把下列条件作为启动前提分别核对：

| 条件 | 失败后通常卡在哪个交接 | 当前证据边界 |
| --- | --- | --- |
| 二进制、动态库与内核接口配套 | 装载进程、调用库或驱动接口 | 当前有文件，缺完整构建/部署对应表 |
| Sensor 模式、MIPI lane、时钟与引脚匹配 | 接入链路没有有效帧或出现接收错误 | 源码目标已知，板级实际设置待确认 |
| SYS/VB 可取得所需媒体内存 | 初始化缓冲、创建或运行通道失败 | 配置项可读，实际分配与占用待确认 |
| 运行目录和 PQ/模型路径正确 | 配置文件打开失败或参数未加载 | A 使用相对当前工作目录的 PQ 文件路径 |
| 当前没有冲突的媒体资源使用者 | 相同 dev/pipe/group/channel 申请或绑定失败 | 示例大量使用编号 0，不能默认多个程序可并行运行 |

## 4.2 A：从一组配置到一条 H.265 输出链

主线 A 的所有编排在 [new_main2.c](../../hi3516firm/new_main2.c)。从 `main()` 看起，可以把启动过程理解为三个阶段。

### 准备约定：此时还没有完成硬件启动

`main()` 创建 `sys_cfg`、`vi_cfg`、`vpss_cfg`、`venc_vpss_chn`，调用 `set_vi_*`、`set_dev_info()`、`set_vpss_*` 等函数填值。Sensor 信息规定总线和模式；VI 配置规定设备、pipe 与输出通道；VPSS 配置规定输出尺寸和通道；最后编码配置再消费这些图像输出。

此时结构体是后续接口的输入，而不是系统状态证明。例如，`set_vi_sys_cfg()` 写了 online/offline 模式，但 `sys_init()` 内部又直接设置各 pipe 的模式，不能仅依据传入参数对象判断哪个值最终被使用。

### 建立生产链：先系统资源，再输入与处理

`sys_init()` 先调用 SYS/VB exit，再设置 VB 配置并初始化 VB、SYS，随后选择 VI/VPSS 模式。它使用 Bayer 图像属性计算 pool 0 的块大小，配置 3 个块。`max_pool_cnt=2` 是配置容量字段，不代表这里已经有两个有效池，也不证明初始化实际成功。内存含义见第 05 章。

`vi_init()` 打开 MIPI 接收设备，发 ioctl 配置时钟、复位和接收属性，然后建立 VI dev、pipe 及 channel。ioctl 是用户态向驱动提交控制请求的接口；它不是应用直接在循环里处理像素。这里还设置提前中断和低延迟参数，其效果依赖匹配的媒体模式。

`true_isp_init()` 取得 `g_sns_sc500ai_obj`，注册 Sensor 与 AE/AWB 接口，设置总线，初始化 ISP 内存和公共属性，再启动 ISP 运行线程。AE 是自动曝光，AWB 是自动白平衡；应用注册的是适配回调及算法库，算法主体不是在 main 中手工实现。

### 导入调校并接上编码输出

`isp_calibration_load_bin()` 读取 `./sc500ai_1080P_100.bin`，通过 `OT_PQ_BIN_ImportBinData()` 导入 ISP 与 3DNR 参数。相对路径基于进程当前工作目录，和可执行文件放在哪里并非必然相同。

之后 `vpss_init()` 创建并启用 VPSS 通道，`vi_bind_vpss()` 连接输入到处理；`encoder_init()` 创建 H.265 编码器并开始接收；`vpss_bind_venc()` 再把 VPSS 通道 0 与 VENC 通道 0 连接。最后 `rtp_send()` 才进入编码出口的持续取流与发送循环。

~~~mermaid
sequenceDiagram
    participant M as A 主线程
    participant D as SDK与媒体驱动
    participant I as ISP线程
    M->>M: set_* 准备配置
    M->>D: sys_init：VB / SYS / 工作模式
    M->>D: vi_init：MIPI / VI dev / pipe / channel
    M->>D: true_isp_init：注册与初始化 ISP
    M->>I: pthread_create
    I->>D: ss_mpi_isp_run
    M->>D: 导入 PQ BIN
    M->>D: 创建 VPSS，绑定 VI 到 VPSS
    M->>D: 创建并启动 VENC，绑定 VPSS 到 VENC
    M->>M: rtp_send 取流与发送循环
~~~

图中的先后关系表达源码调用顺序，不表示所有请求都已经成功。ISP 线程创建之后与主线程并行运行；随后导入 PQ，可能改变前面代码设定的部分参数。没有 SDK 对覆盖范围的说明或导入后回读，就不能确认最终生效值。

## 4.3 B：公共辅助层隐藏了细节，但没有省略依赖

主线 B 从 [sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 的 `main()` 进入。它先注册 SIGINT/SIGTERM 的处理函数，创建端口 554 的 RTSP server 和 `/test.264` 会话，然后调用 `sample_venc_rtsp()`。

这里先创建网络对象，是为了后续码流可以找到输出会话；它并不代表有一个独立线程已经持续处理网络请求。网络事件实际由谁推进，需继续追到第 09 章。

`sample_venc_rtsp()` 先把尺寸枚举转换为宽高，再执行 `start_sys_vi_vpss()`。该函数调用公共辅助代码，依次准备 Sensor 默认配置、VPSS 配置和 wrap 配置，再初始化 SYS/VB、启动 VI、启动 VPSS、绑定 VI 到 VPSS。

`sample_comm_vi_start_vi()` 位于 [sample_comm_vi.c](../../sample_source/common/sample_comm_vi.c)。继续进入这个函数才能看到 MIPI、VI dev、pipe 与 ISP 启动。ISP 又会通过 [sample_comm_isp.c](../../sample_source/common/sample_comm_isp.c) 的运行封装启动线程。B 的进程因此不仅有主线程和码流 worker，也有 ISP 运行线程。

### 两个编码通道如何加入

`venc_start_encode()` 填充两份 H.264 编码参数，先调用小缓冲模式设置，再循环处理通道 0、1：启动 VENC，然后把对应 VPSS 输出通道与 VENC 绑定。两路成功后再创建取流线程，避免 worker 抢先访问尚未就绪的编码通道。

取流线程等候两个 VENC fd，但对外会话只发布通道 0。主线程则进入每秒检查退出标志的循环。图像处理、编码和取流并非由这个每秒循环驱动。

### 初始化回退为什么要记住完成到了哪里

【源码实现】B 的 `start_sys_vi_vpss()` 使用 `exit_vpss`、`exit_vi`、`exit_sys` 等标签回收先前成功的阶段。例如，VPSS 启动失败，后续绑定不会执行，程序转去停 VI，再退出 SYS；若绑定失败，则还需先停已启动的 VPSS。

编码启动同样记录通道循环位置：当前通道绑定失败时先停止该通道，之后回收前面完成的通道。这里的原则是“只释放已经拥有的资源，并按依赖顺序拆除”。标签本身不是问题，关键是所有可能失败的路径是否汇入正确阶段。

【待确认】B 比 A 有更多返回值检查，但还存在小缓冲模式调用未检查、worker 异常未传回 main、join 状态混用等缺口。因此不能把它概括为所有失败都已经得到完整处理。

## 4.4 两条启动链的关键差异

| 交接点 | A | B | 为什么会影响后续理解 |
| --- | --- | --- | --- |
| Sensor 来源 | C 源码直接选择 SC500AI 100 fps 模式 | 来自构建宏与公共默认配置 | B 不能沿用 A 的 lane、曝光与帧率结论 |
| 媒体模式 | VI offline / VPSS online，wrap 关闭 | VI / VPSS online，默认 wrap 开启 | 需要的缓冲、模块连接约束与延迟条件不同 |
| SYS/VB 封装 | 较多直接 MPI 调用，返回值多未检查 | 公共辅助函数检查并回退部分错误 | 同样打印启动信息，证据强度可能不同 |
| ISP 和 PQ | 手动 ISP 启动，随后显式导入 PQ BIN | 公共 VI 启动内部启动 ISP；入口未调用 A 的 PQ 导入函数 | 不应把 A 的调校文件写成 B 的默认加载行为 |
| 输出对象创建 | 媒体建立后才在 `rtp_send()` 创建 UDP socket | main 先创建 RTSP server/session | 网络对象存在与媒体就绪之间没有自动等价关系 |
| 持续运行者 | 主线程取流发送，另有 ISP 线程 | worker 取流并驱动网络，main 等退出，另有 ISP 线程 | 诊断阻塞和退出时必须先找执行者 |
| 正常退出 | 退出循环后 `exit(0)`，未形成完整媒体清理 | 停取流/编码，再拆采集链并删除 RTSP 对象 | 初始化顺序只能帮助设计退出，不能证明退出已经实现 |

## 4.5 “已设置”“已启动”“有数据”需要分别证明

应用发出了设置请求，首先要检查返回值；返回成功后，还要看是否可查询到期望属性；有正确属性之后，仍需观察帧/流计数持续增长。最后接收端的协议与解码证据才能证明传输目标成立。

A 的 `g_start_isp` 在 `pthread_create()` 后直接置 true，没有根据创建结果决定；`Ready for streaming` 在申请发送缓冲后打印，也没有覆盖前面每项失败。Sensor 适配同样存在状态赋值与底层结果未闭环的地方，详见第 03 章。学习代码时应把这些变量理解成“程序写下的状态”，再检查它是否被真实返回值支持。

这会影响故障定位顺序：如果不知道 VI 有没有产帧，就不应先围绕播放器缓存反复调整；如果 VENC 已持续出流但 RTSP 请求不响应，应转向事件驱动关系，而不是重新初始化 Sensor。

## 4.6 自查与回答要点

**问题 1：`set_vi_pipe_info()` 执行完，能否说 VI pipe 已经工作？**

回答要点：它只准备属性。还需要创建、设置、启动接口成功，以及运行状态和真实帧证据。结构体内的期望值与内核里的资源状态要分开。

**问题 2：为什么 B 的 main 没有直接调用 ISP Run，却仍然需要分析 ISP 线程？**

回答要点：main 调用的公共 VI 启动函数内部继续调用 ISP 辅助层。应沿调用关系穿透封装，不能只搜索主文件中的线程创建次数。

**问题 3：为什么导入 PQ 的位置会影响对曝光参数的判断？**

回答要点：A 先设置曝光限制，再导入包含 ISP 参数的 BIN。只有覆盖范围说明或最终回读能确定两者共同作用的结果；后续参数设置时间同样是配置的一部分。

**进一步追问：初始化失败后，能否统一调用所有 stop 函数？**

回答要点：必须知道哪些资源已创建，以及 SDK 是否允许对未创建对象执行 stop。B 用阶段回退表达这一原则；实际完善时还需记录线程创建成功和资源所有权。
