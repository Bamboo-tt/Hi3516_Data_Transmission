# 07 VENC 编码与码流生命周期

[学习入口](README.md) · 上一章：[VI、ISP、VPSS 图像通路](06_VI_ISP_VPSS图像通路.md) · 下一章：[自定义 RTP 与 UDP 发送](08_自定义RTP与UDP发送.md)

VPSS 已经能够提供指定尺寸的图像，接下来的约束是数据量：网络接收端需要连续看见画面，却不适合接收每一幅未经压缩的像素。VENC 负责把图像变成较小的码流；应用负责及时取走结果，并在用完之后归还编码缓冲。

本章沿一轮“图像进入编码器 → 产生码流 → 应用借用 → 协议消费 → 归还”展开。文中的数值是当前源码配置或明确标注的算例，没有新增板端帧率、画质或时延测量。两条应用仍分别称为 A（自定义 RTP）和 B（RTSP 主例）。

## 7.1 数据为什么变小，又为什么会产生解码依赖

假设一幅 1920×1080 图像采用紧密排列的 YUV 4:2:0 布局，单幅数据量为：

```text
1920 × 1080 × 1.5 = 3,110,400 字节
每秒 100 幅：3,110,400 × 100 = 311,040,000 字节/秒
```

这是单遍原始数据量的算例；真实内存布局还包含 stride、对齐等条件，整条媒体链可能多次读写，不能将它当作 DDR 实测带宽。它说明了压缩的必要性：A 的编码目标是约 4096 Kbit/s，传输的已不是原来那三百多 MB/s 的逐像素内容。

### 从预测误差到压缩字节

理解编码时，可先用一个常见场景：相机固定拍摄房间，相邻图像的大部分背景几乎不变。编码器可以利用已知的空间邻域或参考图像预测当前内容，只表达预测方式与剩余差异，而不逐幅重复发送全部背景。

作为通用原理，预测后的残差还会经过变换、量化和熵编码。变换改变残差的表达方式；量化减少需要精确保留的细节，形成有损压缩；熵编码再利用符号统计减少字节。解码器沿相应规则恢复图像。厂商硬件具体怎样搜索预测、分配预算和调度内部缓存，不在这份应用源码中。

这个过程也解释了画面为何会“花屏后持续一会儿”：某幅图像丢失，后面的图像可能仍引用它。包重新到达不等于参考链立即恢复。压缩效率、错误传播和刷新代价因此必须一起考虑。

### 用码率、GOP 与参数集约束输出

**CBR**（Constant Bit Rate，恒定码率控制）围绕目标码率进行调节，不是让每幅图像输出相同长度。场景变复杂时，编码器需要在质量、输出量和其他约束之间折中。**QP**（量化参数）控制量化强度，一般增大它会减少细节和字节；A 还限制 I 图像与其他图像的 QP 范围，使控制不能无限调整。

这里的 **I、P、B** 首先描述编码预测方式：I 类内容只利用当前图像内部的信息，P 类内容可以引用已解码的参考图像，B 类内容允许使用两组参考信息。P、B 图像中也可以包含帧内编码的块；这些名称不意味着把当前图像与上一幅简单相减，也不表示本项目启用了 B 图像。

**GOP**（Group of Pictures，图像组）描述一组图像的参考/刷新组织。本项目使用 NORMAL_P 模式，不能把它理解成“没有起始或刷新图像的纯 P 序列”。关键图像帮助建立解码入口；**IDR**（即时解码刷新）提供切断对先前图像依赖的刷新入口，**CRA**（干净随机接入）还涉及随机接入时对前导图像的处理，因此二者不能仅凭计数变量混称。前导图像在解码次序上位于 CRA 之后、显示次序上却位于 CRA 之前；从 CRA 随机接入时，其中依赖接入点之前图像的部分需要跳过。相关随机接入区别见 [RFC 7798 §1.1.2](https://www.rfc-editor.org/rfc/rfc7798#section-1.1.2)。

图像之前还要有解释码流所需的参数集：H.264 的 SPS/PPS、H.265 的 VPS/SPS/PPS。它们描述解码结构和配置，通常不等于一幅显示画面。**能够收到大量编码字节，与已经具备解码这些字节的条件，是两个阶段。**

## 7.2 把原理对应到 A、B 的编码配置

A 在 [new_main2.c](../../hi3516firm/new_main2.c) 的 `encoder_init()` 中直接填编码参数；B 在 [sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 的 `venc_set_chn_param()` 填公共参数，再通过 [sample_comm_venc.c](../../sample_source/common/sample_comm_venc.c) 建立通道。

| 配置维度 | A：自定义 RTP | B：RTSP 主例 |
|---|---|---|
| 输入来源 | SC500AI 2M/100 fps 模式，VPSS 通道 0 | 编译选择的 Sensor，VPSS 通道 0、1；当前 Makefile 缺省 SC4336P 4M/30 fps |
| 编码通道与尺寸 | VENC 0，1920×1080 | VENC 0：2560×1440；VENC 1：1024×768 |
| 编码类型 | H.265 | 两路 H.264 |
| 输入/输出帧率目标 | 100 fps | 两路 30 fps |
| 码控、GOP、统计周期 | CBR、100、1 秒 | CBR、60、2 秒 |
| 码率目标 | 4096，源码注释单位为 Kbit/s | 按编码面积计算：主路 7281、子路 1553 |
| 获取方式 | `is_by_frame=false`，启用切片输出 | 公共函数设置 `is_by_frame=true` |
| 实际网络消费者 | 通道 0 交给自定义 RTP | 只发布通道 0；通道 1 仍被取出并归还 |

B 的码率来自 `sample_comm_venc_h264_cbr_param_init()`，其计算把 1080p 的预算按像素面积缩放：

```text
目标码率 = 4096 × 编码宽度 × 编码高度 ÷ (1920 × 1080)
2560×1440：整数计算得到 7281
1024×768 ：整数计算得到 1553
```

这是一种静态预算规则，不会因为网络变差自动降低目标。A 不走这个 H.264 公共分支，也没有启用它旁边构造的 H.265 AVBR 参数；活动赋值选择的是 H.265 CBR。

编码器被创建和启动之后，还需要有人提供图像。A 随后调用 `vpss_bind_venc()`；B 逐路启动，再执行 `sample_comm_vpss_bind_venc(VPSS_GRP, i, i)`，两路完成后才启动取流线程。绑定建立的是媒体输入关系，应用不必逐帧调用 SendFrame 转交原图。

上述值都是请求的配置。A 的多处接口没有检查返回值，`venc_chn_attr` 也没有先整体清零；最终属性与输出效果还需要接口返回、属性回读和码流证据。GOP=100 与目标 100 fps 能给出“一组约一秒”的配置意图，不能据此宣布现场每秒必然出现一个完整刷新点。

## 7.3 一幅图像为什么会对应多种“包”

编码、SDK 和网络各自解决不同问题，因此各自划定边界：

**NAL（Network Abstraction Layer，网络抽象层）单元**是编码格式定义的内容单元，其头部告诉解码器后面的字节属于何种内容；名称带“网络”不表示它已经具有 UDP 地址或 RTP 序号。**SEI**是可携带时序等信息的补充增强信息，下面会看到本例怎样处理它。

| 对象 | 边界来自哪里 | 在本项目中装什么 |
|---|---|---|
| 一幅编码图像/其访问单元 | 编码格式与解码顺序 | 同一幅画面所需的切片等内容及相关非图像数据 |
| NAL 单元 | H.264/H.265 码流格式 | 一个切片、参数集或 SEI 等 |
| SDK pack | VENC 输出接口 | 一段编码数据的地址、偏移、长度、PTS、类型等描述 |
| RTP 包 | 网络封装 | 完整 NAL 或 NAL 分片等负载，附传输头 |

访问单元（Access Unit）用于组织与一个解码图像对应的码流内容。一个图像可以有多个切片 NAL，一个较大的 NAL 又可能分成多个 RTP 包，所以数 RTP 包不能得到图像数。

SDK pack 是另一层接口边界。A 的 `sendPacket()` 只剥离输入开头的一次 Annex B 起始码，并把余下区域当作一个 NAL；B 的 `rtsp_sever_tx_video()` 会在区域内扫描多个 NAL。但这两种处理都不能代替对 SDK 数据契约的确认，例如一个 NAL 是否可能跨多个 pack。

已有的 [MPP 开发参考](../../hi3516cv610/海思Hi3516CV610R001C01SPC020/ReleaseDoc/zh/01.software/board/MPP/MPP%20媒体处理软件%20V6.0%20开发参考.pdf) §6.3.9 给出了进一步约束：H.264/H.265 按包获取时，一次获取一个 NAL；按帧获取时应按当前帧的包数准备描述符；启用 `one_stream_buf` 时，一个 pack 又可以容纳同帧的多种 NAL。由此应先确认获取模式和模块配置，再解释 pack。该参考与实际构建头库的完整对应尚未建立，仍需把这些契约与运行属性核对。

后续协议章节会利用这些边界继续推导。这里先记住：`pack_cnt` 告诉应用要准备多少个描述对象；它本身没有证明这些描述分别对应几幅图像、几个 NAL 或几个网络包。

## 7.4 应用取得的是描述和使用权，不是整块内存的所有权

### 描述符怎样指向有效数据

`GetStream` 需要应用先提供描述符空间，再由 SDK 填入码流位置。下面是为解释关系节选的实际成员访问，不是可直接运行的完整函数：

```c
/* stream.pack 指向应用准备的描述符数组；码流字节仍由 SDK 管理。 */
stream.pack = packet_descriptor;
stream.pack_cnt = channel_status.cur_packs;

/* GetStream 成功后，才能使用 SDK 填入的地址、长度和时间信息。 */
uint8_t *data = stream.pack[i].addr + stream.pack[i].offset;
uint32_t size = stream.pack[i].len - stream.pack[i].offset;
```

用一个虚构地址算例看有效区间：假设 `addr=0x10000000`、`offset=64`、`len=1464`，有效起点是 `0x10000040`，长度是 1400 字节。

```text
SDK 区间： [前64字节][本次有效1400字节]
addr       = 0x10000000：SDK 返回的基地址
data       = addr + 64 ：跳过前缀区域，开始读取
区间终点   = addr + 1464（不包含）
可读区间   = [data, data + 1400)
```

因此不能从 `addr` 原位置直接发送 `len` 字节。表达式还依赖 `offset <= len`、地址有效等条件；这些检查属于接口边界，不能因常见数据正常就省略其含义。

描述符与码流的回收也不同：`ReleaseStream` 归还 SDK 数据的使用权，`free(stream.pack)` 释放应用自己的描述符数组。A 使用栈数组，不需要 free，但它仍需要归还 stream。

描述符中的 **PTS**（Presentation Time Stamp，显示时间戳）提供媒体时间信息，供下游组织播放节奏。它不是 `GetStream` 函数返回时的墙钟；本项目随后按微秒输入将它转换成 RTP 时钟值，实际产生位置和单位仍应与配套 SDK 核对。

### A 怎样完成一轮消费

A 的主线程进入 `rtp_send()`，反复调用 `processStream()`：

1. 查询 VENC 0 的状态；没有 pack 就返回，外层短暂休眠后重查。
2. 在栈上准备 `ot_venc_pack packet_descriptor[32]`，将查询数量写入 `stream.pack_cnt`。
3. 调用 `ss_mpi_venc_get_stream(..., 0)`。失败不使用数据；成功才进入 pack 循环。
4. 每个 pack 按有效区间交给 `sendPacket()`，同时传递 PTS 换算结果和 `is_frame_end`。
5. 本轮同步封装/发送调用结束，执行 `ss_mpi_venc_release_stream()`，让编码系统复用资源。

正常空轮询使用的 `usleep(1)` 与查询/取流失败时的 100 毫秒等待不同。1 微秒是休眠请求，不是调度器承诺的再次执行时间。

当前数组只有 32 个元素，却没有先比较 `cur_packs` 与 32。如果某次输出超过容量，描述空间与请求数量就不匹配；该数量在当前板端是否出现尚无证据。正确的容量设计应按接口可能返回的数量准备或明确处理超限。

### B 怎样等待两路结果

B 将消费放在 `venc_get_stream_proc()`。线程先取出两路 VENC fd，随后以 `select()` 等待就绪，单轮等待上限设为 2 秒。这里 fd 是编码器提供的可等待句柄；`select()` 只通知哪些句柄已有可处理事件，不把码流字节复制给应用，也不替应用取得 stream 使用权。可读时才进入 `venc_get_and_send_one_frame()`：

1. 查询该通道当前 pack 数，按数量 malloc 描述符。
2. 调用 `GetStream`；源码第三参写为 `TD_TRUE`。上述 MPP 参考将第三参定义为毫秒超时：`-1` 阻塞等待、`0` 非阻塞、正值为超时。因此若实际头库采用该接口且 `TD_TRUE=1`，它表达的是 1ms 等待，不是无限阻塞；最终以构建使用的声明与定义核对。
3. 通道 0 的非 SEI pack 交给 RTSP 库；通道 1 不发布。
4. 归还 stream，随后 free 描述符；Get 失败只释放尚未承载成功借用的描述符。

未发布的通道 1 已在编码，仍需消费其输出，才能避免该路一直占住有限输出资源。两路共用一个取流线程，所以主路封包或网络事件耗时会延后子路消费。`select()` 的 2 秒是无就绪数据时的超时，不是每幅图像固定等待 2 秒。

B 过滤 SEI 是此示例的选择。SEI 是补充信息，不能推广成所有播放器、所有视频用途都无需它。

### 协议函数返回之后，为什么能归还 SDK 数据

A 在调用期间把待发送片段复制到应用缓冲；B 在调用期间把 RTP 包写进 RTSP 库拥有的队列。因而两者返回之后，后续正常发送工作不再依赖这次 SDK 裸地址，调用者可以归还 stream。

如果未来改成“只把 SDK 地址放进异步队列，再立刻 Release”，网络线程可能读到编码器后来复用的新内容。要么在归还前复制到自有的有界队列，要么使用 SDK 明确支持的持有机制；后一种会延长编码缓冲占用。第 10 章继续分析这种选择对退出与背压的影响。

## 7.5 提前输出怎样减少等待，又把要求交给谁

A 把 `is_by_frame` 设为 false，并启用 `slice_output_en`，`split_mode=1`、`split_size=4`。其意图是在部分编码内容完成时开始消费，减少等待整幅编码结束的机会。

这里的“编码切片”不会直接等于一个 RTP 包。切片形成 NAL 后，网络还可能分片；接收端最终也可能等完整图像才解码/显示。具体 split_size 单位、最小返回批次和 `is_frame_end` 语义需要与实际 SDK 配套的资料，不能只凭注释里的 LCU 尺寸推算固定出包周期。

A 同时设置几种抑制等待或突发的手段：

| 当前配置 | 处理的约束 | 为什么还要观察实际输出 |
|---|---|---|
| 禁止重编码：`max_reencode_times=0` | 少做一次可能延长处理的编码尝试 | 复杂场景的码率和质量仍需折中 |
| QP 范围：I 为 18—42，其他图像为 20—45 | 限制量化调节空间 | 这些边界不是实际每幅采用的 QP |
| 关闭场景变化检测及自适应 IDR 插入 | 减少额外刷新突发的机会 | 场景突变和丢失后的恢复仍需评估 |
| 按行帧内刷新，数量 1，请求 I QP=30 | 将局部刷新分散到后续图像 | 不等价于每幅都能独立解码；与 GOP 共同作用需看码流 |
| 启用 P_SKIP 丢帧策略 | 达到编码侧条件时主动舍弃输出机会 | 与 UDP 网络丢包不同，触发规则以 SDK 为准 |
| 显式编码缓冲/小缓冲模式 | 限制内存预算 | 容量不是当前占用量，也不能直接换算延迟 |

这些设置应以“减少哪一段等待、增加什么代价”来理解。高帧率或切片输出只改变若干环节，接收缓存和显示如果仍然等待多幅图像，端到端效果可能被后段掩盖。

## 7.6 用一个异常定位交接断点

假设运行后没有画面，先问编码器是否持续产生 pack。如果没有，就回到 VENC 启动、VPSS 出图和绑定关系；如果有，下一步核对 Get/Release、有效区间和 NAL，而不是再次盲目更换 Sensor 配置。

若开始正常、后来停住，应检查成功 Get 是否都有对应 Release，以及发送处理是否长期占住借出的数据。这个观察能帮助定位消费压力，不能单凭停顿就宣布泄漏。若日志中“Frames”高于目标帧率，还应先核对计数层级：A 在 `sendPacket()` 中计数，它并不是可靠的图像 fps。

本章确认了控制语句与使用关系；SDK pack 划分、PTS 产生位置和单位、实际生效参数以及返回码仍是需要配套资料或板端补证的具体对象。网络字段如何利用 PTS，下一章继续推导。

## 7.7 自查题

1. 按紧密排列的 YUV 4:2:0 计算 1080p 单幅大小，并解释为什么这个结果不是整条链的 DDR 带宽。
2. 某 pack 的 `addr=0x10000000`、`offset=64`、`len=1464`。应从哪里消费多少字节？释放描述符能否代替归还 stream？
3. B 没有发布通道 1，为什么还在取流？如果将网络异步化，怎样避免 SDK 地址提前失效？
4. 切片输出、GOP=100、目标 100 fps 能否证明“一次 Get 就是一幅图像，且屏幕延迟很低”？还缺哪些依据？

### 参考答案

1. 单幅为 3,110,400 字节。它假定紧密排列，只计算一遍图像；stride、额外缓冲及各模块读写次数会改变真实内存流量。
2. 有效地址为 `0x10000040`，长度 1400 字节。描述符由应用准备，字节由 SDK 管理，必须分别 free/结束数组生命周期和 ReleaseStream。
3. 通道 1 已启动并绑定输入，会持续产生输出；当前通过取出后归还排空它。异步消费者应接收自有副本，或按正式接口延长持有并限制数量，不能排队裸地址后立即归还。
4. 不能。取流粒度需要 SDK 规则及 pack/NAL/结束标志证据；GOP 和帧率是配置，实际帧节奏要测量；端到端延迟还包括图像处理、取流、排队、网络及接收显示。
