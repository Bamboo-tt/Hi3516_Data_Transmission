# 01 项目总览与三条流程

[返回学习入口](README.md) · [下一章：BSP 与 SDK 构建基础](02_BSP与SDK构建基础.md)

这个项目要完成的工作很具体：相机产生连续图像，Hi3516CV610 对图像进行处理和压缩，用户态程序把压缩数据组织成网络能够传输的形式，接收端再恢复并显示画面。

难点来自多个条件必须同时成立：Sensor 要输出正确时序，板上驱动要认识硬件，媒体模块要有可用缓冲和正确连接，编码器要得到图像，发送端与接收端还必须遵守同一协议。某个程序已经运行，只能说明其中一部分条件成立。

## 1.1 先分清参与者的职责

Sensor 是相机的图像传感器。它把光转换成像素采样，按配置的时钟和帧时序输出数据。这里的原始图像常以 RAW Bayer 形式传输：每个像素位置记录一个颜色分量，还需要后续图像处理才能成为适合显示和编码的完整彩色图像。

Hi3516CV610 内部提供相机接入、图像处理和视频编码硬件。Linux 驱动负责让软件以受控方式使用这些硬件资源。厂商 SDK，即软件开发工具包，提供头文件、库、示例和文档；应用通过其中的 MPI 接口配置媒体模块。MPI 在本项目中指厂商媒体接口，不是分布式计算中的同名通信标准。

用户态程序运行在 Linux 进程中。它选择配置、建立模块、创建线程、取得压缩数据、封装网络协议并处理退出。接收端则要解释传输协议、重组压缩数据、解码并显示。接收端的实现不在当前两个主入口中，所以画面延迟与恢复效果不能只从发送函数推断。

| 参与者 | 它产出什么 | 谁依赖它 |
| --- | --- | --- |
| 板级电源、时钟、复位和引脚 | 可工作的硬件连接 | Sensor、MIPI 接收器、网络接口 |
| Sensor | 连续 RAW 图像及相应时序 | 芯片接入与图像处理模块 |
| 媒体硬件与驱动 | 处理后的图像、编码结果、运行状态 | SDK 与应用 |
| SDK 与 Sensor 适配 | 可调用的媒体接口、硬件差异适配 | 两个应用入口 |
| 应用控制代码 | 配置、绑定关系、工作线程和网络输出 | 媒体流水线及协议客户端 |
| 网络接收端 | 重组、解码、显示和接收侧统计 | 最终使用者 |

这些职责可以分别排查。例如，能打开 UDP socket 与 Sensor 是否输出图像几乎是两回事；能收到 RTP 包，与收到的参数集和图像是否足以解码也不是同一证据。

## 1.2 两条主线必须各自保持完整

【源码实现】主线 A 的入口是 [new_main2.c](../../hi3516firm/new_main2.c)。它直接组织 SC500AI、VI/ISP/VPSS、H.265 VENC 和自定义 RTP 发送，目的地址写为 `192.168.0.2:5622`。

【配置目标】A 请求 SC500AI 1920×1080、100 fps，H.265 CBR 4096 Kbit/s。CBR 表示恒定码率控制目标，不能理解为每幅图像或每毫秒都输出相同字节数。源码启用切片输出，并设置多处低延迟参数；这些参数将在对应环节解释。

【源码实现】主线 B 的入口是 [rtsp_4m/sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c)。它使用 `sample_comm_*` 公共辅助代码启动媒体系统，创建两路 H.264 编码，再通过内嵌 RTSP 库发布通道 0。

【配置目标】B 的两个编码输出尺寸是 2560×1440 和 1024×768，均为 30 fps。Sensor 来自构建宏 `SENSOR0_TYPE`；当前 [Makefile.param](../../sample_source/Makefile.param) 的缺省值是 SC4336P 4M/30 fps，不能自动替换成 A 的 SC500AI 模式。已有二进制采用哪个宏值，仍需构建记录或产物证据确认。

RTSP 是播放会话控制协议，用来询问媒体描述、协商传输方式和开始/停止播放；实际视频仍要使用 RTP 等媒体传输机制。A 直接把 RTP 发到固定端点，B 则先接受客户端请求，再按会话状态决定向哪些客户端发送。

## 1.3 构建与交付流程：多个产物汇合

构建发生在开发主机，目的是产生能够在目标板运行的文件。交叉工具链生成目标 CPU/ABI 的程序；ABI 是二进制接口约定，涉及指令架构、函数调用、数据布局和运行库等。

下面是【背景原理】与本工程材料相对应的产物关系，**不是声称这些构建入口在当前工作区全部齐备**：

~~~mermaid
flowchart LR
    BSP["板级支持源码与配置"] --> Boot["启动装载程序 / 环境"]
    BSP --> Kernel["Linux 内核 / 驱动"]
    RootCfg["根文件系统配置 / 用户态依赖"] --> Rootfs["根文件系统内容"]
    AppSrc["应用源码 + Sensor 适配"] --> Build["目标工具链编译链接"]
    SDK["SDK 头文件和库 / PQ API"] --> Build
    Build --> App["应用可执行文件"]
    PQ["调校 BIN / 配置 / 启动脚本"] --> Package["交付清单与文件系统打包"]
    App --> Package
    Rootfs --> Package
    Boot --> Delivery["配套交付物"]
    Kernel --> Delivery
    Package --> Delivery
~~~

启动程序、内核和用户态应用是分别构建、最终配套的产物，并非每次修改应用都必须顺次重编所有组件。更换了 ABI、驱动接口或板级配置时，配套范围才可能扩大。

【资料记录】当前目录有 SDK/工具链归档、若干 ELF 可执行文件、内核及根文件系统镜像，也有 DOCX 手工构建记录。【待确认】这些文件与当前源码之间尚缺一份完整的版本和摘要对应表。因此后面先解释如何读懂依赖，再讨论如何补齐构建证据。

## 1.4 上电与初始化流程：先有资源，再有应用连接

上电阶段的具体启动器和根文件系统脚本需要实际板端资料确认。能够从当前应用和已有说明确认的是依赖关系：应用使用媒体设备节点、SDK 库和图像缓冲，运行前必须有匹配的驱动、Sensor 连接和媒体内存。

## 1.5 运行时数据流：硬件持续处理，应用管理出口

VI 是视频输入模块，承接传感器接入与视频通道；ISP 是图像信号处理模块，处理 Bayer 图像并参与曝光、白平衡等控制；VPSS 是视频处理子系统，组织后续图像处理与不同尺寸通道；VENC 是视频编码器，把图像压缩成码流。

为了看清职责，可先按“采集与 ISP → VPSS → VENC”理解数据方向。VI 与 ISP 的实际内部耦合、在线通路和缓存方式取决于芯片/SDK，不能把这条概念箭头当成所有内部总线与内存搬运的精确图。

~~~mermaid
flowchart LR
    subgraph A["A：自定义 RTP 应用"]
        SA["SC500AI RAW"] --> IA["VI / ISP"]
        IA --> PA["VPSS chn0：1920×1080"]
        PA --> EA["VENC chn0：H.265"]
        EA --> GA["应用取码流 / RTP 封装"]
        GA --> UA["UDP 固定目的地址"]
    end
    subgraph B["B：RTSP 示例"]
        SB["由构建选择的 Sensor"] --> IB["VI / ISP"]
        IB --> PB["VPSS chn0 / chn1"]
        PB --> EB["VENC 0 / 1：H.264"]
        EB --> GB["取两路码流；只发布 chn0"]
        GB --> QB["RTSP 库的 RTP 队列"]
        Req["客户端会话请求"] --> State["RTSP 事件处理 / 客户端状态"]
        QB --> Send["按客户端进度发送"]
        State --> Send
        Send --> NB["UDP 或 TCP interleaved"]
    end
    UA --> RX["外部接收端：重组 / 解码 / 显示"]
    NB --> RX
~~~

图中的媒体箭头由通道连接和硬件工作推动。**CPU 上的应用并没有为每幅图像依次调用“做 ISP、做 VPSS、做编码”三个函数。** 它先配置并绑定模块，再在编码出口等待数据。取流时读到的是压缩结果，不是把全部原始像素重新在应用中处理一次。

另一方面，绑定只能证明建立了 SDK 层的数据关系。A 的协议封装仍使用内存复制；AI 示例甚至会把原始图像映射并复制到用户缓冲。因此必须在每个边界单独分析复制与所有权，不能只用“零复制”概括全系统。

## 1.6 把“一帧到达”拆成可检查的交接

以 A 为例，一幅图像首先由 Sensor 按时序产生；接入和图像处理链得到图像后，VPSS 向已连接的编码器提供输入。编码器可能逐个切片地产生压缩输出，应用通过 GetStream 得到描述符及有效字节范围，再把数据组成一个或多个 RTP 包。发送调用成功只能说明本机接受了该数据报，接收端还需要收到、重组、解码和显示。

描述符是“地址、长度、时间戳等信息”，并不等于描述符数组里存放了完整图像。归还编码码流后，原地址不再由本次应用读取周期持有；网络队列和接收队列又拥有各自的生命周期。

接下来学习 SYS/VB、VENC 和 RTP 的目的，就是把这段概述中的每个交接补齐：数据格式是什么，谁有权继续读取，谁负责归还，以及谁变慢会让哪里开始积压。

## 1.7 自查与回答要点

**问题 1：为什么不能说“程序启动后，CPU 不断执行 ISP，再执行编码”？**

回答要点：初始化调用建立硬件状态与连接，持续媒体处理主要由硬件和驱动推进；CPU 线程承担控制、算法框架运行及编码出口处理。应区分控制调用图与媒体数据图。

**问题 2：B 的两个编码通道是否意味着有两路摄像头，或两个 RTSP 地址？**

回答要点：当前示例把一个采集路径分成两个 VPSS/VENC 输出；会话发布逻辑只发送通道 0。通道数量、Sensor 数量和发布会话数量要分别核对。

**问题 3：为什么目录中有镜像和可执行文件仍不能说源码能够完整重建？**

回答要点：缺少完整的外层 SDK 构建配置、部分独立依赖与版本关联；文件存在只证明有产物，不能证明来自本次源码，也不能证明当前板端正在运行它。

**进一步追问：无线图传和串口遥测在图中应该放哪里？**

回答要点：放在媒体应用外部的承载与转发进程。文档中的无线派生发送器先发本机 UDP，再交给 WFB；MAVLink 转发由另一进程处理。主线 A 当前写死的远端地址与这一派生场景不同。
