# 16 关键源码与资料阅读索引

[返回学习入口](README.md) · [上一章：项目讲解提纲](15_项目讲解提纲.md)

前面已经形成了系统模型，本章把模型连接回实际文件。查证从一个具体判断出发：谁产生数据，哪个调用交接，谁消费，哪里释放？表中的函数名和路径用于定位这些关系，不能仅以“找到了同名函数”作为完成核对。

本次复核日期为 **2026-10-13**。链接不固定旧行号；代码变化后重新确认调用者、宏选择和活动分支。源码、配套资料、构建产物与板端记录分别承担不同证据，阅读顺序应随要验证的判断选择。

## 16.1 先用入口确认正在分析的对象

先确定可执行程序，再进入公共层。同一个 `sample_comm_*` 被不同示例调用时，接收到的 Sensor、通道、编码类型与运行模式可能不同。例如“B 发布哪一路”要先从 `main` 跟到取流发布条件，“已有 ELF 采用哪一 Sensor”还需要构建记录，单看缺省宏无法完成证明。

## 16.3 媒体初始化与缓冲

初始化阅读应同时记录“创建了什么”和“失败后撤销什么”。同一个编号 `0` 在 VI pipe、VPSS group、VPSS channel 和 VENC channel 中指不同对象，绑定函数把它们连接起来。缓冲大小计算与通道属性共同限定数据布局；结构字段、有效池项、每池块数和实际占用要分别核对。尤其不能把参考版本中的保留字段 `max_pool_cnt` 当成已经分配的池数量。

## 16.7 协议原始资料

第 08、09 章引用以下标准解释协议字段，项目实际调用仍以当前 C 源码为准：

- [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550)：RTP 基本头、序号、时间戳、SSRC 与 RTCP。
- [RFC 7798](https://www.rfc-editor.org/rfc/rfc7798)：H.265 的 RTP 负载、FU 与访问单元标记。
- [RFC 6184](https://www.rfc-editor.org/rfc/rfc6184)：H.264 的 RTP 负载与 Marker 语义。
- [RFC 2326](https://www.rfc-editor.org/rfc/rfc2326)：当前简易库所对应的 RTSP/1.0 请求及 TCP interleaved 背景；不据此宣称它实现了标准所有能力。

阅读标准后仍要问：源码是否实现了这个分支、是否保留了要求的字段、失败时有没有维持状态？“协议规定应如此”与“本程序已如此”是两层结论。

## 16.8 查证练习

1. 找到 `thread_start` 后，怎样判断 worker 失败退出时是否仍会被 join？给出要查的分支，不能只看变量类型。
2. 发现源码注释写“移到 tail”，实际赋值却使用 `streamq_head(q)`。应该怎样说明行为，再用什么关系判断其影响？
3. SDK 资料说明某模式支持低延迟，当前代码存在一个低延迟字段。还需要哪些证据，才能判断正在播放的通道使用了它？
4. 某个已有 ELF 与源码文件修改日期接近。怎样建立可重复的对应关系？当前最少缺少哪些记录？

## 16.9 参考答案

1. 查线程创建成功和失败路径、worker 对标志的全部写入、主线程对标志的读取，以及 stop 函数的 join 条件。当前 B 把运行标志与 join 条件混用；worker 先清标志时，stop 可能跳过已经创建的线程。
2. 以活动赋值说明“从仍保留的最旧包继续”，再结合 queue 有效区、淘汰与客户端进度分析。它与直接跳最新位置具有不同延迟，且按包恢复不保证完整 NAL 或可解码图像。
3. 核对 SDK/库配套、调用成功、字段作用的模块与通道、实际发布分支、参数回读或运行记录。B 的 200 行配置在通道 1，发布通道为 0，不能跨通道移用结论。
4. 日期和同名只提供线索。需要源码提交/摘要、工具链与 SDK/PQ 版本、构建宏和命令、链接输入与最终 ELF 摘要，再与板端实际运行文件对应。Git 记录源码这一层，不自动补齐其余层。
