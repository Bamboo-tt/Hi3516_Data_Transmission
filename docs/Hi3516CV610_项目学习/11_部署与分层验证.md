# 11 部署与分层验证

[返回学习入口](README.md) · [上一章：并发与资源退出](10_并发与资源退出.md) · [下一章：低延迟与性能分析](12_低延迟与性能分析.md)

理解源码之后，部署要回答一个新的问题：板端运行的程序，是否就是刚才分析的那份代码、那组配置和那套依赖？如果对应关系不清楚，后面的日志和测量即使真实，也可能无法解释当前源码。

本章给出需要建立的证据和后续操作顺序。**这些是待执行的验证步骤，本次没有运行应用、交叉编译、安装、刷机、装卸驱动或修改系统配置。** 不提供伪造终端输出，也不把历史说明中的成功记录转写成当前结果。

## 11.1 交付前先固定一个配置组合

选择 A 或 B 后，需要把“选了什么”整理成一份可追溯记录。它的作用是让构建者、板端操作者和接收端测试者讨论同一个对象。

| 需要记录 | A 的当前已知信息 | B 的当前已知信息 | 仍需补齐 |
| --- | --- | --- | --- |
| 源码入口 | `new_main2.c` | `rtsp_4m/sample_rtsp.c` 与公共代码 | 所有参与构建源文件的版本或摘要 |
| Sensor | SC500AI 2M/100 fps 定制适配 | 来自 `SENSOR0_TYPE`，Makefile 缺省 SC4336P 4M/30 fps | 实际编译宏、实物 Sensor 与板级连接 |
| 工具链与 SDK | 本地有相应归档和历史命令 | 依赖外层 SDK 构建配置 | 实际编译器版本、ABI、头库与内核模块配套 |
| 附加依赖 | PQ API、`sc500ai_1080P_100.bin` | 内嵌 `librtsp.a` | 库的来源、构建摘要、调校文件与模式对应关系 |
| 运行目录 | PQ 使用 `./` 相对路径 | 主入口没有 A 的 PQ 导入调用 | 板端程序路径、当前目录、动态库搜索环境 |
| 输出配置 | 远端 `192.168.0.2:5622` | 554、`/test.264`；传输方式由 SETUP 选择 | 接收器、网络地址及接收端实际协议配置 |
| 运行结果 | 本次未验证 | 本次未验证 | 分阶段日志、数据计数、接收与退出记录 |

根工作区当前没有 Git 仓库，因此不能假定存在可用的提交号。可以用参与构建文件的内容摘要和构建记录建立关联，但“给文件计算过摘要”只证明文件身份，不能证明程序运行正确。

## 11.2 从构建到接收画面，要跨过哪些证据边界

~~~mermaid
flowchart LR
    S["源码与配置可追溯"] --> C["干净环境编译链接"]
    C --> P["产物与板端依赖一致"]
    P --> I["逐阶段初始化成功"]
    I --> V["实际图像与编码持续产出"]
    V --> T["发送成功与接收包一致"]
    T --> D["接收端重组并解码"]
    D --> A["时延 / 稳定性满足使用目标"]
~~~

每条箭头都需要新增证据。编译通过不能证明 Sensor 有图像；图像存在不能证明码流封装正确；发送成功不能证明网络到达；接收包到达不能证明解码依赖完整；出现画面也不能证明延迟和长期稳定性满足目标。

## 11.3 第一步：在开发主机确认依赖能够闭合

先检查构建入口到底消费哪些文件，再决定如何准备环境。A 需要 SDK 头库、定制 Sensor 目录和独立 PQ API；当前 `new_main2.c` 的相对 include 与工作区 Sensor 实际位置不同。B 需要外层 `Makefile.param` 和公共对象，RTSP 库还存在目标依赖顺序问题。这些条件在第 02 章已经从 Makefile 解释。

后续验证时应使用明确的目标工具链和干净输出目录，保存完整编译与链接命令、宏值、所用库路径和产物摘要。静态库由哪些对象构成也需可追溯，避免把旧 `.o/.a` 当作本次构建结果。

这一步成功可以证明“这一组源码和依赖能够形成目标产物”。它仍不能证明文件已放到板端、动态库能被装载、内核接口匹配，或 Sensor 初始化会成功。

【资料记录】[使用文档（3）](../../hi3516firm/hi3516firm/海思hi3516-hi3519使用文档(3).docx) 有 `arm-v01c02-linux-musleabi-gcc` 的手工链接示例，并记录独立 `libbin` 的头文件与库复制过程。这里把它作为依赖组成的例子，不复制其中 `/home/ubuntu/...` 路径为当前可直接执行的重建命令。

## 11.4 第二步：确认板端环境与交付物身份

后续实际部署前，需要记录板型、Sensor 实物、内核与驱动版本、运行中的媒体内存设置、应用/库/PQ 文件摘要，以及进程运行目录。读取已有启动配置和日志时，保留原始时间与上下文；本次没有执行这些板端读取。

重点有三处：

1. **应用和驱动必须配套。** 用户态接口名称相同，不足以保证结构布局和驱动 ABI 相容。
2. **启动说明必须对应板上实际文件。** DOCX 中的 `S99autostart` 不代表镜像里已经有相同脚本。示例功能开关最初全部注释，之后才指导选择启用。
3. **文件所在位置与当前目录要分开。** A 即使从绝对路径启动，也会按当前目录寻找 `./sc500ai_1080P_100.bin`；历史脚本先 `cd /root`，是那份部署例子中的路径约定。

[nand_burn_table.xml](../../hi3516firm/nand_burn_table.xml) 列出了 boot、env、kernel、rootfs 的计划，但当前 rootfs 项的 `SelectFile` 为空。该文件可以帮助理解烧录工具的输入，不能作为板端真实分区、已刷内容或可直接执行烧录的依据。

## 11.5 第三步：沿媒体链验证，避免用一条日志代替全部状态

实际板端验证宜一次只选择一个媒体应用。多个示例默认使用相同设备、pipe、group 和编码通道编号；并行运行可能互相占用甚至被另一程序的全局 SYS/VB 初始化影响。

| 检查对象 | 应取得的具体证据 | 可以证明 | 仍不能证明 |
| --- | --- | --- | --- |
| MIPI/VI 配置与启动 | 关键接口返回值、配套驱动状态、输入帧计数或错误计数 | 接入模块被配置、是否持续看到输入 | ISP 处理正确、颜色与曝光合理 |
| Sensor/ISP | 模式、曝光与帧时序，PQ 导入结果，最终参数查询 | 当前请求及部分生效参数相互一致 | 实际图像质量、所有闭源算法内部状态 |
| VPSS | 实际输出尺寸、像素格式、通道运行与出帧状态 | 处理链能提供预期形态的图像 | VENC 已接到图像并正常编码 |
| VENC | 输入/输出状态、连续编码计数、PTS、错误/丢帧信息 | 编码器持续产出数据，输出节奏可观察 | RTP 封装与接收解码正确 |
| Get/Release | 成功借出与归还数量、错误退出路径 | 应用消费和归还是否闭合 | SDK 内部没有其他资源压力 |

其中具体状态接口和只读诊断节点，应先在配套 SDK/板端确认；文档不凭其他平台经验虚构 `/proc` 路径或命令。

A 当前许多调用没有检查返回值，程序现有日志可能不足以提供上述全部证据。此时应把缺失项记录出来；若后续需要增加最小诊断，再单独实施。**本任务没有补写日志或修复源码。**

100 fps 的验证应观察持续产出的图像数或可信帧序号/PTS 间隔，并说明采样时长、场景和错误计数。A 的 `frames_sent` 实际按处理 NAL 的调用增加，不能直接作为实际图像帧率。

## 11.6 第四步：在传输与接收边界分别取证

### A：先对齐双方协议约定

接收端必须知道目标端口、H.265 编码、RTP 动态负载类型映射与时钟。PT=96 本身不能告诉任意接收器“这里一定是 H.265”。A 没有 RTSP 协商，因此这份映射需要从接收配置或单独的会话描述取得。

发送端应记录 `sendto()` 成功/失败与成功字节，接收端应记录 RTP 序号、时间戳、NAL 重组和解码结果。通过同一段时间窗口对照，才能把本地发送失败、途中丢失和解码依赖缺失分开。

当前源码没有这套完整统计。后续抓取或解析时，只能说明实际观察到的内容，不把 `packets_sent` 这种“调用次数”计数当成内核成功发送数。

### B：分别确认会话推进与媒体到达

先确认 DESCRIBE 的媒体描述和参数集，SETUP 选择的传输方式与端口/通道，再确认 PLAY 对应的客户端状态和 RTP 到达情况。TCP 连接成功只能证明控制连接建立；当前网络事件仍由视频发送入口驱动，编码停产时控制响应也可能停滞。

UDP 与 TCP interleaved 应分别验证，因为它们的发送边界不同。UDP 包丢失与 TCP 短写不是同一种问题；TCP 发送需要续传状态，不能仅检查是否返回负数。验证标准是接收端能正确解析完整媒体边界，而不只是“连接没有断开”。

## 11.7 第五步：退出、重启与实际使用目标

画面出现后，还需要在受控条件下观察正常退出：线程是否结束并被 join，在途 stream/frame 是否归还，媒体通道是否停止，下一次启动是否能够重新申请资源。A 当前没有完整停机路径，因此应把这个实现缺口与实际运行结果分别记录，不能预填“已通过”。

对于延迟，至少说明测量起止点。例如只测 `sendto()` 的耗时，不包含曝光、ISP、编码、无线、接收缓存和显示。端到端比较需要相同测量定义与可比较的场景，不能把两个不同起止点的数值放在一起判断优化收益。

无线场景还应单独记录派生发送器的本机目的地址、WFB 版本与参数、接收端配置和实际链路条件。主线 A 的有线/固定远端源码验证，不能自动覆盖这条额外承载链。

## 11.9 自查与回答要点

**问题 1：编译成功、初始化成功、接收端出图分别增加了什么证据？**

回答要点：分别证明源码/依赖能形成产物、资源建立与部分配置可生效、传输及解码链在该场景中至少工作过；前一个结论不能替代后一个，短时出图也不等于长期可靠。

**问题 2：为什么运行目录也要写入交付记录？**

回答要点：A 的 PQ BIN 使用相对路径，AI 示例也有相对模型和输入路径。可执行文件的路径与当前工作目录不同，会导致读取不同文件或打开失败。

**问题 3：既然目录中有 `local_rtp_demo` 的部署记录，能否据此确认当前源码已部署？**

回答要点：记录中的文件可能来自不同编译参数、SDK 或地址修改。需要源文件到产物摘要再到板端文件的对应关系，文件名不够。

**进一步追问：如果只获得“Ready for streaming”日志，该写什么结论？**

回答要点：只说明执行到该打印点；还缺关键接口返回值、持续编码输出、发送结果和接收解码证据。先按缺失的交接补证，不能宣布全链路成功。
