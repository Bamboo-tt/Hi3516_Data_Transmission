# 11 部署与分层验证

[返回学习入口](README.md) · [上一章：并发与资源退出](10_并发与资源退出.md) · [下一章：低延迟与性能分析](12_低延迟与性能分析.md)

前面已经能解释图像怎样经过媒体模块，码流怎样被取出、发送和归还。部署要把这条静态调用链连接到真实设备：板端执行的程序，是否来自分析过的源文件、编译选项和配套参数？

假设开发机改了 Sensor 宏，板上仍运行旧二进制，接收器又沿用另一份协议配置。三个地方即使各有“成功”日志，也无法归到同一个系统。因此本章先建立产物身份，再检查装载与资源前提，最后沿媒体、协议、解码和退出取得运行证据。

以下板端步骤属于后续验证设计；本次只核对本地源码和材料，没有构建或运行应用，也没有修改板端环境。

## 11.1 交付前先固定一个配置组合

选择 A 或 B 后，先问这份可执行文件的行为由哪些输入决定。编译宏、头文件和静态库对象会影响生成的二进制；动态库、驱动与 PQ 参数又会在装载或运行阶段继续参与。只记录入口文件名，会漏掉这些选择。

把它们整理在同一份记录中，构建者、板端操作者和接收端测试者才是在讨论同一个对象：

| 需要记录 | A 的当前已知信息 | B 的当前已知信息 | 仍需补齐 |
| --- | --- | --- | --- |
| 源码入口 | `new_main2.c` | `rtsp_4m/sample_rtsp.c` 与公共代码 | 所有参与构建源文件的版本或摘要 |
| Sensor | SC500AI 2M/100 fps 定制适配 | 来自 `SENSOR0_TYPE`，Makefile 缺省 SC4336P 4M/30 fps | 实际编译宏、实物 Sensor 与板级连接 |
| 工具链与 SDK | 本地有相应归档和历史命令 | 依赖外层 SDK 构建配置 | 实际编译器版本、ABI、头库与内核模块配套 |
| 附加依赖 | PQ API、`sc500ai_1080P_100.bin` | 内嵌 `librtsp.a` | 库的来源、构建摘要、调校文件与模式对应关系 |
| 运行目录 | PQ 使用 `./` 相对路径 | 主入口没有 A 的 PQ 导入调用 | 板端程序路径、当前目录、动态库搜索环境 |
| 输出配置 | 远端 `192.168.0.2:5622` | 554、`/test.264`；传输方式由 SETUP 选择 | 接收器、网络地址及接收端实际协议配置 |
| 运行结果 | 本次未验证 | 本次未验证 | 分阶段日志、数据计数、接收与退出记录 |

当前工作区已经是 Git 仓库。提交号能够标识受版本管理的内容，但未提交修改、目录外 SDK 和被忽略的库不一定由该提交覆盖。可追溯交付需要把源码版本及差异、构建输入和产物身份连接起来；提交号或文件摘要单独都不能证明板端程序运行正确。

## 11.2 从构建到接收画面，要跨过哪些证据边界

~~~mermaid
flowchart LR
    S["源码与配置可追溯"] --> C["干净环境编译链接"]
    C --> P["产物与板端依赖一致"]
    P --> I["逐阶段初始化成功"]
    I --> V["实际图像与编码持续产出"]
    V --> T["发送成功与接收包一致"]
    T --> D["接收端重组并解码"]
    D --> A["时延 / 稳定性满足使用目标"]
~~~

图中的箭头表示新增证据，不能用前一步的成功代替后一步的完成。编译通过说明选定输入能够形成产物；初始化返回值说明部分资源操作被接受；持续编码说明媒体通路在产生结果；对端重组与解码才把证据延伸到传输之后。

把验证拆开还有一个收益：失败能够留在两个相邻对象之间。若媒体一直出流而对端未收到，应先研究封装和提交；若程序还没有进入 `main()`，网络播放器就不是当前的排查对象。

## 11.3 先让构建输入形成一个可解释的产物

先检查构建入口到底消费哪些文件，再决定如何准备环境。A 需要 SDK 头库、定制 Sensor 目录和独立 PQ API；当前 `new_main2.c` 的相对 include 与工作区 Sensor 实际位置不同。B 需要外层 `Makefile.param` 和公共对象，RTSP 库还存在目标依赖顺序问题。这些条件在第 02 章已经从 Makefile 解释。

旧 `.o`、`.a` 和 ELF 可以让一个目录看起来有完整产物，却掩盖缺失的依赖。后续重建应使用明确的目标工具链和独立输出位置，保存完整编译与链接参数、宏值、所用库路径和产物摘要。静态库由哪些对象组成也需要可追溯，而不是只看链接器最终找到同名符号。

这一步成功可以证明“这一组源码和依赖能够形成目标产物”。它仍不能证明文件已放到板端、动态库能被装载、内核接口匹配，或 Sensor 初始化会成功。

【资料记录】[使用文档（3）](../../hi3516firm/hi3516firm/海思hi3516-hi3519使用文档(3).docx) 有 `arm-v01c02-linux-musleabi-gcc` 的手工链接示例，并记录独立 `libbin` 的头文件与库复制过程。这里把它作为依赖组成的例子，不复制其中 `/home/ubuntu/...` 路径为当前可直接执行的重建命令。

## 11.4 板端怎样接过这个产物

### 装载、接口和硬件是三种前提

编译器按照当前头文件检查调用，链接器在选中的对象和库中找符号。放到板端后，装载器还要识别目标架构和 ABI，找到需要的动态库；媒体调用随后才进入内核驱动并操作硬件资源。

ABI 是二进制接口约定，涉及调用方式、数据布局和运行库环境。函数名字相同，不足以证明不同版本的参数结构、驱动请求和算法库相容。因此应核对工具链、运行库、SDK 用户库与内核模块的配套关系。

这也给出第一轮判断：执行前装载失败，先查产物与运行库；进入 `main()` 后媒体调用失败，查接口与资源；已经持续产出编码数据，再向网络和解码推进。不能把这三种情况都解释成 Sensor 配置错误。

### 路径与启动记录怎样影响实际读取

后续实际部署前，需要记录板型、Sensor 实物、内核与驱动版本、运行中的媒体内存设置、应用/库/PQ 文件摘要，以及进程运行目录。读取已有启动配置和日志时，保留原始时间与上下文；本次没有执行这些板端读取。

在这组环境记录中，有三处容易断开对应关系：

1. **应用和驱动必须配套。** 用户态接口名称相同，不足以保证结构布局和驱动 ABI 相容。
2. **启动说明必须对应板上实际文件。** DOCX 中的 `S99autostart` 不代表镜像里已经有相同脚本。示例功能开关最初全部注释，之后才指导选择启用。
3. **文件所在位置与当前目录要分开。** A 即使从绝对路径启动，也会按当前目录寻找 `./sc500ai_1080P_100.bin`；历史脚本先 `cd /root`，是那份部署例子中的路径约定。

[nand_burn_table.xml](../../hi3516firm/nand_burn_table.xml) 列出了 boot、env、kernel、rootfs 的计划，但当前 rootfs 项的 `SelectFile` 为空。该文件可以帮助理解烧录工具的输入，不能作为板端真实分区、已刷内容或可直接执行烧录的依据。

## 11.5 从资源建立观察到持续出流

实际板端验证宜一次只选择一个媒体应用。多个示例默认使用相同设备、pipe、group 和编码通道编号；并行运行可能互相占用，部分初始化还会影响全局 SYS/VB，使一个应用的日志难以解释另一个应用的资源状态。

初始化返回值回答“某项操作是否被接受”，连续数据回答“建立的关系是否一直工作”。创建成功后没有图像输入，编码仍会为空；开始有图像但长期不归还缓冲，也可能先正常后停住。把这两类证据放在同一时间范围观察，才能沿下表向后推进。

| 检查对象 | 应取得的具体证据 | 可以证明 | 仍不能证明 |
| --- | --- | --- | --- |
| MIPI/VI 配置与启动 | 关键接口返回值、配套驱动状态、输入帧计数或错误计数 | 接入模块被配置、是否持续看到输入 | ISP 处理正确、颜色与曝光合理 |
| Sensor/ISP | 模式、曝光与帧时序，PQ 导入结果，最终参数查询 | 当前请求及部分生效参数相互一致 | 实际图像质量、所有闭源算法内部状态 |
| VPSS | 实际输出尺寸、像素格式、通道运行与出帧状态 | 处理链能提供预期形态的图像 | VENC 已接到图像并正常编码 |
| VENC | 输入/输出状态、连续编码计数、PTS、错误/丢帧信息 | 编码器持续产出数据，输出节奏可观察 | RTP 封装与接收解码正确 |
| Get/Release | 成功借出与归还数量、错误退出路径 | 应用消费和归还是否闭合 | SDK 内部没有其他资源压力 |

其中具体状态接口和只读诊断节点，应先在配套 SDK/板端确认；文档不凭其他平台经验虚构 `/proc` 路径或命令。

借还计数应按同一通道、同一次运行比较。例如成功 GetStream 100 次、成功 ReleaseStream 99 次时，差值 1 可能只是 worker 正在处理一份 stream；只有停止获取并完成在途处理后，差值才应回到零。差值持续不回落或长期增长时，应继续查持有过久、遗漏归还或归还失败。这里数的是借用次数，一次 stream 内有多个 pack 也只对应这一次借还。

A 当前许多调用没有检查返回值，程序现有日志可能不足以提供上述全部证据。此时应把缺失项记录出来；若后续需要增加最小诊断，再单独实施。**本任务没有补写日志或修复源码。**

100 fps 的验证应观察持续产出的图像数或可信帧序号/PTS 间隔，并说明采样时长、场景和错误计数。切片输出时，同一幅图像的多个 pack 可能共享 PTS；应先按经 SDK 语义确认的帧尾或图像序号识别图像，再比较不同图像的时间间隔，不能把每个 pack 当作一幅图像。A 的 `frames_sent` 实际按处理 NAL 的调用增加，不能直接作为实际图像帧率。

## 11.6 把编码输出连接到远端解码

### A：先对齐双方协议约定

接收端必须知道目标端口、H.265 编码、RTP 动态负载类型映射与时钟。PT=96 本身不能告诉任意接收器“这里一定是 H.265”。A 没有 RTSP 协商，因此这份映射需要从接收配置或单独的会话描述取得。

发送端应记录 `sendto()` 成功/失败与成功字节，接收端应记录 RTP 序号、时间戳、NAL 重组和解码结果。通过同一段时间窗口对照，才能把本地发送失败、途中丢失和解码依赖缺失分开。

当前源码没有这套完整统计。后续抓取或解析时，只能说明实际观察到的内容，不把 `packets_sent` 这种“调用次数”计数当成内核成功发送数。

### B：分别确认会话推进与媒体到达

先确认 DESCRIBE 的媒体描述和参数集，SETUP 选择的传输方式与端口/通道，再确认 PLAY 对应的客户端状态和 RTP 到达情况。TCP 连接成功只能证明控制连接建立；当前网络事件仍由视频发送入口驱动，编码停产时控制响应也可能停滞。

UDP 与 TCP interleaved 应分别验证，因为它们的发送边界不同。UDP 包丢失与 TCP 短写不是同一种问题；TCP 发送需要续传状态，不能仅检查是否返回负数。验证标准是接收端能正确解析完整媒体边界，而不只是“连接没有断开”。

## 11.7 出图之后，再验证退出与使用目标

一次出图只覆盖当时的启动与数据条件。结束使用后，原来持有资源的执行者还需要停止，让在途 stream/frame 归还、线程被 join、媒体通道回收，下一次启动才能重新取得资源。因此正常退出和再次启动是同一生命周期的后半段。

A 当前没有完整显式停机路径，这是源码事实；它在具体板端造成什么现象，要与实际记录分开。验证表不能因为画面曾经出现，就预填退出也已通过。

对于延迟，至少说明测量起止点。例如只测 `sendto()` 的耗时，不包含曝光、ISP、编码、无线、接收缓存和显示。端到端比较需要相同测量定义与可比较的场景，不能把两个不同起止点的数值放在一起判断优化收益。

无线场景还应单独记录派生发送器的本机目的地址、WFB 版本与参数、接收端配置和实际链路条件。主线 A 的有线/固定远端源码验证，不能自动覆盖这条额外承载链。

## 11.8 让下一位操作者能够复核同一结果

记录应先固定对象，再保留过程，最后写能够成立的结论。下面是字段说明，不代表测试已经执行：

| 字段 | 待记录内容 |
| --- | --- |
| 对象 | A/B/某个扩展示例；源文件、应用、库和参数文件摘要 |
| 环境 | 板型、Sensor、SDK/驱动、内存配置、网络与接收端版本 |
| 配置 | 实际 Sensor 宏、尺寸、帧率、码率、模式、运行目录、传输端点 |
| 操作 | 本次真正执行的步骤、时间窗口、输入场景 |
| 观察 | 原始返回值、状态、计数、包或解码记录；保存其来源 |
| 结论 | 哪个交接已经有证据支持 |
| 边界 | 未覆盖的阶段、触发条件、使用场景和仍待确认事项 |

## 11.9 自查问题

1. 编译成功、初始化成功和接收端出图，分别比前一个阶段增加了什么证据？短时出图仍缺少哪些条件？
2. 已用绝对路径启动 A，却无法打开 PQ 文件。需要区分哪两个路径概念？
3. 已有 Git 提交和 `local_rtp_demo` 部署记录，还缺什么才能确认当前源码已在板端运行？
4. 如果只获得 `Ready for streaming` 日志，该写出怎样的有限结论，下一步怎样补证？

## 11.10 参考答案

1. 编译把一组源码与依赖连接成产物；初始化返回说明部分资源操作被接受；接收出图再覆盖当时的媒体、传输与解码关系。持续帧率、退出、异常场景及长期稳定性仍要各自观察。
2. 可执行文件的位置与进程当前工作目录。`./sc500ai_1080P_100.bin` 按后者解析，还需要核对实际读到的文件是否对应当前模式。
3. 需要记录相关未提交差异、目录外头库和编译宏，把构建产物身份再与板端文件对应。提交、同名文件和历史记录单独都不构成完整关联。
4. 只能说明执行到打印点。先确认关键初始化返回与持续编码输出，再核对发送结果和接收解码，不能用 Ready 替所有交接作证。
