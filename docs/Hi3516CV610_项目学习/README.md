# Hi3516CV610 图像数据传输项目学习

这套文档从“相机图像怎样到达接收端”出发，逐步解释板级环境、传感器适配、媒体流水线、硬件编码、协议发送和资源回收。目标是读完后能够沿一幅图像讲清整套系统，也能在某一环节异常时知道下一步查什么。

本次源码复核日期：**2026-10-06**。工程根目录是 `hi3516_Image_Data_Transmission/`；本目录中的源码链接均从这里所在位置使用相对路径定位，正文用函数名辅助检索，不依赖旧行号。

## 先确定自己正在理解哪一个程序

当前工程包含多个独立示例、SDK/工具链归档、固件和历史说明。学习时以两个可执行程序的源代码入口为主线：

| 对照项 | 主线 A：自定义 RTP | 主线 B：RTSP 示例 |
| --- | --- | --- |
| 入口 | [hi3516firm/new_main2.c](../../hi3516firm/new_main2.c) 的 `main()` | [rtsp_4m/sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 的 `main()` |
| Sensor 选择 | 源码选择 SC500AI 1080p/100 fps 模式 | `SENSOR0_TYPE` 来自构建；当前 [Makefile.param](../../sample_source/Makefile.param) 缺省为 SC4336P 4M/30 fps，可被外部构建配置覆盖 |
| 图像与编码目标 | 1920×1080，H.265，100 fps，CBR 4096 Kbit/s | 主通道 2560×1440、子通道 1024×768，均为 H.264、30 fps |
| 主要数据模式 | VI offline、VPSS online；wrap 关闭；编码切片输出 | VI/VPSS online，默认启用 wrap；两路编码取流 |
| 实际输出路径 | 自定义 RTP，经 UDP 发往 `192.168.0.2:5622` | RTSP 554、`/test.264`；发布编码通道 0，通道 1 仍被取流但未在此会话发布 |
| 不能据此推断 | 当前板端确实达到 100 fps 或使用相同二进制 | 当前板端实际使用哪一 Sensor、两路都有对外画面 |

**A 与 B 是两个入口，参数不能拼接成一个应用。** OSD、AI、录像、其他协议和无线部署集中放在扩展章，说明它们改变的接入位置与资源关系。

## 本套文档如何使用证据

正文在容易混淆的地方使用以下标记。它们表达不同证据层级，不是同一功能逐渐升级的状态名称。

| 标记 | 含义 | 不能扩大解释为 |
| --- | --- | --- |
| 【背景原理】 | 为理解代码补充的通用机制，例如压缩、缓冲所有权、TCP 分段写入 | 闭源 SDK 内部恰好采用了某个未公开实现 |
| 【源码实现】 | 当前文件中实际存在的调用、分支、返回值处理或资源关系 | 代码已经编译成功或对应分支已经在板端执行 |
| 【配置目标】 | 源码或 Makefile 请求的模式、数量、帧率、尺寸、码率 | 实际分配量、最终生效值或测量结果 |
| 【资料记录】 | 已有 DOCX、PDF 或历史构建说明记载的例子 | 当前工作区具备相同环境，或者当前固件包含该例子 |
| 【验证证据】 | 明确说明执行对象、检查方法及结果的记录 | 其他版本、其他阶段和现场效果也通过 |
| 【待确认】 | 缺少当前 SDK 配套、构建、板端或接收侧依据的事实 | 已知成功，或已经现场复现的失败 |

本次执行的检查限于文件阅读、源码调用与配置复核、Markdown 结构及链接检查、原文件保护核对。**没有执行交叉编译、程序运行、驱动装卸、系统配置、安装或刷机，也没有测量板端帧率与接收端时延。** 需要补充的运行验证在第 11 章列明，每一步同时说明能证明什么和不能证明什么。

上一份 [全局架构与技术剖析](../全局架构与技术剖析.md) 保留原样。它是历史分析入口，本套文档以重新核验的源码为依据，重点讲解问题、机制与组件之间的交接过程。

## 读代码时一直带着的六个问题

每进入一个新阶段，先问：谁在执行？数据在哪里？格式是什么？通过什么接口交给下一环节？下一环节尚缺什么条件？当前资源什么时候归还或释放？

例如，`GetStream` 的调用者是应用线程，但返回码流的存储由 SDK 管理；网络发送需要读取这些字节，而 `ReleaseStream` 之后其内容不能再被异步消费者继续引用。这个判断方法会贯穿整套文档，比先记住大量结构体成员更有用。
