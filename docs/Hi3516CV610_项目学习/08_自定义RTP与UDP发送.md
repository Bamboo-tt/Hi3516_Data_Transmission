# 08 自定义 RTP 与 UDP 发送

[学习入口](README.md) · 上一章：[VENC 编码与码流生命周期](07_VENC编码与码流生命周期.md) · 下一章：[RTSP 会话与媒体分发](09_RTSP会话与媒体分发.md)

本章只跟踪 [new_main2.c](../../hi3516firm/new_main2.c) 的 `processStream()` → `sendPacket()` → `transmit()`。输入是 SDK 提供的 H.265 码流区域；输出是发往 `192.168.0.2:5622` 的 UDP 数据报。

它解决的是：压缩码流大小不固定、网络每次能承载的数据有限，而且接收端需要知道包的顺序、所属画面时间和分片边界。RTP 提供这些描述，UDP 负责投递数据报；当前程序没有由此获得可靠交付保证。

> 【源码实现】表示当前发送器执行的逻辑；【配置目标】表示程序填写的参数；【背景原理】表示协议解释；【待确认】表示依赖 SDK 或接收端证据的条件。本章未进行编译、抓包、接收解码或延迟测试。

## 8.1 先把四层包装分清楚

【背景原理】Annex B 是一种用起始码分隔 NAL 的字节流组织方式。RTP/H.265 负载则有自己的 NAL/分片结构。网络传输需要把前一种组织转换为后一种，而不是机械地给每段原始字节加一个 UDP 头。

```text
SDK 有效数据：Annex B 起始码 | H.265 NAL 头 | NAL 内容
小 NAL RTP：RTP 头 | 原 NAL 头 | 原 NAL 内容
大 NAL RTP：RTP 头 | FU 负载头 | FU 头 | 该段 NAL 内容
网络承载：IPv4 头 | UDP 头 | RTP 头及负载
```

这里的 FU（Fragmentation Unit，分片单元）把一个过大的 NAL 分成多个 RTP 包。它与编码器切片是两个层次：切片由编码器决定编码结构，FU 只把现有 NAL 字节拆开传输。

【源码实现】应用只手工构造 RTP 和 H.265 FU；`socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP)` 及 `sendto()` 把 UDP/IP 封装交给操作系统。源码没有自行构造以太网或无线帧。

## 8.2 从 SDK pack 中识别一个 NAL

### 起始码为什么去掉，哪里需要再确认边界

`processStream()` 将 `addr + offset`、`len - offset` 交给 `sendPacket()`。后者依次执行：

1. 输入长度小于 4 时返回。
2. 检查开头是 `00 00 00 01` 还是 `00 00 01`。
3. 指针跳过相应的 4 或 3 字节，长度随之减少。
4. 从 H.265 NAL 第一个字节提取类型：`(byte0 >> 1) & 0x3f`。

【源码实现】函数要求 Annex B 起始码位于传入区域的开头，不接受其他输入布局；起始码去掉后不会再扫描第二个起始码。它依赖上一章说明的“一个传入区域足以当成一个 NAL”假设。

代码最初的“小于 4 字节”检查不等于剥离起始码后仍有完整的 2 字节 H.265 NAL 头。稳健的接口契约需要检查有效长度、起始码后的头长度以及 SDK pack 是否完整；当前输入是否会触及这些边界尚无运行证据。

### NAL 类型决定内容性质，不等于 I/P/B 分类

当前代码统计类型 32/33/34 为 VPS/SPS/PPS，类型 39/40 为 SEI，将 0/1 计入普通图像类计数，将 19/20/21 一起计入名为 `idr_count` 的计数。

【源码实现】变量名并不精确：类型 21 是 CRA，不能因为被加到 `idr_count` 就把它叫作 IDR。判断一幅图像的具体预测类型，也不能只把所有类型 0/1 NAL 统一称为某种 P 或 B 图像。

理解这一点的目的不是背类型表，而是防止错误统计：一幅图像可能包含多个切片 NAL，参数集也会占用 NAL 数量；统计 NAL 类型无法直接得到图像数量。

## 8.3 包长预算：先确定哪个“长度”受限

### 小 NAL 直接装入，大 NAL 再分片

【配置目标】`rtp_send()` 的 `max_frame_size=1405` 实际传给 `sendPacket()` 作为 **RTP 负载长度上限**。它不是原始图像大小，也不是完整 RTP 包或完整 IP 包大小。

包长预算的意义是：路径允许的 IP 数据报空间，扣除外层头部后，才是本层可用负载。当前代码采用无选项 IPv4、普通 UDP、无扩展/CSRC 的 RTP 头这一假设：

```text
IP 数据报长度 = 20 字节 IPv4 + 8 字节 UDP + 12 字节 RTP + RTP 负载
最大值 = 20 + 8 + 12 + 1405 = 1445 字节
```

【待确认】源码注释把 1445 与 WFB 联系起来，但没有当前链路 MTU 的测量证据。无线隧道、额外封装、IPv6 或 RTP 扩展都会改变预算；这里的算式只解释本发送器的假设，不能证明所有部署路径都不会发生 IP 分片。

【源码实现】起始码去除后的 NAL 长度不超过 1405 时，所有 NAL 类型均走直接发送路径，包括参数集。超过此长度时，只有类型白名单 `0、1、19、20、21` 进入 FU 分片，其余类型走丢弃分支。

因此，“小参数集能发送”与“大参数集会丢弃”可以同时成立。丢弃日志写的是 `non-VCL`，但实际判断是该白名单，未列入的类型不都能由这条日志准确归类。

### FU 怎样让接收器还原原 NAL

【背景原理】H.265 RTP 的 FU 使用类型 49 的负载头以及含 S/E 标志和原 NAL 类型的 FU 头；S 表示首段，E 表示末段。原 NAL 头中的相关字段需要保留以便重建。协议依据见 [RFC 7798 §4.4.3](https://www.rfc-editor.org/rfc/rfc7798#section-4.4.3)。

【源码实现】当前发送器先剥除原 NAL 的 2 字节头，然后每次最多取 `1405 - 3 = 1402` 字节内容。3 字节由 2 字节 FU 负载头和 1 字节 FU 头组成。

若一个去掉起始码后长度为 4000 字节的 NAL 符合白名单，则 3998 字节内容分成 `1402 + 1402 + 1194`，依次装入 3 个 RTP 包。这是理解算法的算例，不是一次真实抓包结果。

| 分片 | FU 的 S/E | RTP 时间戳 | RTP 序号 | RTP Marker |
|---|---|---|---|---|
| 首段 | S=1，E=0 | 与该输入 NAL 相同 | 本段分配一个 | 0 |
| 中间段 | S=0，E=0 | 不变 | 继续增加 | 0 |
| 末段 | S=0，E=1 | 不变 | 继续增加 | 仅当输入的 `is_frame_end` 为真时置 1 |

【源码实现】`g_tx_buffer[0]` 保留原第一字节的 `0x81` 位并填入类型 49；第二字节被固定写成 `1`，而不是复制原 NAL 第二字节。它因此不能视为完整保留任意 LayerId/TID 的通用实现。

【待确认】当前编码器实际是否只输出与该固定头字段相容的码流，应检查 NAL 头。小范围编码器输出可以使这一简化暂时可用，但不能据此推广到其他 H.265 层次/时域配置。

## 8.4 RTP 头如何描述“哪个包、哪幅画面、哪个发送源”

### 序号、时间戳和 SSRC 各回答一个问题

【背景原理】RTP 固定头包含包序号、媒体时间戳和同步源标识 SSRC。序号用于区分同一流的包顺序；时间戳描述媒体时间；SSRC 区分发送源。它们不能互相替代，具体字段依据见 [RFC 3550 §5.1](https://www.rfc-editor.org/rfc/rfc3550#section-5.1)。

【源码实现】`transmit()` 填写一个打包的 12 字节 `RTPHeader`：

| 字段 | 当前取值/计算 | 如何理解 |
|---|---|---|
| 版本及标志 | 第一字节 `0x80` | RTP 版本 2，无扩展/填充/CSRC 列表 |
| PT | 低 7 位为 `0x60`，即 96 | 动态负载类型编号，需要与接收端约定编码映射 |
| Marker | 第二字节最高位 | 当前由 pack 的图像结束信息控制，见下文 |
| 序号 | `htobe16(rtp_sequence++)` | 每次封包调用增加，16 位会回绕；不是图像编号 |
| 时间戳 | `htobe32(rtp_timestamp)` | 同一输入 NAL 的分片保持相同值 |
| SSRC | 固定 `0xDEADBEEF` | 当前硬编码的源标识；多发送源/重启识别需另行设计 |

特别注意，源码注释“`0x60` 是 H265 标志位”不成立。当前 RTSP 示例也使用 PT 96，却映射到 H.264。自定义发送器没有提供 RTSP/SDP 协商，接收端必须通过自己的配置获知这里的 H.265、时钟和封装约定。

### 时间戳为什么乘 9 再除 100

【背景原理】H.265 RTP 使用 90 kHz 媒体时钟；一秒媒体时间对应 90000 个时钟单位。Marker 表示访问单元最后一个 RTP 包，而不是每个 NAL 的末包。见 [RFC 7798 §4.1](https://www.rfc-editor.org/rfc/rfc7798#section-4.1)。

【源码实现】PTS 来自 SDK 返回的 `stream.pack[i].pts`，不是 `sendto()` 时读取的系统时间。代码执行 `pts × 9 / 100`，等价于假设 PTS 单位为微秒后换算：

```text
RTP 时钟值 = PTS × 每秒 RTP tick 数 ÷ 每秒 PTS 单位数
           = PTS_us × 90000 ÷ 1000000
           = PTS_us × 9 ÷ 100
```

若实际相邻图像 PTS 差为 10000 微秒，对应 RTP 差值是 900；这与 100 fps 的理想间隔相容。丢帧时可以出现更大间隔，不应为追求固定差值而改写真实媒体时间。

【待确认】微秒是本代码换算所依赖的单位假设；PTS 起点、生成位置、同图像不同 pack 是否相同，以及是否对应采集时刻，需要配套 SDK 与运行观测确认。RTP 时间戳也不是直接可与接收电脑墙钟相减的端到端延迟值。

【源码实现】直接发送时 Marker 取 `is_frame_end`；FU 分片时仅最后一片且 `is_frame_end` 为真才置位。这比“每片都有 Marker”更接近图像边界，但正确性仍依赖 SDK 结束标志与输入 NAL/pack 边界的契合。

## 8.5 从用户缓冲到 UDP：非阻塞不等于没有排队

### 当前谁复制，谁持有

`rtp_send()` 分配两个各 65536 字节的全局缓冲。大 NAL 的一个分片先被复制到 `g_tx_buffer`，`transmit()` 再把 RTP 头和负载复制到 `g_combined_buffer`，然后调用 `sendto()`。小 NAL 路径也要复制负载到组合缓冲。

【源码实现】`sendmsg()`/`iovec` 方案只存在于注释中，实际执行的是 `memcpy()` 与 `sendto()`。即使以后使用分散/聚集发送，也首先只是减少应用层拼接复制，不能未经核实称为从 Sensor 到网络的端到端零复制。

当前发送调用同步返回后，本轮封包缓冲可被下一次调用复用；SDK 码流则在整个 `processStream()` 消费完后归还。它没有另起线程继续引用这两个全局缓冲。

### 允许立即失败，与保证低延迟是两回事

【配置目标】socket 被设置为 `O_NONBLOCK`，并申请 `SO_SNDBUF = 2 MiB`。前者试图避免发送缓冲满时阻塞取流执行者；后者允许本地吸收一定突发。

内核接受更多排队数据可能降低瞬时失败概率，也可能让旧视频排队更久。缓冲申请值、内核实际采用值、当前排队字节数是三件事，不能用 `2 MiB` 直接计算实测延迟。

【源码实现】`transmit()` 没有检查 `sendto()` 返回值。非阻塞发送发生失败时，本轮没有重试、失败分类或反馈给码率控制的逻辑。因此当前打印计数不能证明内核接受了全部数据报。

成功调用至多证明该调用被本机网络栈接受，不证明对端收到、更不证明解码成功。UDP 的这种边界要求接收侧同时观察序号缺口、完整 NAL/图像和解码结果。

### 现有统计应怎样阅读

| 源码计数 | 实际增加位置 | 不宜使用的解释 |
|---|---|---|
| `frames_sent` | 起始码剥离后，每次 `sendPacket()` 增加 | 实际图像 fps、成功显示帧数 |
| `packets_sent` | 每次调用 `transmit()` 后增加 | 成功发送 RTP 包数 |
| `single_packets` | 不分片路径增加 | 小图像数 |
| `bytes_sent` | 仅 FU 分片路径增加内容与 FU 头字节 | 全部发送字节、完整网络码率 |

要衡量链路，应分别记录图像结束次数、NAL 类型/数量、RTP 尝试数、成功字节、失败原因及主动丢弃数，并避免空样本除零。这里是后续观测设计建议，本任务没有修改统计代码。

## 8.6 与裸 UDP 模式、无线部署和接收端的边界

【源码实现】`stream_mode` 默认值为 1。模式 0 仅在 `transmit()` 中省去 RTP 头；此时上层已经剥离 Annex B 起始码，大 NAL 还可能已改成 FU。把这些 UDP 负载简单拼接，不能自动得到标准 Annex B H.265 文件。

【资料记录】已有部署资料描述无线派生程序先发送到本机 `127.0.0.1:5622`，再由外部 WFB 进程承载。它与本文件硬编码的远端 `192.168.0.2:5622` 是不同部署版本的路径，不能静默替换。资料见 [使用文档（3）](../../hi3516firm/hi3516firm/海思hi3516-hi3519使用文档(3).docx) 的自启动与无线部分。

外部无线纠错、加密和串口 MAVLink 转发不在上述三个发送函数内部。接收端的解包、抖动缓存、解码和显示也没有在这份源码中实现。

【待确认】下一轮应先建立发送源版本与接收配置的对应关系，再核对 PT 映射、NAL 头、FU 重组、时间戳和 Marker。仅确认目的端口有流量，仍不能证明这些协议契约正确。

## 8.7 自查问题与回答要点

1. **为什么同一幅图像可能有很多序号，却只有一个 RTP 时间戳？**
   回答要点：序号区分传输包；图像中的多个 NAL/分片可以共享媒体时刻。还要确认 SDK 对同图像各 pack 的 PTS 定义。
2. **把 1405 调大是否一定提升效率？**
   回答要点：可能减少分片及调用开销，但必须重新核算路径 MTU和外层封装；IP 分片或链路丢弃可能抵消收益。
3. **为什么不能依据 `Frames` 和 `Rate` 日志宣布达到 100 fps、4096 Kbit/s？**
   回答要点：计数边界不是图像，字节统计遗漏小 NAL及头部，发送结果也未检查；目标配置与测量证据不同。
4. **接收端有 UDP 包但无法解码，先检查什么？**
   回答要点：确认运行的是 RTP 还是模式 0、PT/时钟约定、Annex B 到 NAL 的转换、参数集和可随机接入图像、FU/Marker 边界，再定位网络丢包与接收器状态。
