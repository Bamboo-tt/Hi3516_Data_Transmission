# 08 自定义 RTP 与 UDP 发送

[学习入口](README.md) · 上一章：[VENC 编码与码流生命周期](07_VENC编码与码流生命周期.md) · 下一章：[RTSP 会话与媒体分发](09_RTSP会话与媒体分发.md)

现在应用已经从 VENC 借到一段 H.265 字节。它大小不固定，而网络每个数据报的空间有限；接收端还需要知道哪些包相邻、哪些片段属于同一个 NAL、它们对应什么媒体时刻。A 用 RTP 描述这些关系，再交给 UDP 发送。

**UDP**（用户数据报协议）以独立消息传输字节，但不保证消息必达或按发送顺序到达。**RTP**（实时传输协议）在媒体字节外补上序号、时间戳和源身份，使接收器能够识别这些关系；添加 RTP 头本身不会把 UDP 变成可靠传输。两层分工可对照 [RFC 3550 §1](https://www.rfc-editor.org/rfc/rfc3550#section-1)。

本章沿 [new_main2.c](../../hi3516firm/new_main2.c) 的 `processStream()` → `sendPacket()` → `transmit()` 推导一份内容怎样变成网络包。所有算例均为解释算法构造，未进行真实抓包、接收解码或延迟测量。

## 8.1 先确定输入里有什么，再决定给网络什么

`processStream()` 传入的不是原始 YUV，而是 `addr + offset` 开始、长度 `len - offset` 的压缩数据。A 要求这段数据开头带 Annex B 起始码：`00 00 01` 或 `00 00 00 01`。

起始码用于在连续字节流中找出 NAL 边界。RTP/H.265 的负载有自己的组织规则，所以发送器先去掉起始码，再决定把完整 NAL 或 NAL 的一部分装进 RTP。它没有重新编码像素。

```text
输入有效区：Annex B 起始码 | H.265 NAL头 | NAL内容
短 NAL：    RTP头 | 原NAL头 | 原NAL内容
长 NAL：    RTP头 | FU负载头 | FU头 | 本段NAL内容
发往网络：  IPv4头 | UDP头 | 上面的RTP包
```

RTP 头与 FU 由应用构造，UDP/IP 头由 socket 网络栈构造。编码器切片和 FU 也不同：切片改变编码结构，FU 只是把已经形成的 NAL 字节分段传输。

`sendPacket()` 先检查输入长度不少于 4，再识别开头的 3/4 字节起始码。它只做一次剥离，不寻找第二个 NAL，也不拼接跨 pack 的 NAL。因此它依赖上一章的输入边界契约；最初的 4 字节检查也不能替代“剥离后仍有完整 NAL 头”的检查。

## 8.2 NAL 头怎样告诉发送器这是什么内容

H.265 的 2 字节 NAL 头包含禁止位、类型、层编号和时域编号信息。当前源码只直接提取类型及第一字节的部分保留位。以下为用于解释的代码节选：

```c
/* pack_data 已跳过 Annex B 起始码。类型占第一字节中间的 6 位。 */
uint8_t nal_type_hevc = (pack_data[0] >> 1) & 0x3F;
uint8_t nal_bits_hevc = pack_data[0] & 0x81;
```

类型能区分参数集、SEI、图像切片等内容，却不能直接替代整幅图像的全部 I/P/B 判断。当前统计将 32/33/34 分别记作 VPS/SPS/PPS，39/40 记作 SEI，0/1 记入普通图像类计数，19/20/21 一起记入 `idr_count`。

这里需要按内容理解变量：类型 21 是 CRA，不会因为计数名叫 IDR 就改变含义；同一幅画面还可能出现多个切片 NAL，因此 NAL 数量与图像数量仍然不同。

接收器既需要图像切片，也可能依赖先前收到的参数集和参考图像。发送器不能只根据“这个包不含像素”就断定可以安全丢弃它。

## 8.3 一个 NAL 放不下时，怎样决定分成几包

### 1405 限制的是 RTP 负载

`rtp_send()` 将 `max_frame_size` 设为 1405，传到 `sendPacket()` 后，它实际限制的是 RTP 负载长度。变量名里的 frame 不能解释成一幅原始图像。

先说明包长预算的意义：路径能接纳的 IP 数据报空间，扣除头部后才是媒体负载空间。当前算式假定无选项 IPv4、普通 UDP、无 CSRC/扩展的 RTP：

```text
IP数据报 = 20字节IPv4头 + 8字节UDP头 + 12字节RTP头 + RTP负载
当前最大值 = 20 + 8 + 12 + 1405 = 1445字节
```

**MTU**（最大传输单元）限制链路能够承载的报文大小；路径 MTU 还要考虑沿途最小的限制。这里比较的是 IP 数据报长度，目的是让它在选定路径上无需 IP 分片。源码注释把 1445 与 WFB 相联系，但这只是本发送器采用的预算，不能替代实际路径 MTU 确认。额外隧道封装、IPv6 或 RTP 扩展都会改变可用空间。

去掉起始码后的 NAL 不超过 1405 字节时，当前代码对所有类型直接发送。超过上限时，只对白名单 `0、1、19、20、21` 做 FU 分片，其他类型进入丢弃分支。日志称其为 non-VCL，但实现按白名单判断，不能用日志字样精确概括所有被丢类型。

### 同一个 4000 字节 NAL 的完整算例

FU 是分片单元。H.265 FU 使用类型 49 的负载头，附上含首段 S、末段 E 和原始类型的 FU 头，供接收器重建原 NAL。通用格式见 [RFC 7798 §4.4.3](https://www.rfc-editor.org/rfc/rfc7798#section-4.4.3)。

假设已经去掉起始码的 NAL 长 4000 字节，类型在当前白名单内。原 NAL 的 2 字节头不作为普通内容重复发送，而由 FU 信息表达；于是内容还剩 3998 字节。当前每包占 3 字节 FU 头部，内容上限为：

```text
每片内容上限 = 1405 - 3 = 1402字节
原NAL内容     = 4000 - 2 = 3998字节
分片内容     = 1402 + 1402 + 1194
```

再设本例第一包序号为 2000，输入 PTS 为 1,000,000 微秒，且这个 NAL 是所属图像的最后一个 NAL。按当前字段计算将得到：

| 包 | 内容字节 | FU字节 | RTP负载 | 完整RTP包 | IP数据报 | S/E | 序号 | RTP时间戳 | Marker |
|---|---:|---:|---:|---:|---:|---|---:|---:|---:|
| 第一包 | 1402 | 3 | 1405 | 1417 | 1445 | 1/0 | 2000 | 90000 | 0 |
| 第二包 | 1402 | 3 | 1405 | 1417 | 1445 | 0/0 | 2001 | 90000 | 0 |
| 第三包 | 1194 | 3 | 1197 | 1209 | 1237 | 0/1 | 2002 | 90000 | 1 |

这里一个 NAL 变成三包，序号逐包增加，媒体时刻保持相同。若这个 NAL 不是图像最后一个，第三包仍为 E=1，但 Marker 应为 0：**NAL 分片结束与图像访问单元结束不是同一个边界。**

接收规则也可以用这三包反向理解：遇到 S=1 开始收集，按 RTP 序号检查中间片段，再用 FU 中的原始类型等信息恢复 NAL 头，直到 E=1 才得到这个 NAL 的末段。如果 2001 丢失，仅收到 2000 和 2002，E=1 仍不能证明内容完整；缺失部分不会由 Marker 自动补回。这是接收端需要承担的重组工作，本项目没有提供该接收实现。

### 当前 FU 头的简化条件

实际代码以 `nal_bits_hevc | (49 << 1)` 构造第一字节，第二字节直接写为 `1`，第三字节写原类型，并按位置加上 S/E 位。

固定第二字节没有完整保留原 NAL 的 LayerId/TID 字段，因此不能把它视为支持任意 H.265 层次/时域设置的通用封包器。当前编码器是否始终输出与这项简化相容的头字段，需要检查实际码流。

大参数集或不在白名单中的大 NAL 也不会走这套分片。将程序推广到其他编码配置时，应先明确这些输入限制，而不是只扩大 UDP 缓冲。

## 8.4 给三个包加上顺序、时间与源身份

RTP 的序号回答“这是该源的第几个包”，时间戳回答“对应哪个媒体时刻”，SSRC 回答“来自哪个同步源”。字段定义见 [RFC 3550 §5.1](https://www.rfc-editor.org/rfc/rfc3550#section-5.1)。三者分工不同，丢包与帧节奏也应分别观察。

当前 `transmit()` 使用打包的 12 字节 `RTPHeader`：

| 字段 | 当前代码 | 本例与使用含义 |
|---|---|---|
| 版本/标志 | 第一字节 `0x80` | 版本 2，无填充、扩展和 CSRC 列表 |
| PT | `0x60` 的低7位，即96 | 动态类型编号；接收端需要约定这里映射 H.265 |
| Marker | 第二字节最高位 | 由输入 `is_frame_end` 及末分片条件决定 |
| 序号 | `htobe16(rtp_sequence++)` | 本例2000、2001、2002；16位自然回绕 |
| 时间戳 | `htobe32(rtp_timestamp)` | 本例三包都是90000 |
| SSRC | 固定 `0xDEADBEEF` | 硬编码源身份，多个发送源及重启场景需另行设计 |

`htobe16/32` 将多字节整数转为网络所需的大端顺序，让接收器不依赖发送 CPU 的字节序。

PT=96 不自带 H.265 含义。B 也使用 96，却通过 SDP 映射到 H.264。源码里“0x60 是 H265 标志位”的注释应按这一关系纠正；A 没有 RTSP/SDP 交互，映射需要由接收配置等外部约定提供。

### PTS 为什么乘 9 再除 100

H.265 RTP 使用 90 kHz 时钟，Marker 指向访问单元最后一包，参见 [RFC 7798 §4.1](https://www.rfc-editor.org/rfc/rfc7798#section-4.1)。当前代码不是每发一包就读取墙钟，而是从 SDK pack 取得 `pts`：

```text
RTP时钟值 = PTS × 每秒RTP tick数 ÷ 每秒PTS单位数
若PTS单位为微秒：
          = PTS_us × 90000 ÷ 1000000
          = PTS_us × 9 ÷ 100
```

本例的 1,000,000 微秒由此变成 90000。假设下一幅的 PTS 是 1,010,000 微秒，则变成 90900，差值 900 与理想 100 fps 相容；这不意味着每幅都必然按该间隔实际产出。

微秒是当前代码换算所依赖的单位。SDK 在哪里生成 PTS、同图像的多个 pack 是否相同、它与曝光/采集时刻的关系，仍需配套接口资料和运行证据。也不能拿 RTP 时间戳直接减接收电脑的墙钟，宣布端到端延迟。

A 的直接发送路径用 `is_frame_end` 决定 Marker；分片路径只有最后一片可能置 Marker。这个设计将 SDK 的图像结束语义传向协议层，所以仍需核对 pack/NAL 边界和结束标志的契合。

## 8.5 三个包怎样离开用户态，以及何时能复用缓冲

`rtp_send()` 建立 UDP socket，目的地址固定为 `192.168.0.2:5622`，再分配两个各 65536 字节的全局缓冲。

对本例的每个 FU，程序先把内容复制到 `g_tx_buffer` 的 3 字节头之后；`transmit()` 再把 RTP 头和负载复制到 `g_combined_buffer`，最后调用 `sendto()`。小 NAL 省掉分片构造，但仍会复制到组合缓冲。源码中的 `sendmsg/iovec` 方案处于注释状态。

当前没有另一个发送线程继续引用这两个缓冲；本次同步系统调用返回后，应用可以构造下一包。SDK 原码流则在 `processStream()` 整轮消费完后归还。减少一次应用拼接复制与端到端零复制是不同目标，不能从某个发送接口名称推导全链路结论。

### 非阻塞改变的是等待策略

socket 配置了 `O_NONBLOCK`，并申请 `SO_SNDBUF=2 MiB`。前者希望发送空间不足时及时返回，避免持有码流一直等待；后者希望吸收一定突发。申请容量、系统实际采用容量、运行中的已排队字节数并不相同。

更大的排队空间可能减少暂时失败，也可能积压旧视频。非阻塞只是将“等到能发”改成“本轮可能失败”，并没有保证成功或限制所有后续队列的时延。

当前 `transmit()` 不检查 `sendto()` 的返回值，也没有重试或网络反馈码率控制。发送调用成功至多说明本机接受数据报；对端收到、完整重组和成功显示仍各需要独立证据。

### 现有计数为什么不能直接作为吞吐结论

| 计数 | 实际增加位置 | 适合如何解释 |
|---|---|---|
| `frames_sent` | 剥离起始码后的每次 `sendPacket()` | 被处理的输入区域次数，通常按NAL假设处理，不是图像fps |
| `packets_sent` | 每次调用 `transmit()` 后 | 发送尝试数，不区分系统调用成功与否 |
| `single_packets` | 无需FU的路径 | 直接封包次数，不是小图像数 |
| `bytes_sent` | 仅FU路径累计内容和FU头 | 漏掉小NAL和RTP/UDP/IP头，不能代表总网络码率 |

例如本例会增加一次 `frames_sent`、三次 `packets_sent`，并累计 4007 个 FU 负载字节；网络上三个 IP 数据报合计是 4127 字节。若换成短 NAL，现有 `bytes_sent` 不增加。这个差异来自统计位置，不需要假设网络已经发生丢包。

真正观察链路应区分图像结束次数、NAL数、RTP尝试/成功/失败、主动丢弃和成功字节，并处理空样本除零。这里解释的是应如何取证，没有修改计数代码。

## 8.6 发送器之外还要满足什么条件

`stream_mode` 默认是 1。若改为 0，`transmit()` 仅省去 RTP 头；上层已经去掉 Annex B 起始码，大 NAL 还可能被改成 FU。因此将模式0的 UDP 负载直接拼接，并不会自动得到标准 Annex B 文件。

[历史使用文档（3）](../../hi3516firm/hi3516firm/海思hi3516-hi3519使用文档(3).docx) 描述无线派生程序先发 `127.0.0.1:5622`，再交外部 WFB。它不是当前源文件发远端地址的路径。无线纠错、加密和串口 MAVLink 转发不在上述三个函数内，接收端的抖动缓存、重组、解码与显示也在应用之外。

实际验证宜先对齐运行版本和接收约定，再查看 RTP 字段、FU 重组、参数集及图像结束。只有目的端口收到流量时，仍无法排除类型映射、NAL边界或解码依赖不匹配。

## 8.7 自查题

1. 本例4000字节NAL为什么拆成三包？若把1405调大，需要重新确认哪个长度预算？
2. 三个分片为什么序号不同但时间戳相同？若NAL不是图像末尾，E与Marker分别是什么？
3. 根据本例计算现有 `bytes_sent` 的增量和三个IP数据报总字节数，解释为何它们不同。
4. 对端有UDP流量却不能解码，怎样先区分模式、封装约定、重组和图像依赖，而不直接认定Sensor故障？

### 参考答案

1. 去原2字节NAL头后剩3998字节，每片容纳1402字节，得到1402、1402、1194。调整上限时应从路径IP数据报预算扣除实际外层头部和封装，避免误把负载长度当MTU。
2. 序号描述传输包，时间戳描述媒体时刻。该NAL末片仍E=1，但如果图像还有后续NAL，Marker=0；下一图像的时间戳差值还要由可信PTS推导。
3. 增量为3998+3×3=4007字节；IP总量1445+1445+1237=4127字节，相差三组RTP/UDP/IP头共120字节。实际统计还漏掉所有短NAL，且未确认sendto成功。
4. 先确认RTP模式还是省RTP头的模式0，再确认H.265/PT/时钟约定、起始码与NAL范围、FU头及结束标志，最后核对参数集、可随机接入图像和包缺失。编码正常后才有依据把问题继续定位到协议或接收侧。
