# 03 板级资源与 Sensor 适配

本章处于“系统已经能运行用户程序”与“媒体流水线开始接收图像”之间。Sensor 是把光转换成像素信号的图像传感器；它需要供电、时钟和寄存器配置，才会按接收端期待的格式输出数据。

先抓住两条并行通道：应用和 ISP 框架通过控制通道改变 Sensor 的工作状态；Sensor 通过图像通道持续输出像素。控制函数没有逐帧搬运原始图像，图像链路就绪也不代表自动曝光已经正确工作。

返回 [学习首页](README.md)。主线 A 指 [new_main2.c](../../hi3516firm/new_main2.c)，主线 B 指 [rtsp_4m/sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c)。下文 SC500AI 100fps 适配主要对应 A，不能直接移植为 B 的当前配置结论。

## 3.1 先把“能控制”与“能收到图像”分开

**I²C**是低速控制总线，用于写 Sensor 寄存器；寄存器是器件内部保存控制参数的地址单元。**MIPI CSI 图像接口**用于高速传输像素，**lane**是其中承载数据的高速通道。两者速度、用途和故障表现不同。

```mermaid
flowchart LR
    APP[应用选择模式与注册适配] --> ISP[ISP 控制框架和 AE/AWB 库]
    ISP --> CB[Sensor 回调与寄存器描述]
    CB --> CTL[I2C 驱动与控制线]
    CTL --> SNS[Sensor]
    CLK[板级供电 时钟 复位] --> SNS
    SNS -->|MIPI 像素数据| RX[MIPI RX 与 VI 图像通路]
    RX --> PIX[后续图像处理]
```

图中控制框架与像素处理是两个职责视角；不表示每一帧都先进入用户态回调再通过 I²C 发送给 VI。

【背景原理】正常启动至少需要这些条件互相匹配：供电稳定，复位时序正确，输入时钟正确，引脚复用正确，I²C 地址和总线正确，Sensor 输出模式与 MIPI 接收配置一致。寄存器能写成功，只证明控制通道前进了一步；它不能证明 lane 接线、像素格式和帧时序都匹配。

【源码实现】A 的 `set_vi_sns_info()`选择 `bus_id=0`、时钟源 0、复位源 0；`vi_init()`打开 `/dev/ot_mipi_rx`，通过 `ioctl` 下发 lane 分组、Sensor 时钟/复位、MIPI 时钟/复位与接收属性。`ioctl`是应用向设备驱动提交专用控制请求的接口。

【待确认】这些编号怎样对应当前板卡的实际连接，要结合实际电路、内核配置及加载参数确认。源码注释中的某个 I²C 控制器名称不是板级测量结果。[pin_mux.c](../../hi3516firm/pin_mux.c)是引脚复用相关的内核侧代码片段，不能因为它在同一目录就认为 `new_main2.c` 会自动执行其中的寄存器写入。

## 3.2 一个模式必须同时约束 Sensor 和接收端

**RAW Bayer**是 Sensor 输出的原始颜色采样排列，每个像素位置先记录一种颜色分量，后续 ISP 再恢复和处理完整图像。`RAW10` 表示图像接口上的原始采样位宽为 10 bit；它不等于用户态 RGB 图像，更不等于 H.265 数据。

【配置目标】A 中的 `SENSOR0_TYPE` 固定为 `SC500AI_MIPI_2M_100FPS_10BIT`，MIPI 属性配置 4 lane、1920×1080、RAW10；ISP 公共属性也设置为 1920×1080、100fps、非 WDR。**WDR**是宽动态范围模式；这里使用 `OT_WDR_MODE_NONE`，所以不要把适配文件中其他 WDR 分支当作本主线启用的功能。

【源码实现】[sc500ai_cmos.c](../../学习文件/smart_sc500ai_100/sc500ai_cmos.c)的 `g_sc500ai_info[].mode_tbl`保留 5M30 与 2M100 两个线性模式，2M100 模式的尺寸、最大帧率和时序常量来自 [sc500ai_cmos.h](../../学习文件/smart_sc500ai_100/sc500ai_cmos.h)。`cmos_isp_global_init()`把默认状态设为 2M100，并初始化帧行数与寄存器描述缓存。

这不是只改一个“fps=100”字段：`cmos_isp_set_image_mode()`按尺寸、帧率与 WDR 条件寻找模式；`cmos_isp_init()`再按选中的模式进入具体寄存器初始化函数。接收端与 Sensor 两侧的描述必须最终指向同一套输出行为。

### 帧率、曝光和行时序为什么互相限制

【背景原理】一帧时间包含有效像素读出及行、场消隐等时序。可以用“帧周期约等于一帧总行数乘以行周期”理解帧率的来源，但具体寄存器单位必须服从 Sensor 手册和适配代码，不能把所有 `full_lines` 都直接解释为可见图像高度。

【源码实现】2M100 的基础 `VMAX` 常量是 1305，而适配状态中的 `fl_std`使用该值左移一位。`cmos_fps_set()`先按 `lines × max_fps / fps`求新的 `vmax`，再更新 `VMAX` 寄存器描述、`fl_std`、曝光上限及行时间等信息。这说明帧率请求会改变时序约束，也说明不能把 1080 行画面高度等同于一帧总时序行数。

【配置目标】100fps 的名义帧周期是 10ms。A 在 `true_isp_init()`中把自动曝光时间上限设为 10000μs，意图避免曝光持续增长挤占目标帧率的时间预算。但真实帧率还受 Sensor 时序、照明、框架策略、后级吞吐和参数覆盖影响；源码中的目标值不能替代帧时间戳测量。

【资料记录】2M100 初始化函数打印包含 `27MInput`、`4lane`、`792Mbps` 的文字。它表示代码作者给该模式的标签，不能证明当前板上实际输入时钟和 lane 速率已测得这些数值。

## 3.3 应用注册的是控制契约，算法由框架调度

**回调**是把函数地址交给另一个模块，让后者在适当阶段调用。这里需要注册的原因很直接：ISP 和自动控制算法面对多种 Sensor，不应把每种器件的曝光寄存器、增益编码和模式表硬编码在算法内部。

**AE（自动曝光）**决定曝光时间与增益等，使图像亮度接近目标；**AWB（自动白平衡）**估计和校正光源造成的颜色偏差。当前应用使用厂商框架和算法库，适配层负责告诉这些算法“这个 Sensor 能怎么调、应该怎样写”，并提供初始参数。

【源码实现】A 的 `true_isp_init()`先取得 `g_sns_sc500ai_obj`，准备 AE、AWB 库标识，再依次执行：

1. 调用对象的 `pfn_register_callback`，登记当前 Sensor 对 ISP、AE、AWB 暴露的函数。
2. 通过 `pfn_set_bus_info`保存 I²C 总线号。
3. 调用 `ss_mpi_ae_register()`、`ss_mpi_awb_register()`登记所用算法库。
4. 完成 ISP 内存、公共属性和初始化，最后创建线程运行 `ss_mpi_isp_run()`。

这两种“注册”不能混为一谈：Sensor 注册告诉框架如何控制器件；算法库注册告诉 ISP 使用哪套自动控制算法。

### 回调表怎样连到实际代码

`g_sns_sc500ai_obj`把对象操作映射到 `cmos_register_callback()`等函数。后者构造三组回调，交给 [sensor_common.c](../../学习文件/smart_sc500ai_100/sensor_common.c)的 `cis_register_callback()`；该函数创建 Sensor 状态，再分别调用 `ot_mpi_isp_sensor_reg_callback()`、`ot_mpi_ae_sensor_reg_callback()`、`ot_mpi_awb_sensor_reg_callback()`。

| 框架需要回答的问题 | 本地适配函数 | 返回或改变的内容 |
|---|---|---|
| 当前请求适合哪个模式，如何开始输出？ | `cmos_isp_set_image_mode()`、`cmos_isp_init()` | 模式状态及初始化寄存器配置 |
| 按该模式怎样限制帧率和曝光？ | `cmos_get_ae_default()`、`cmos_fps_set()` | AE 初值、时序及曝光范围 |
| AE 算出的曝光和增益怎样落实？ | `cmos_inttime_update()`、`cmos_gains_update()` | 更新寄存器描述缓存中的数据 |
| 哪些寄存器需要按时更新？ | `cmos_isp_get_sns_regs_info()` | 寄存器地址、数值、更新标志和生效延迟信息 |
| AWB 用什么初始标定参数？ | `cmos_awb_get_default()` | 参考色温、初始增益、颜色相关参数表 |

【资料记录】本地 [ISP 开发参考](../../hi3516cv610/海思Hi3516CV610R001C01SPC020/ReleaseDoc/zh/01.software/board/ISP/ISP%20开发参考.pdf)§1.2、§2.3.53、§3.5.1.4说明：初始化阶段获取 Sensor 差异化参数；运行阶段由 ISP 控制框架调度算法并通过回调调节器件；模式改变时可能重新调用 Sensor 初始化回调。它支持上述职责划分，但本工作区没有闭源库源码，不能补出每个回调相对某次中断的精确内部调用栈。

## 3.4 初始化写寄存器与运行时寄存器更新是两条路径

【源码实现】第一次配置 Sensor 时，`cmos_isp_init()`调用 `cis_i2c_init()`准备 I²C 接口，再进入 [sc500ai_sensor_ctrl.c](../../学习文件/smart_sc500ai_100/sc500ai_sensor_ctrl.c)的 `sc500ai_linear_2m100_10bit_init()`。该函数选取 [sc500ai_cfg.h](../../学习文件/smart_sc500ai_100/sc500ai_cfg.h)中的 `sc500ai_linear_2m100_10bit`表。

`sc500ai_reg_init()`先写软件复位，短暂等待，再逐项写入模式寄存器表；之后写入已有动态寄存器描述中的初值，最后写启动输出的寄存器。这解释了“模式表”与“AE 动态状态”为什么都要存在：前者建立工作模式，后者在该模式下不断更新曝光和增益。

在普通 I²C 分支中，`cis_i2c_init()`按保存的总线号打开 `/dev/i2c-N`，设置从设备地址；`cis_write_reg()`把寄存器地址和数据编码到字节缓冲区后调用 `write()`。源码把 0x60 右移一位用于从地址设置，因此需要区分器件资料中的地址表达和 Linux 接口采用的地址表达，不能把它们直接当作不同器件。

### 动态曝光通常先写“寄存器描述”，不是立即自行写总线

【源码实现】`cmos_inttime_update()`及 `cmos_gains_update()`把算法结果拆成器件要求的高低位，并修改 `sns_state->regs_info[0].i2c_data[]`。这些函数主体并没有为每次调整直接调用 `cis_write_reg()`。

随后 `cmos_isp_get_sns_regs_info()`交出当前描述。它在首次调用时准备总线、地址和延迟信息，之后把本次数据与 `regs_info[1]`保存的上次数据比较，仅把发生变化的项标记为需要更新；最后复制当前描述，保存下一次比较所需的快照。

【资料记录】ISP 参考中的 `pfn_cmos_get_sns_reg_info`用于向内核态传递 AE 寄存器配置。这说明动态调整还要经过框架和驱动按时下发，不能把“回调改了内存里的 data 字段”视为“Sensor 已在当前帧生效”。本地描述里曝光项和 VMAX 项的 `delay_frame_num`也并非全部相同。

【待确认】实际生效帧、总线错误处理、驱动调度和当前库版本必须通过匹配资料、运行日志或受控测量确认。这里不虚构底层写入次数或精确中断时机。

### 读回和退出也必须有真正实现

【源码实现】本地 `cmos_read_register()`与 `cis_read_reg()`只是返回成功的占位函数，没有完成硬件寄存器读取。因此对象中有 `pfn_read_reg`字段不等于应用已经具备可用的寄存器回读能力。

Sensor 退出回调 `cmos_isp_exit()`调用 `cis_i2c_exit()`关闭 I²C fd；解除注册还会释放状态对象。主线 A 本身没有形成调用这些退出步骤的完整回收路径，故不能因为适配层存在退出函数，就声称进程退出时必然走到了它。

同样，`cmos_isp_init()`没有检查具体模式初始化函数的返回值，就继续设置 `sensor_state->init=TD_TRUE`。这是一条清晰的学习边界：内存状态被置位不等于所有寄存器已经写成功，更不等于接收到了完整图像。

## 3.5 PQ BIN 在模式之后补充画质参数

Sensor 寄存器模式决定“怎样产出原始像素”；**ISP（Image Signal Processor，图像信号处理器及其控制软件）**负责把这些原始采样处理成可用图像。**PQ BIN**保存调校后的一组图像质量参数，不能替代 Sensor 供电、时钟、MIPI 配置或模式寄存器表。

【源码实现】A 的 `main()`先调用 `true_isp_init()`，再调用 `isp_calibration_load_bin()`。后者读取当前工作目录的 `sc500ai_1080P_100.bin`，启用 ISP 和 3DNR 参数导入，其中 3DNR 指利用图像时空关系进行降噪的处理类别，具体算法由平台实现。

函数通过 `OT_PQ_BIN_ImportBinData()`把文件内容交给配套 PQ 库，应用没有在源码中逐字段解析这个 BIN。文件名表达了预期 Sensor、分辨率与帧率场景，不是文件内部版本和全部参数内容的证明。

【待确认】因为曝光限制设置发生在导入之前，若 BIN 中包含相关配置，导入可能改变前面的结果；ISP 与 3DNR 其他设置也有同类问题。应核对 BIN 配套版本、导入返回值和最终参数回读，才能陈述实际生效值。当前源码只打印错误后返回，主流程仍会继续启动 VPSS、VENC，不能把应用继续运行当作调校文件加载成功。

## 3.6 B 的 Sensor 选择必须独立阅读

【源码实现】B 从 `SENSOR0_TYPE`开始，通过 `sample_comm_vi_get_default_vi_cfg()`生成 VI 与 ISP 参数，再由 `sample_comm_vi_start_vi()`内部启动 ISP。`sample_comm_vi_register_sensor_lib()`和 `sample_comm_isp_get_sns_obj()`负责找到相应 Sensor 对象并注册，而不是固定使用 A 的 `g_sns_sc500ai_obj`。

【配置目标】[Makefile.param](../../sample_source/Makefile.param)默认选择 SC4336P 4M30；外层构建可以覆盖这一宏。B 的 VPSS 输出配置是主通道 2560×1440、子通道 1024×768，两路编码目标 30fps。它们属于后级输出配置，也不能反向证明物理 Sensor 一定以完全相同的有效分辨率输出。

【待确认】B 已有二进制使用的实际宏、链接的 Sensor 库版本和板上 Sensor 均需要构建记录与运行证据确认。`学习文件`里的 SC500AI 2M100 源码，与 SDK 自带 `libsns_sc500ai.a`之间的版本关系目前也不能直接等同。

## 3.7 自查问题

1. **I²C 写入成功，为什么仍可能完全没有图像？**

   回答要点：控制和数据是两条通道。继续检查模式是否开始输出、时钟、复位、MIPI lane、RAW 位宽与 VI 时序匹配，不能直接跳到网络层排查。

2. **AE 回调更新 `i2c_data[].data` 后，Sensor 是否立即改变曝光？**

   回答要点：这是更新寄存器描述；还需框架取得描述、按更新标志和延迟提交给驱动，并由 Sensor 在其时序约束下生效。精确时机要有 SDK 和板端证据。

3. **注册 Sensor 回调与注册 AE/AWB 库有什么区别？**

   回答要点：前者提供器件差异化控制和初值，后者选择算法实现。应用没有因此实现完整自动曝光或白平衡算法。

4. **曝光上限设为 10ms，为何仍不能声称已经稳定 100fps？**

   回答要点：它是配置目标，后续 PQ 导入可能覆盖；Sensor 时序、输入条件、后级负载也会影响实际输出。应分别检查最终参数、帧计数和时间戳。
