# 10 并发与资源退出：让每个使用者先停下，再回收资源

[返回学习导航](README.md) · [下一章：部署与分层验证](11_部署与分层验证.md)

前面已经建立了“硬件持续产出码流，应用取出后交给网络”的主线。本章解决另一个问题：当这些工作同时进行，或者程序准备退出时，谁还在使用哪一块内存、哪一个通道、哪一个连接？

学习并发首先要找出执行者与资源所有者。多建一个线程并不会自动提高吞吐；如果消费者来不及处理，新增的队列可能只是把丢包变成更久的等待。

## 10.1 两条应用各有谁在执行

### 10.1.1 自定义 RTP：主线程发送，ISP 线程运行框架

【源码实现】[new_main2.c](../../hi3516firm/new_main2.c) 的 `main()` 依次完成配置、SYS/VI/ISP/VPSS/VENC 初始化与绑定，然后进入 `rtp_send()`。这个发送循环就在主线程中，未再创建一个网络线程。

`true_isp_init()` 创建 `sample_comm_isp_thread()`；后者调用 `ss_mpi_isp_run()`。它运行的是厂商 ISP 框架所需的用户态工作，不是由应用线程逐像素完成 ISP 图像处理。媒体硬件及其缓冲区仍在持续推进图像通路。

| 执行者 | 正在做什么 | 主要依赖的资源 | 当前停止路径 |
|---|---|---|---|
| 主线程 | 查询 VENC、取流、封装 RTP、调用 `sendto()`、归还码流 | VENC chn0、SDK 码流地址、两个发送缓冲区、UDP socket | `SIGINT` 改标志后跳出循环 |
| ISP 工作线程 | `ss_mpi_isp_run()` | ISP pipe、已注册 Sensor/AE/AWB、SDK 内部资源 | 当前主函数没有显式 ISP exit 与 join |
| 媒体硬件/驱动 | 采集、处理、编码及缓冲流转 | VI、VPSS、VENC、VB 等 | 当前主函数没有完整停止和销毁链路 |

因此“发送循环结束”和“整个媒体系统有序停止”是两个不同事件。当前 `rtp_send()` 返回后直接执行 `exit(0)`，不能把进程结束当成应用已经验证了所有硬件资源的释放顺序。

### 10.1.2 RTSP：主线程管理退出，取流线程兼做网络工作

【源码实现】[sample_rtsp.c](../../sample_source/rtsp_4m/sample_rtsp.c) 的主线程初始化服务器和媒体系统，随后在 `sample_venc_rtsp()` 中等待退出标志。`venc_start_get_stream()` 创建 `venc_get_stream_proc()`。

这个 worker 同时负责两路编码码流的获取，以及主码流的 RTSP/RTP 分发。其 `select()` 等待的是 **VENC 文件描述符**，不是独立网络事件线程。

此外，`sample_comm_vi_start_vi()` 会经过公共 ISP 辅助代码创建 ISP 运行线程，所以完整执行者是“主线程 + 取流/网络 worker + ISP 运行线程”，不能漏掉第三者。公共链路见 [sample_comm_vi.c](../../sample_source/common/sample_comm_vi.c) 与 [sample_comm_isp.c](../../sample_source/common/sample_comm_isp.c)。

```text
主线程：媒体初始化 → 启动 worker → 等待退出请求 → 停 worker → 回收媒体资源
                           │
取流 worker：select(VENC fd) → GetStream → RTSP 封装/分发/网络事件 → ReleaseStream

ISP 线程：                         ISP Run ─────────→ ISP exit 后返回 → join
媒体硬件：                 持续采集 → 处理 → 编码（不由上面的循环逐帧调用）
```

## 10.2 一个“线程开关”不足以表达完整生命周期

### 10.2.1 创建成功、请求停止、执行结果、回收完成

线程创建是向系统请求一个执行者；停止请求是告诉它应结束工作；执行结果说明它为什么结束；`pthread_join()` 则等待该 joinable 线程结束并完成回收。这四件事应该分别判断。`pthread_create()` 返回 0 表示创建成功，非零值表示创建错误；已经自行返回的 joinable 线程仍需要 join。背景依据见 [pthread_create](https://man7.org/linux/man-pages/man3/pthread_create.3.html) 和 [pthread_join](https://man7.org/linux/man-pages/man3/pthread_join.3.html)。

| 状态 | 回答的问题 | 不能由它推出什么 |
|---|---|---|
| 创建成功 | 是否存在需要管理的线程实例？ | 不能推出业务初始化成功 |
| 已请求停止 | 管理者是否希望 worker 结束？ | 不能推出 worker 已经返回 |
| 已结束及结果 | 正常结束、初始化错误，还是运行错误？ | 不能推出 join 已经完成 |
| 已 join | 管理者是否回收了该线程？ | 不能推出线程持有的其他资源已按要求释放 |

【源码实现】A 的 `true_isp_init()` 没有检查 `pthread_create()` 返回值，随后直接把 `g_start_isp[vi_pipe]` 设为真。这个变量不能作为“ISP 线程确实创建且业务运行正常”的充分证据。

B 正确检查了取流线程的创建返回值，但把 `g_para.thread_start` 同时用作运行开关和 join 条件。worker 在获取 fd 失败或循环退出后自行把它设为假，`venc_stop_get_stream()` 又只在它为真时 join。

这意味着：worker 提前结束时，主线程以后可能跳过对已创建线程的 join。该分支是源码可确认的；是否在具体板端触发，需要运行证据。主循环也没有根据 worker 的退出结果结束应用，因此“主进程仍在”不代表取流还在工作。

学习时可把更完整的设计理解成四份记录：创建标志、停止请求、结束原因、join 完成标志。它们可以放在同一上下文中，但不能用同一个布尔值替代。

### 10.2.2 信号标志只负责提出退出请求

A 的 `handler()` 只修改 `volatile sig_atomic_t g_loop_running`；它在进入发送阶段后注册 `SIGINT`。B 的 `sample_venc_handle_sig()` 对 `SIGINT`、`SIGTERM` 设置 `g_sample_venc_exit`，类型为 `volatile td_bool`。

信号处理函数尽量只提出请求，把媒体 API、内存释放、日志收尾交回普通执行流程，原因是信号可能在任意执行位置到达。A 的标志类型符合这种简单信号通知用途；B 的类型应结合平台定义检查信号访问保证。

`volatile` 不等于线程间同步。B 的 `g_para.thread_start` 被两个普通线程访问，单靠读写一个开关没有表达互斥、内存可见性和生命周期先后关系。若以后整理实现，应选择原子状态或受锁保护的上下文，并让等待操作可以被停止请求唤醒。

这属于设计建议，本任务没有修改信号或线程代码。

## 10.3 从 GetStream 到 ReleaseStream：借用不是所有权转移

### 10.3.1 两类内存必须分开

前面的取流章节已经区分 SDK pack 与图像、NAL、RTP 包。这里再从所有权看一次：

| 对象 | 谁准备或管理 | 当前使用方式 | 使用结束时做什么 |
|---|---|---|---|
| pack 描述符数组 | 应用 | A 使用栈上 32 个元素；B 按 `cur_packs` 分配 | A 离开函数自动失效；B `free()` |
| pack 指向的编码字节 | SDK/编码系统 | 应用在 GetStream 成功后读取有效区间 | 调用对应的 `ReleaseStream()` 归还 |
| A 的发送缓冲区 | 应用 `malloc()` | 拼接 FU 或 RTP 数据 | 应用应在不再发送后释放；当前缺少清理 |
| B 的 RTP 环形队列 | RTSP 库分配 | 保存封装后的 RTP 字节，供客户端继续发送 | 会话销毁时释放 |

`addr + offset` 与 `len - offset` 描述的是这一份借用中有效字节的位置和长度。描述符数组释放与码流归还是两种不同操作，不能互相代替。

A 的 `processStream()` 和 B 的 `venc_get_and_send_one_frame()` 都在同步发送调用返回后归还码流。B 的 RTP 封装把数据写入库自己的队列，后续客户端发送使用队列中的字节，不继续保留原始 SDK 指针。

### 10.3.2 为什么异步发送会改变资源合同

假设以后把网络发送搬到另一个线程：取流线程把 `pack.addr` 放进工作队列，然后立即 `ReleaseStream()`。此后编码器可以重用那块内存，网络线程读到的内容就未必仍属于原来的图像。

因此异步化必须明确选择一种方式：在归还前复制到应用所有的有界缓冲区，或者依据 SDK 正式接口延长持有期。后者也会占住编码资源，网络变慢时可能阻塞上游；不能仅为减少一次复制而无期限持有码流。

同理，A 的固定 32 个描述符必须覆盖实际 `cur_packs`。当前将查询结果直接写入 `stream.pack_cnt`，没有容量检查。B 的动态分配解决了“固定容量”问题，但还需要考虑合理上界、内存申请失败和逐次分配成本。

## 10.4 消费者变慢时，等待或丢弃出现在哪里

### 10.4.1 A 用非阻塞 UDP 让发送尽快返回

【源码实现】`rtp_send()` 给 UDP socket 设置 `O_NONBLOCK`；`transmit()` 调用 `sendto()`，但没有检查返回值。非阻塞表示本次操作不为等待可用发送空间而一直阻塞，并不保证报文成功交给网络，更不保证对端收到。一般语义见 [send(2)](https://man7.org/linux/man-pages/man2/send.2.html)。

当本地发送条件不满足时，程序仍会继续处理后面的 pack 并归还 SDK 缓冲。这样减少了网络阻塞长期占有码流的机会，但丢弃没有反馈到当前统计和业务状态中。

背压是下游消费速度不足对上游造成的限制。这里有的层选择等待，有的层选择丢弃：硬件缓冲耗尽可能影响取流；UDP 发送失败后当前代码继续；已经进入内核队列的数据则可能继续排队。这些现象不能统称为“网络卡了”。

### 10.4.2 B 为每个客户端记录消费位置

[rtsp_demo.c](../../sample_source/rtsp_4m/rtsp_lib/rtsp_demo.c) 的会话持有 `vstreamq`，客户端 RTP 连接持有 `streamq_index`。队列保存一份媒体数据，各客户端按自己的位置消费。

[stream_queue.c](../../sample_source/rtsp_4m/rtsp_lib/stream_queue.c) 用 `head`、`tail` 管理环形空间。生产者为新 RTP 包准备空间时，必要时推进队头，丢弃旧包；落到有效区间之外的慢客户端被移到当前 `head`。源码旁的注释写了 tail，实际赋值是 head，应按赋值理解。

【源码实现】配置为 601 个槽位，留一个槽区分满与空，最多保存 600 个 RTP 包。包不是视频帧，600 包不能直接换算成固定秒数。当前准备空间按最多 300 包进行，实际保留窗口还与每次封装的包数和预留动作有关。

这是一种有界丢弃策略，避免为慢客户端无限增长内存。但丢弃点不一定落在可独立解码的图像边界；客户端跳过一些参考数据后，可能要等待后续有效刷新才能恢复画面。

### 10.4.3 TCP 的可靠字节流仍需要正确处理短写

TCP interleaved 把 RTP 包放进 RTSP TCP 连接，前面加 4 字节框架头。当前 `rtp_tx_data()` 分别 `send()` 框架头和载荷，只针对 `SOCKET_ERROR` 分支处理，没有维护“已经发送多少字节”的状态。

两种边界尤其值得理解：一次 `send()` 返回正数但不足请求长度时，剩余字节仍待发送；框架头已经发出、载荷遇到暂不可写时，重试需要继续当前载荷，而不是重发整个框架。

当前实现未保存这些进度。慢连接下可能出现应用层边界损坏，这是源码推导的运行风险，尚非本项目现场复现记录。可靠传输协议也无法修复应用遗漏或重复提交的字节。

合理的发送上下文要同时记录缓冲所有权、总长度、已发送偏移，并在可写事件到来后续传；完成或明确丢弃连接前不能回收仍被引用的队列槽位。

## 10.5 网络事件与视频输入耦合在哪里

【源码实现】当前调用链为：

```text
VENC chn0 有可发布 pack
  → venc_get_and_send_one_frame()
  → rtsp_sever_tx_video()
  → 封装、入队、尝试发送
  → rtsp_do_event()
  → 接受连接、收请求、处理会话、继续发送
```

`rtsp_do_event()` 内部使用零超时 `select()`，但应用没有独立循环周期性调用它。若主码流停止、worker 提前退出，或者连续处理的都是被跳过的 pack，就不能假定 RTSP 请求仍会推进。仅有 chn1 数据也无助于此，因为 chn1 不进入发布入口。

这个设计将媒体封装和网络状态集中在同一执行者内，减少了共享队列的并发访问；代价是网络控制面的活性依赖视频输入。

若要解除耦合，可以让同一个事件循环独立调度媒体就绪和网络就绪；也可以引入明确的跨线程消息队列。不能直接再开线程同时调用 `rtsp_do_event()`：当前会话、客户端列表和环形队列没有因此自动获得线程安全保证。

## 10.6 退出顺序来自资源依赖

### 10.6.1 B 已有的显式退出链路

【源码实现】正常响应退出标志时，B 先执行 `venc_stop_encode()`：请求 worker 停止并尝试 join，然后解绑 VPSS/VENC、停止编码通道。接着 `stop_sys_vi_vpss()` 解绑 VI/VPSS，停止 VPSS、VI，退出 SYS。

公共 `sample_comm_vi_stop_vi()` 先停止 ISP；`sample_comm_vi_stop_one_pipe_isp()` 调用 ISP exit，再通过 `sample_comm_isp_stop()` join 运行线程，并注销 Sensor 库。最后主函数删除 RTSP 会话和服务器。

这个顺序的核心是让使用资源的执行者先停下。前述 worker join 条件与共享标志仍有局限，因此应理解为“存在清理主干”，不能理解为所有退出边界已经验证。

worker 的 VENC `select()` 使用 2 秒超时。它给没有数据时再次检查停止标志提供机会；它不是每帧强制增加 2 秒延迟，也不是整个退出过程绝不超过 2 秒的保证。后续 SDK 调用和 ISP join 是否及时返回仍需单独观察。

### 10.6.2 A 应补齐的设计与当前缺失

下面是按依赖关系提出的退出设计，**不是当前 A 已经实现的调用链**：

1. 提出停止请求，让取流/发送循环结束，并保证所有已借出的 stream 已归还。
2. 解绑并停止、销毁 VENC，再停止依赖它的发送上下文，关闭 socket、释放应用发送缓冲。
3. 解除 VI/VPSS 关系，停止并销毁 VPSS；按 SDK 要求退出 ISP，使运行线程返回后 join，再停止 VI/MIPI 相关资源。
4. 最后退出 SYS/VB，清理初始化阶段打开的文件、设备 fd 和临时内存。

具体媒体停止与解绑 API 顺序还须遵循该 SDK 的接口约束；公共示例提供可对照的组织方式，不能盲目照搬其他模式。

当前 A 还在 `isp_calibration_load_bin()` 中打开 PQ 文件并分配整文件缓冲，但函数没有对应的 `fclose()`、`free()`；`vi_init()` 打开的 MIPI 设备 fd 也缺少关闭。这些资源不因变量离开作用域而自动释放。

初始化失败也需要同一套资源账本：只回收已经成功取得的资源，并保留最早的失败原因。否则后续失败日志可能掩盖真正断点，“正常退出”字样也失去意义。

## 10.7 自查问题与回答要点

**问题 1：线程函数已经返回，为什么还要 join？**

回答要点：结束执行与管理者回收 joinable 线程是两件事；是否需要 join 应由创建记录判断，不能只看循环开关。

**问题 2：把 GetStream 的地址塞进队列后立即 ReleaseStream，可否减少复制？**

回答要点：地址仍由 SDK 管理，归还后可能复用；必须复制到应用自有缓冲或有正式持有机制，同时限制排队长度。

**问题 3：RTSP TCP 连接成功，但停止视频后请求无响应，先追哪条链？**

回答要点：确认 `rtsp_do_event()` 的调用是否仍发生；当前由主码流发送入口驱动，监听 socket 存在不证明用户态事件持续处理。

**问题 4：增加一个网络线程是否就能解决慢客户端问题？**

回答要点：还需确定队列容量、数据所有权、并发访问和丢弃策略；TCP 要保存部分发送进度，线程数量本身不解决背压。

下一章把这些资源状态映射到构建、板端启动、编码输出和接收解码四类证据，说明每一项检查究竟能证明哪一段链路。
